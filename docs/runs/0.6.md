# Run 0.6: TipTap on Android

**Model:** S·low

## Goal

Find out how the TipTap editor (ProseMirror) behaves in Android browsers, before the real editor is built in 1.11 and 1.12. You test by hand from the checklist below; Claude fixes what is fixable and records the rest as findings for 1.12 and `docs/spike-findings.md` (0.7).

## Setup

On the PC (already started by Claude when this run began; otherwise):

```bash
docker compose -f spike/docker-compose.yml up -d --wait
dotnet run --project spike/server/Spike.Server           # :5080
pnpm --dir spike/client dev:lan                          # :5173, listening on the LAN
```

On the phone (same Wi-Fi as the PC): open `http://192.168.1.11:5173/?page=android&user=phone`.

- The page is plain HTTP on a private address, so some browser features (clipboard API, service workers) behave differently than on the real HTTPS site. Typing, selection and the on-screen keyboard are not affected.
- If the page doesn't load: Windows Firewall must allow inbound TCP 5173 on the Private profile (a rule for Node.js exists today), and the phone must be on the same network as the PC (not a guest network).
- Open the same page on the laptop (`http://localhost:5173/?page=android&user=laptop`) to see sync and presence while you type on the phone.

## Findings

**Tested:** one Android phone, Chrome and Firefox; Gboard and SwiftKey. Firefox + Gboard was skipped on purpose (the pattern was already clear from the other three). Lines 1–14 and 16–20 and 22 worked everywhere, including autocorrect, suggestions, glide and voice typing, selection, markdown shortcuts, lists, the keyboard opening and closing, rotation, emoji, sync with the laptop, and a long page. Only lines 15 and 21 had problems.

### Line 15, undo: ⚠️

- SwiftKey offers no undo at all.
- Gboard's undo works, but only one character at a time, and it seems to take two taps for it to take effect.
- Not diagnosed. The spike editor has no undo UI and the Yjs undo manager is only bound to the keyboard shortcuts, which a phone doesn't have. **For 1.12:** the mobile editor needs its own undo and redo buttons driven by the editor's commands, and shouldn't rely on the keyboard's undo.

### Line 21, reconnect: ❌, fixed in this run

What you saw: with Wi-Fi off, text typed on the phone and on the laptop never merged; the laptop's text "won" because it stayed connected.

Cause, reproduced in a test: when a phone loses its network, **nobody closes the WebSocket**. The browser still reports it as open, so the client kept writing edits into a dead connection and never reconnected, and the server never learned the phone was gone. My earlier offline tests cut the connection cleanly, which a real network drop doesn't do, so they missed it. A silent-death scenario (`blackhole()` in the e2e client: the socket stays open but nothing passes) failed in exactly the way you saw: each side kept only its own text for 40 s.

The fix:

- **Heartbeat.** The client pings every 3 s and drops a connection that has been silent for 8 s. Ping and pong are a single byte, with no page id. Any message counts as proof of life.
- **Browser events.** On `offline` the client drops the socket at once; on `online` it reconnects immediately, without waiting for the backoff and without trusting a socket from before the outage.
- **Late close events are ignored.** A socket the client has given up on may report its close much later; every handler first checks that its socket is still the current one, so it can't disturb the connection that replaced it.
- **Server keep-alive.** The server now pings clients every 15 s with a 15 s timeout (the default interval is two minutes), so a vanished phone leaves the presence list within about 30 s instead of minutes. This part is not covered by a test: the e2e harness keeps the server side of the route open.

After the fix the silent-death scenario merges in about 10 s, and the offline and online events scenario merges within seconds. Both pass 20 out of 20 times in a repeated run.

- **For 1.09 and 1.12:**
  - The production hub needs the same ping and pong and server keep-alive, and a limit on how fast a client may ping.
  - The mobile editor needs undo and redo buttons.
  - On a hidden browser tab, timers are throttled, so a tab can drop and reconnect its socket now and then. That is harmless but worth knowing.
- **Not tested:** Firefox with Gboard, and anything with HTTPS or a service worker (the phone used plain HTTP on the LAN).
- **Surprising:** the only real defect in the whole Android checklist was not in the editor at all; it was in connection handling that a desktop browser test can't show.
