# Run 0.2: persistence, one socket per session, multi-tab and presence

**Model:** O·high → S·med (planned and executed on Opus 5.5)

## Goal

Append updates to Postgres and rebuild a page from them on reconnect; one WebSocket per session with page-id multiplexing; several tabs of the same user on one page with no duplicate updates and presence shown sensibly.

## Inputs

- `docs/architecture.md`: "Sync flow" steps 1–4, "Server CRDT handling" (opaque blobs), Phase 0 table.
- Run 0.1 handoff.

## Done when

- A brand-new client rebuilds a page from Postgres alone, also after a server restart.
- One socket carries several pages; frames never leak between pages.
- Two tabs on one page store each edit exactly once; reconnecting after offline edits stores exactly one diff.
- Presence groups one user's tabs ("jos (2 tabs)") and a closed tab disappears within 1 s.

## How to run

```bash
docker compose -f spike/docker-compose.yml up -d --wait   # Postgres on 127.0.0.1:5434
dotnet run --project spike/server/Spike.Server            # http://localhost:5080 (Development)
pnpm --dir spike/client dev                               # http://localhost:5173/?pages=a,b&user=jos
pnpm --dir spike/client check:sync                        # headless Yjs clients against :5080
dotnet test spike/server                                  # needs Docker (Testcontainers)
```

## Design

**Wire protocol.** lib0 encoding (the same as y-protocols). Every frame is `[varuint type][varstring pageId][payload]`:

| Type | Direction | Payload |
| --- | --- | --- |
| 0 `SUBSCRIBE` | C→S | none |
| 1 `UNSUBSCRIBE` | C→S | none |
| 2 `UPDATE` | both | varUint8Array Yjs update |
| 3 `SYNC` | S→C | varuint count, then count × varUint8Array |
| 4 `AWARENESS` | both | varUint8Array awareness update |

- Page ids are 1–128 chars.
- Frames over 1 MB, malformed frames, and updates or awareness for a page that wasn't subscribed close the socket with a policy violation.

**Decisions:**

1. **The client computes the diff, not the server (deviation from the architecture).**
   - On subscribe the server sends every stored update; it cannot diff opaque blobs.
   - The client merges them (`Y.mergeUpdates`), derives the server's state vector (`Y.encodeStateVectorFromUpdate`), applies the merge, and sends back only `Y.encodeStateAsUpdate(doc, serverSV)`.
   - Revisit the architecture's "server replies with the missing diff" after 0.4 (YDotNet).
2. **Local edits are held until the page is synced.** The diff sent after `SYNC` covers them, so nothing reaches the server twice.
3. **One `SemaphoreSlim` per page.**
   - Register, load and queue `SYNC` run under it; so do append and broadcast.
   - With the ordered send queue per connection, a subscriber gets every update exactly once, either in the `SYNC` or live.
   - The update is stored before it is broadcast. If storing fails, the socket closes and the client's reconnect diff resends the edit.
4. **Tabs only meet through the server.** No BroadcastChannel. Every tab has its own random Yjs `clientID`, which is never persisted.
5. **Presence.**
   - y-protocols awareness carries `{ user: { name, color } }`, with the name from `?user=` or localStorage, so it is the same in every tab.
   - The server keeps the latest entry per awareness client per page, in memory only. A new subscriber gets it at once.
   - When a connection unsubscribes or drops, the server broadcasts removals with the **same clock** and a `null` state. y-protocols applies a null state at an equal clock, and a reconnecting client's re-announce (clock + 1) is accepted again. A clock + 1 removal would block that re-announce.
6. **Storage.** Plain Npgsql, schema created on startup. Table `page_updates`: id as identity, `page_id`, `data`, `created_at`, plus an index on `(page_id, id)`. `id` is the future compaction watermark.

## Handoff

- **Done:**
  - Server: lib0 codec and frames; `PostgresUpdateStore`; `AwarenessCache`; `SyncHub` multiplexing pages over one socket with per-page locks. 20 xUnit tests on Testcontainers Postgres; 5 repeated runs all green. They cover:
    - lib0 vectors byte-exact against JS;
    - ordered load;
    - store-then-relay without echo;
    - multiplexing;
    - unsubscribed-page rejection;
    - a subscriber joining while 300 updates stream in, getting each update exactly once;
    - presence cache and removal on drop.
  - Client: `SyncClient`, presence grouping, multi-page editor UI, and `check:sync` with 5 scenarios plus timing, all passing.
  - Also checked: a page read back intact after a server restart.
- **Numbers:**
  - 200 sequential edits took 2.1 ms per edit for the full round trip: the client sends, the server inserts under the page lock and relays, the other client applies.
  - One row per edit, so typing produces many small rows. Compaction (0.5) is what keeps this bounded.
- **Left / surprising:**
  - Typing in real tabs was checked by hand (`?pages=a,b&user=jos` in two tabs, `?page=a&user=anna` in a third) and in headless Chrome over CDP.
  - A first manual try failed: a stale Vite left over from 0.1 served modules that didn't match the dependency cache after a second Vite start rewrote it, most likely loading Yjs twice. If the editor stops syncing during dev, restart Vite and delete `node_modules/.vite`.
  - A local Windows PostgreSQL service already holds port 5433, so the spike database moved to 5434.
  - Node's type stripping rejects TS parameter properties, so `erasableSyntaxOnly` is now on.
  - Spike gaps carried to 1.09:
    - pages are never evicted from the hub;
    - send queues are unbounded;
    - no auth, Origin check or permission check on subscribe.
  - For 1.09 or 0.4: the full update list on every subscribe grows with history until compaction exists.
