# Run 1.06: CSRF tokens, login throttling, audit log, deny-by-default permissions

**Model:** O·high → S·high (planned on Opus 5.5, built on Sonnet)

## Goal

Every state-changing request carries a CSRF token. Guessing passwords is slow for one account and for one address. Security events land in their own table. Every endpoint goes through one permission service, and a test fails for any endpoint that does not say who may call it.

## Inputs

- `docs/architecture.md`: "Security from day one" (CSRF, rate limiting with lockout backoff, audit log, deny-by-default), "Permission resolution" (implemented in phase 2, 2.2), data model (`workspace_members`).
- Run 1.05: cookie auth, `JsonOnlyApi`, `FallbackPolicy`, `ApiError`, the e2e setup project.

## Done when

- A state-changing API call without a valid CSRF token gets 400 `csrf_invalid`. The web client never sees that error in normal use.
- Five wrong passwords lock that email for a minute, doubling up to 15 minutes. An unknown email behaves exactly the same. One address gets at most 10 login or setup attempts a minute.
- Setup, login (successful, failed, locked), logout and logout everywhere are written to `audit_events`.
- `IPermissionService` answers "what role does this user have on this workspace or page" from `workspace_members`. Endpoints declare the role they need, and denial is 404 (no access at all) or 403 (lower role).
- `EndpointPolicyTests` fails, naming the endpoint, when any endpoint has no named policy and is not on the reviewed anonymous allow-list.

## Design

No new packages: Antiforgery and rate limiting are in the ASP.NET shared framework.

### 1. CSRF (`CsrfProtection`)

- ASP.NET **Antiforgery**:
  - the cookie token is `inkpact-csrf` (HttpOnly, SameSite=Strict, Secure on HTTPS through `SameAsRequest`);
  - the request token travels in the **`X-CSRF-Token`** header;
  - tokens are bound to the signed-in user, so a token from before login stops working after it.
- **Delivery:** `GET /api/auth/state` also returns `csrfToken`, and sets the cookie with `GetAndStoreTokens`. The client already calls it on start and after every login, setup and logout, so it always holds a token for the current identity.
- **Middleware**, after `UseAuthentication`:
  - for POST, PUT, PATCH and DELETE under `/api`, `IAntiforgery.ValidateRequestAsync`;
  - on failure, 400 `{ code: "csrf_invalid" }`.
  - Login and setup are covered too, which closes login CSRF.
- **No `__Host-` prefix on this cookie.** Antiforgery has one fixed cookie name, and the per-request name trick from 1.05 would mean reimplementing its token store. The risk is small: a request token is bound to the user's identity, so a planted cookie only helps an attacker against the anonymous login form. And the JSON-only rule from 1.05 still blocks cross-site forms on its own.
- **Client:** `api.ts` sends the header with the token from the last state answer. On `csrf_invalid` it reloads the state once and retries once (a token can expire, or another tab can sign out), then gives up.

### 2. Login throttling

**Per address:**
- the built-in rate limiter, a fixed window of `Auth:Throttle:PerAddressPerMinute` (default 10), partitioned by `RemoteIpAddress` after forwarded headers;
- applied to `POST /api/auth/login` and `/setup`;
- 429 `{ code: "too_many_requests" }` with `Retry-After`.

**Per email, the lockout backoff** (table `login_throttles`):

| Column | Type | Notes |
| --- | --- | --- |
| `key` | text | Primary key: SHA-256 hex of the normalized email, so strangers' typed addresses are not kept here |
| `failures` | int | |
| `locked_until` | timestamptz | Null when not locked |
| `last_failure_at` | timestamptz | |

How it behaves:
- After `Auth:Throttle:FailuresBeforeLock` (default 5) failures, the email is locked for 1 minute, then 2, 4, 8, and at most 15.
- A success deletes the row. A row with no failure for 24 hours counts as fresh.
- While locked, no password is checked (a dummy hash is, for the same timing), and the answer is 429 `{ code: "login_locked" }` with `Retry-After`.
- **The same rules apply whether or not the account exists**, so the lockout reveals nothing.
- Concurrent failures may each read the same count and lose an increment; the per-address limit bounds what that buys an attacker. Recorded, not fixed (raw SQL would be needed).
- **Trade-off to accept:** anyone can lock a known email for up to 15 minutes at a time. Existing sessions are not affected, only new logins.

### 3. Audit log (`audit_events`, `IAuditLog`)

| Column | Type | Notes |
| --- | --- | --- |
| `id` | bigint identity | |
| `occurred_at` | timestamptz | |
| `type` | text | `setup_completed`, `login_succeeded`, `login_failed`, `login_locked`, `logout`, `logout_everywhere` |
| `user_id` | uuid, null | FK, set null when the user is deleted |
| `email` | text, null | The address typed, for failed and locked logins |
| `ip` | text, null | After forwarded headers |
| `user_agent` | text, null | Truncated to 256 |

- Index on `(occurred_at)` and `(user_id, occurred_at)`.
- Written by the endpoints with awaited inserts. A failing insert fails the request, so the log has no silent gaps.
- Rate-limiter rejections go to the application log only, because an attacker could flood the table.
- No API or UI yet (admin page 2.9). No retention yet (B.7 decides; recorded in the architecture).

### 4. Permissions

**Schema (migration `AddPermissions`):**
- `workspace_members`: `workspace_id`, `user_id`, `role` (text: `owner`, `editor`, `viewer`) and `created_at`, with the primary key on the workspace and user, and a cascade from both.
- The migration backfills one owner row per existing workspace. Setup now inserts the owner row in its transaction.

**`Role` enum:** `None < Viewer < Editor < Owner`.

**`IPermissionService`** (scoped):
- `GetWorkspaceRoleAsync(userId, workspaceId)` reads the membership.
- `GetPageRoleAsync(userId, pageId)` reads the page's workspace membership. Shares and ancestors are added in 2.2, behind the same method.
- Results are cached per request. **This is the only place that decides access.**

**Enforcement:**
- `.RequireWorkspaceRole(Role.Viewer, routeParameter: "workspaceId")` and `.RequirePageRole(...)` add metadata plus an endpoint filter.
- The filter parses the route value. A malformed id is 404.
- With no role at all the answer is 404 `not_found`, so ids of other people's workspaces don't leak. With a role that is too low it is 403 `forbidden`.
- These also add the `signed-in` policy.

**Named policies (`Policies`):** `signed-in` and `admin` (`is_admin`, read from the database by the permission service, not from a claim). Every endpoint names one; a bare `.RequireAuthorization()` no longer passes the test.

**First real endpoints**, which 1.08 needs anyway:
- `GET /api/workspaces`: the caller's workspaces with their role (`signed-in`).
- `GET /api/workspaces/{workspaceId}`: requires Viewer.

### 5. The coverage test (`EndpointPolicyTests`)

- It enumerates every `RouteEndpoint` from the real app's `EndpointDataSource`. Each must either:
  - carry `IAllowAnonymous` **and** appear in the test's `ReviewedAnonymousEndpoints` list (method and pattern: health, auth state, setup, login, the two fallbacks); or
  - carry `IAuthorizeData` with a policy name from `Policies`.
- Endpoints with permission metadata must also have a matching route parameter.
- The failure message lists every offender.
- The test is proven against a throwaway app with an unprotected endpoint, a bare `RequireAuthorization()`, and an anonymous endpoint missing from the list. Each must be reported.

### Client

- `api.ts`: the CSRF header and the retry once on `csrf_invalid`.
- New error codes and messages in both languages:
  - `too_many_requests` and `login_locked` show "Too many attempts. Try again in {time}", with the time from `Retry-After` formatted by `Intl.RelativeTimeFormat`;
  - `csrf_invalid` only shows if the retry also fails;
  - `forbidden`.
- `ApiError` gains `retryAfterSeconds`.

### Tests

**Server:**
- CSRF:
  - no token, a wrong token, or a token from before login → 400;
  - a valid token → passes;
  - a GET needs none;
  - logout with an anonymous token → 400.
- Rate limit: the 11th attempt in a minute from one address → 429 with `Retry-After`; another address is unaffected.
- Lockout, with `MutableTimeProvider`:
  - 5 failures lock; while locked even the right password gets 429;
  - the backoff doubles and caps at 15 minutes;
  - a success resets;
  - 24 hours idle resets;
  - an unknown email gives the same status codes and headers in the same order.
- Audit: every event type is written, with the user, email, ip and user agent; deleting the user keeps the row with `user_id` null.
- Permissions:
  - owner, editor and viewer each get their role;
  - a stranger gets None;
  - a deleted workspace gives None;
  - page role through the workspace;
  - per-request cache (one query);
  - endpoint 404 versus 403;
  - a malformed id gives 404;
  - setup creates the owner membership;
  - the migration backfill.
- The coverage test and its self-test.

**Web:** the header is sent, the retry happens once and only once, the `Retry-After` message is formatted in both languages.

**E2E:**
- The config raises the limits for the run, because the suite signs in about 30 times from one address: `Auth__Throttle__PerAddressPerMinute=600` and `FailuresBeforeLock=10`. The existing wrong-password tests stay below that.
- A new spec locks **an email without an account**, one per project, and checks the message. That proves the lockout without locking the admin.
- The `api.spec` stranger tests expect `csrf_invalid` where a token is now missing.

`docs/architecture.md`:

- "Permission resolution": that phase 1A resolves workspace membership through the same service, and 404 versus 403.

## Not in this run

Shares and ancestor resolution (2.2), the admin and audit views (2.9), audit retention (B.7), password change, and WebSocket Origin and CSRF (1.09).

## Decisions (confirmed)

All six, as proposed: Antiforgery with the token in the state answer and no `__Host-` prefix on its cookie; lockout after 5 failures, 1 minute doubling to 15, 10 attempts a minute per address, identical for unknown emails; the typed email, IP and user agent in the audit log, with no retention or UI yet; 404 for no access and 403 for too low a role; `workspace_members` now with a backfill; every endpoint names a policy.

## As built: changes from the plan

- **The lockout service is `LoginThrottling`**, the table entity `LoginThrottle` (a name clash).
- **Order in the pipeline:** forwarded headers, security headers, JSON-only, authentication, rate limiter, CSRF, authorisation. A request without a token never reaches the password check, so it is not counted or audited (tested).
- **The login page says how long to wait**, formatted with `Intl.RelativeTimeFormat` in the page language, from `Retry-After`.
- **The audit row for setup is written in the setup transaction**, so an account without its audit row cannot exist. The other events are written with their own insert.
- **The `ReviewedAnonymousEndpoints` list** is checked in both directions: an anonymous endpoint that is not on it fails, and an entry on it that no longer exists fails too, so a stale entry cannot let a future endpoint through.
- **The coverage test is proven against a throwaway app** with an unprotected endpoint, a bare `RequireAuthorization()`, an unknown policy name, an unreviewed anonymous endpoint, and a role requirement without its route parameter.
- **The 403 path is tested on a small app with a stand-in permission service**, because the real app has no endpoint that needs more than Viewer yet. Every role against every minimum is covered.
- **Playwright:** the run raises the per-address limit to 600 a minute, because the suite signs in about forty times from one address. The lockout per email stays at its real value. Wrong-password tests use an address nobody has, one per project, so the shared administrator is never locked. A new `lockout.spec.ts` locks such an address and checks the message in both languages. The anonymous API tests fetch a token first, as the client does. `.prettierignore` skips the generated `e2e/.auth`.
- **Not fixed, as planned:** two failures at the same moment can read the same count and lose an increment. The per-address limit bounds what that is worth to an attacker, and fixing it needs a statement EF cannot express (raw SQL is for tree queries only).

## Handoff

- **Done:** CSRF, login throttling, the audit log, membership, the permission service and the coverage test.
- **For 1.07 and later:** new endpoints use `RequireWorkspaceRole` or `RequirePageRole` and must be added to nothing else; the coverage test then passes by itself. A new anonymous endpoint needs an entry in `EndpointPolicyTests.ReviewedAnonymousEndpoints` and a reason.
- **For 1.09:** the WebSocket upgrade must check the CSRF token or the `Origin` (planned there), and authenticate through the same cookie.
- **For 2.2:** shares and ancestor resolution go inside `PermissionService.GetPageRoleAsync`; endpoints do not change.
- **For 2.9 and B.7:** reading the audit log, and how long to keep it.
