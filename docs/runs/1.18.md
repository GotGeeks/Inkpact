# Run 1.18: Export to Markdown

**Model:** S·med in the roadmap. Planned on Opus 5.5 high; 1.18a builds on Sonnet 5.5 high (it adds a sidecar operation, part of the codec's contract), 1.18b on Sonnet 5.5 medium. `/code-review` at high on Opus before each PR merges: the export is the promise that the data is yours, so what it leaves out is lost the day someone relies on it.

## Goal

At any time, a person downloads everything they can read in a workspace as one zip of Markdown files and attachments, which opens without Inkpact: in a text editor, Obsidian, Joplin's Markdown import or a file browser. Every page is there, in the tree it has here, with its title, text, pictures, files and links between pages. A page exported and read back by the import's own Markdown converter gives the same document.

## Inputs

- `docs/architecture.md`: the core principle ("export everything to standard Markdown plus attachments, without needing Inkpact to read it"), the 1.18 row, "Attachments", "Permission resolution", the `pages` table (title, to-do fields, dates), "Sync flow" (a page is its snapshot plus its updates).
- `docs/runs/1.10a.md`: the sidecar's operations, framing and contract tests.
- `docs/runs/1.15.md` and `1.16.md`: the Markdown converter, the editor's nodes and marks, links between pages (`/p/<id>`), notes stored as files.
- The code as it is:

  - `Crdt/IYjsCodec.cs`, `YjsSidecar.cs`; `Sync/PageUpdateStore.cs` (a page's inputs);
  - `Import/MarkdownConverter.cs`, `JoplinContent.cs`, `ContentRules.cs`;
  - `Attachments/` (the store, `AttachmentFiles`), `Pages/TreeService.cs` (`live_pages`);
  - `web/src/layout/UserMenu.vue`.

## What the code is now (found while planning)

1. **Nothing on the server reads a page's content as a document.** The sidecar builds Yjs from ProseMirror JSON (`build`, `replace`) and gives a page's plain text (`compact`), but no operation turns a page back into JSON. The text alone loses headings, lists, tables, marks, pictures and links.
2. **The editor's schema is small and listed in one place.** `NODE_ATTRIBUTES` and `MARK_ATTRIBUTES` in `build.ts` (checked against the real editor by a test in `web/`): paragraphs, headings 1 to 6, quotes, bullet and numbered lists, task lists, code blocks with a language, rules, hard breaks, tables (with merged cells and alignment), images and file nodes; bold, italic, strike, underline, code and links. Everything has a Markdown form except underline and merged table cells.
3. **The import already reads Markdown into this schema** (`MarkdownConverter`, Markdig with tables, task lists, footnotes and maths, HTML through `HtmlConverter`). It is the natural judge of a round trip.
4. **Titles, tags, to-do fields and dates are on the page row, not in the document.**

## Decisions

1. **Two runs.**
   - **1.18a, a page as Markdown:** the sidecar's new `read` operation and `IYjsCodec.ReadAsync`, the Markdown writer, and the round-trip tests. No zip, no endpoint.
   - **1.18b, the export:** the zip (layout, names, attachments, links between pages), the endpoint, the menu item, the guide.
2. **`read` in the sidecar** (`server/sidecar/src/read.ts`, new opcode): the inputs (snapshot and updates, as `compact` takes them) replayed into a document, and its `default` fragment written out as ProseMirror JSON. It is the inverse of `build`: element name and attributes, text with its marks from the delta's attributes, and only what `NODE_ATTRIBUTES` and `MARK_ATTRIBUTES` allow (anything else is left out, and counted in the answer, so a test can see it). An explicit stack, as `text.ts` has. Contract tests: `build` then `read` gives the same JSON for a document with every node and mark; a page of the edit streams reads back as what the editor made. No new dependency.
3. **The Markdown writer** (`Export/MarkdownWriter.cs`), from that JSON, CommonMark with the GitHub extensions the import reads:
   - headings `#` to `######`; paragraphs; `>` quotes; `-` lists and `1.` lists (keeping `start`); task lists `- [ ]` and `- [x]`; fenced code blocks with the language, the fence longer than any run of backticks in the code; `---` rules; hard breaks as a backslash at the end of the line;
   - `**bold**`, `*italic*`, `~~strike~~`, `` `code` `` (with enough backticks), links `[text](address "title")`;
   - **underline** as `<u>…</u>`, the one mark Markdown has no form for (inline HTML, which the import reads back);
   - **tables** as GFM pipe tables with their alignment; a table with a merged cell (`colspan` or `rowspan` above 1), or a cell holding more than one paragraph or a list, as an HTML table, since a pipe table cannot hold it;
   - **pictures** `![alt](path)` and **files** `[name](path)`, the path given by the caller (1.18b puts them in the zip);
   - **links between pages** (`/p/<id>`): the address given by the caller (1.18b makes it the relative path to the other page's file); a link to a page that is not exported (in the trash, say) stays `/p/<id>`;
   - **text is escaped** where Markdown would read it as markup (`*`, `_`, `` ` ``, `[`, `]`, `<`, `#` and `-` and `+` and `1.` at the start of a line, `|` in a table, a backslash), and only there, so the file still reads as prose.
4. **Front matter** (YAML) at the top of each file, with what is on the page row: `title`, `id`, `created`, `updated`, `tags` (when there are any), and for a to-do `todo: true`, `completed` and `due` (when set). Obsidian, Joplin's Markdown import and most static-site tools read it; a person reading the file sees it plainly. The title is not repeated as a heading: it is not one in Inkpact either. Question 2.
5. **The round trip** (the 1.18 row's "round-trip test with the import"): a page written as Markdown and read back by the import's `MarkdownConverter` gives the same document, with links between pages and paths of files mapped back. Tested on a document with every node and mark, on the edit streams' pages, on the Joplin fixtures the import tests use (imported, exported, read back), and as an FsCheck property over generated documents (nesting, marks crossing word boundaries, text full of Markdown's special characters). Where the two cannot be equal by design it is listed, not hidden: two adjacent lists of the same kind become one, and white space at the ends of a paragraph is not kept.
6. **The zip (1.18b):**
   - **Layout:** a page is `Title.md`; the pages under it are in a folder `Title/` beside it (`Notes.md` and `Notes/Ideas.md`). Question 1.
   - **Names:** the title with the characters a file name cannot hold (`/ \ : * ? " < > |`, control characters, a trailing dot or space) made a dash or left out; Windows' reserved names (`CON`, `NUL` and the like) get a `_`; cut at 100 characters; `Untitled` for an empty title; two siblings with one name are `Name.md` and `Name (2).md`, in tree order, so an export of the same tree is the same zip.
   - **Attachments:** in `_attachments/` at the top, each under its own file name, one copy per content (SHA-256): a file that is on two pages is in the zip once; two different files with one name get ` (2)`. Pages link to them with a relative path (`../_attachments/manual.pdf`), spaces and brackets percent-encoded so every Markdown reader follows the link.
   - **What is in it:** the pages of `live_pages` (not the trash), and their attachments; no Yjs, no history, no accounts. A `README.md` at the top says what the export is, when it was made, and how pages and files are laid out, in the person's language.
7. **The endpoint (1.18b):** `GET /api/workspaces/{id}/export`, `RequireWorkspaceRole(Viewer)`: whoever may read the workspace may take it. The zip is written straight into the response while it is made (`ZipArchive` on the response stream, no temporary file, nothing kept on the server), named `inkpact-<workspace>-<date>.zip`. Pages are read one at a time (a page's inputs, the sidecar's `read`), so memory stays the size of the largest page. Files are copied from the store as they are; Markdown is compressed, pictures and other files stored as they are (they are mostly compressed already).
   - Weighed: a background job with a file in `/data/exports` and a link when it is done. It survives a dropped connection, but it is a queue, a state, a clean-up and a file of all the data on the server's disk; the streamed zip has none of that. A broken download is started again.
   - A page the sidecar cannot read (it is down) fails the export with `sidecar_unavailable` before anything is sent when it is the first; later, the zip ends early and the browser shows the download as failed. Never a zip that looks whole and is not.
8. **The menu (1.18b):** "Export everything" in the account menu, a plain download link to the endpoint (cookie, no CSRF on a GET), with a line under it that it can take a minute for a large library. Both languages.

## Done when

**1.18a**
- `read` gives back what `build` was given, for every node, attribute and mark, and its contract tests pass against the real sidecar.
- Every node and mark of the editor has its Markdown (or, for underline and merged cells, HTML) form.
- Markdown written for a page and read back by `MarkdownConverter` gives the same document, for the fixtures and as a property over generated documents.

**1.18b**
- A download of the export of a workspace with nested pages, pictures, files, links between pages, an empty title, two pages with one title, a page with an attachment used twice, and a page in the trash: the tree is there as folders, every page once, every file once, every link resolves inside the zip, nothing from the trash.
- The zip opens in Windows' and macOS's own archive tools (tested by reading it back with `System.IO.Compression` and by the names rules); names are valid on Windows, macOS and Linux.
- A viewer can export, a stranger gets 404.
- 5,000 pages are exported in under a minute on this laptop, with memory flat (`Category=Slow`).
- The menu item downloads the zip, on desktop and phone (Playwright), in both languages; no CSP violation.

## Out of scope

- Importing the export again (a Markdown import is a later run; the round trip here is the import's converter).
- Exporting a single page or notebook (B.4 or later), PDF or HTML exports, version history.
- Encrypting the zip.

## Questions

1. **How is the tree laid out?** A page as `Title.md` with the pages under it in a folder `Title/` beside it (as Obsidian and most tools expect), or a folder per page with its own text inside (`Notes/Notes.md`, or `Notes/index.md`)? Recommended: the file beside the folder; a reader sees every note as a file with its title.
2. **Front matter or not?** YAML front matter with the title, id, dates, tags and to-do fields (recommended: nothing on the page row is lost, and the tools that read Markdown folders understand it), or plain Markdown with only the text, and the metadata lost?
3. **Pages in the trash:** left out (recommended: an export is what you have, and the trash is emptied after 30 days anyway), or in a `_trash/` folder?

## For the trial

- Export on the phone: the download starts and ends.

## Handoff

### 1.18a, a page as Markdown (built on Sonnet 5.5)

**Done:** decisions 2, 3 and 5 of the card (the recommended answers to its questions: the file beside its folder, front matter, the trash left out; those are 1.18b's). No migration, no endpoint, no new dependency.

**What was built:**
- **Sidecar `read`** (`server/sidecar/src/read.ts`, `OP_READ = 6`): a page's inputs replayed, its `default` fragment walked with a stack of its own (bounded at depth 200) and written as ProseMirror JSON in the schema's names (`NODE_ATTRIBUTES`, `MARK_ATTRIBUTES`); marks in a fixed order; null attributes left out as `build` leaves them; whatever the schema does not have (an unknown node, mark or attribute, an embed) is left out and counted. The answer is `[json, count]`.
- **`IYjsCodec.ReadAsync`** (`YjsRead(Json, Skipped)`) and `YjsSidecar.ReadAsync`; the two fake codecs in the import tests pass it on.
- **`Export/MarkdownWriter`** (with `MarkdownInline`, `ExportDocument`): a document as CommonMark with the GitHub tables and task lists. `ExportLinks` gives the paths of pictures, files and other pages (1.18b fills them in; the tests give `:/id`, which the import maps back).
  - Blocks: headings, paragraphs, quotes, bullet, numbered (keeping `start`) and task lists, fenced code (the fence longer than any backtick run, the language only when it is a word), rules, pictures, pipe tables (alignment kept), and an HTML table for what a pipe table cannot hold (a merged cell, no header row, more than a paragraph in a cell, a cell of another kind in a body row). Empty paragraphs say nothing in Markdown and are left out.
  - Marks: `**`, `*`, `~~`, `` ` ``, links with their title, and `<u>` for underline. A mark is written as HTML (`<strong>`, `<em>`, `<del>`) where Markdown would not open it: next to a letter when its text starts or ends with punctuation or another marker, and right after another emphasis that closed; a code span after a backtick is HTML too, and a `!` right before a link or a file gets a backslash. White space is outside the marks that end and inside those that go on. A link is inside bold and the others, so that a link in the middle of bold text does not cut the bold in two.
  - Text is escaped only where Markdown reads markup: `\ ` * [ ] ~ ^ | $` always, `_` where it is no part of a word, `<` before anything but white space (an email address in angle brackets starts with nearly anything), `&` before an entity, `=` and `+` doubled, an address in text (`https://`, `www.`, `mailto:`, `tel:`) so that it is not made a link, and the first character of a line that starts a heading, a quote, a list, a rule or a definition, in a paragraph and after a hard break (also after spaces, and with a tab after the marker).
  - Two lists that touch have the other marker (`-` and `*`, `.` and `)`), or Markdown makes them one. An empty task item is `- [ ] &nbsp;` (GitHub shows a checkbox with nothing after it as text). A `|` in a link's address or title in a table has a backslash; code with a `|` makes the table HTML, because GitHub ends the cell there even in code. Code in an HTML table writes the line break before a blank line as `&#10;`, since a blank line ends the HTML block.
- **Docs:** `docs/architecture.md` (the sidecar's operations).

**Where the plan was wrong or open:**
1. **The front matter is 1.18b's, not the writer's:** it is made from the page's row (title, dates, tags, to-do fields), which the writer never sees, so its input is only the document.
2. **Alignment and a column's width are not read back by the import** (`HtmlConverter`/`MarkdownConverter` make cells without `align`), so the round trip does not compare them; the Markdown has the alignment for every other reader.
3. **What the import reads differently from what it wrote** (each is in `DocumentNormal`, with why, and none loses words): an empty paragraph or heading; the white space at the ends of a block, after a break, and at the ends of a run of one mark; code and other marks (a code span is code and nothing else when imported, though the Markdown shows it bold or italic to every other reader); a link's `target`, `rel` and `class`.
4. **Import defects the round trip found, left for later** (the generator does not write them; issue to file): a rule inside a list item splits the list in two; a link inside `<u>` after earlier underline with strike loses the link; a link whose text is `x` first in a heading of a task item is taken for a checkbox; the leading space of a code line in a task item loses one space of the item's indent.

**Checked by tests (all against the real sidecar and the real converter):**
- Sidecar Vitest, 10 new (`read.test.ts`): build then read gives the content back for every node and mark and attribute; the mark order; a page edited by typing; what the schema lacks is left out and counted (5); a page nested 5,000 deep is bounded; every node and mark of the schema is read; the operation's answer, empty inputs, an input that is not an update.
- C# codec contract tests, 4 new tests and 7 cases (`YjsCodecContractTests`): every kind of node back as it was built; a snapshot and updates as the page after all of them; the editor's real pages (the four fixtures) read with the text the compaction finds; no updates and a bad update.
- `MarkdownWriterTests` (89): every node, mark and escape, table-driven, plus where marks must be HTML.
- `MarkdownRoundTripTests` (125): the import's own conversion fixtures (what the import made of Markdown and HTML) written as Markdown and read back by the import: equal but one, a heading with a break (a heading is one line in Markdown), checked on its own. Plus 21 shapes from the review that neither the fixtures nor the generator had (line starts after spaces, a bang before a file, pipes in a table, lists that touch, code with blank lines in an HTML table, a table in a table, `mailto:`, an empty task item).
- `ExportOfEditedPagesTests` (4): the real editor pages, through `read`, the writer and the import.
- `MarkdownRoundTripPropertyTests`: 300 random documents (nesting to 3, marks that cross words, text made of what Markdown reads as markup, tables, pictures, files, task lists, quotes) from a fixed seed, so a run is always the same; `INKPACT_PROPERTY_SEED` and `INKPACT_PROPERTY_RUNS` explore others.

**Not covered / known:** a random search of 2,000 to 3,000 documents on other seeds still finds rare shapes that do not come back. The last ones looked at were emphasis next to punctuation and a link in the same paragraph (for example `***[link](url)~~alpha~~***` in a nested paragraph, and a `!` lost before a mark), where the choice of Markdown or HTML for a mark is still not right. They lose no words and the file is still correct Markdown for another reader, but the import reads one mark differently. They were not chased: they are for an issue.

**Review (Opus 5.5), all 10 findings fixed:** the line starts, the bang before a file, the pipes in a table, the heading's closing hashes (a `#` after a letter is text, so `## C#` has no backslash now), lists that touch, blank lines in code in an HTML table, the code of a table in a table (its line breaks were removed), `mailto:` and `tel:`, the empty task item, and one mark order (`MarkdownInline.MarkOrder`, also for the HTML of a table and in `DocumentNormal`) with the backtick run and the language word in one place each. Six of the 21 shapes already came back with Markdig: the three pipes, the empty task item, a bullet list next to a task list, and a heading ending in hashes after a space. The first four are fixed anyway for GitHub's reader, which is stricter, and the tests keep all six.

**For 1.18b:** `MarkdownWriter.Write(documentJson)` and `ExportLinks`; `IYjsCodec.ReadAsync` gives `Json` and `Skipped` (log a count above 0 once per export). A page whose `read` fails with the sidecar down must fail the export, as the card says.
