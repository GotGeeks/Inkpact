# Run 1.22: A changed large note stays text (#49)

**Model:** a bug-fix run from the trial ("S·med; O·high for anything that loses or corrupts data"). This one changes no data on its own, but it calls the compactor from a new place, and compaction is a critical path (CLAUDE.md, rule 1). So it gets the O·high treatment: planned on Opus 5.5 high, built on Sonnet 5.5 high, `/code-review` at high on Opus before the PR merges.

## Goal

A note of several MB that changes in Joplin is replaced as text at the next import, instead of being turned into a file. Today that happens to a note whose page is over about 4 MiB (the update of a note is about a fifth larger than its text, so about 3.5 MB of text). Nothing a client sees gets worse: a client that opens the page straight after the import gets a page about the size of its new content, and is never dropped.

## What is there now (found while planning)

1. **The rule:** a replacement is text only when the page's stored updates plus the new update fit `Import:MaxNoteUpdateBytes` (8 MiB). A client that opens the page before the compactor has run is sent all of it. So both the old and the new content must fit, which means a note of over about 4 MiB that changes becomes a file (`stored_as_file`). `ImportSizeTests.A_replacement_whose_page_with_the_old_content_would_be_over_the_limit_is_a_file_though_each_alone_fits` tests exactly that.
2. **The window is closed by a lock that already exists.** `WriteReplacementAsync` writes inside `hub.PublishAsync`, which holds the page's room lock while the commit callback runs. A subscribe takes the same room lock before it loads the page (`SyncHub`, the subscribe path). So if the compaction runs inside the callback, after the replacement's transaction has committed, no client can load the page between the write and the compaction. Clients that are already subscribed get only the replacement update, broadcast after the callback, as today.
3. **The compactor needs no change.** `Compactor.CompactAsync(pageId)` keeps every guarantee by itself: its own transaction, the advisory lock (a try, so it never waits), the watermark, verification against a replay, and the archive. It is a singleton, so `ImportRunner` can take it from DI.
4. **"Unchanged since the import" still works after a compaction.** `PageContent.LastSeq` is the snapshot's watermark once the log is compacted, and the compaction's watermark is the replacement's own sequence number. So `row.PageSeq == content.LastSeq` stays true until someone writes to the page.
5. **The compactor can skip or stop short:**
   - `Skipped` when the worker holds the page's advisory lock at that moment;
   - `Unavailable` when the sidecar is down;
   - `Failed` on a verification error;
   - a page with more than `MaxUpdatesPerCompaction` (5,000) live updates takes several rounds, since the oldest are folded first and the replacement is the newest.
6. **The compacted size can be known before writing:** `yjs.CompactAsync([..current, replacement.Update])` returns the merged state. This costs one more sidecar call, needed only when the old rule fails.

## Decisions

1. ~~**Compact inside the page lock.**~~ *Changed by the review: after the lock, see Review fixes 1.* In `WriteReplacementAsync`, after `transaction.CommitAsync` and still inside the `PublishAsync` callback, the page is compacted with `Compactor.CompactAsync` until it returns `NothingToDo`, with at most 5 rounds (for a page with a long log). A `Skipped` (the worker is compacting the page) is tried again every 200 ms for up to 30 s, since one that asks after the worker has committed runs. The compactor's code does not change.
2. ~~**Only for a large page** (question 2):~~ *Changed by the review: only when old plus new is over `Import:MaxNoteUpdateBytes`, see Review fixes 5.* when the page's stored updates plus the replacement are over `Sync:MaxDiffBytes` (2 MiB). That is the size from which the hub sends a page as stored instead of a diff, so below it the window does not matter. The small-page path stays exactly as it is and as it is tested.
3. **The new size rule in `MakeUpdateAsync`.** A replacement is text when all of these hold:
   - the new update alone is at most `Import:MaxNoteUpdateBytes` (it is broadcast as one message to clients that have the page open, as now);
   - ~~the page after compaction is at most `Import:MaxNoteUpdateBytes`, from `yjs.CompactAsync` on the stored updates and the new one~~ *(dropped by the review, Review fixes 6: the compacted page is never larger than old plus new, which the next rule bounds);*
   - stored plus new is at most three quarters of `Sync:MaxQueuedBytes` (12 MiB by default) (question 1). This is the safety net: if the compaction right after cannot run, the page still opens until the worker compacts it.

   Otherwise the note is a file, as now.
4. **When the compaction after the write does not succeed** (`Unavailable`, `Failed`, still `Skipped` after 30 s, or rounds left): the replacement stays written (it is correct), a warning is logged, and the worker compacts the page later as it does any page. The import's report does not change, since the note was imported. Decision 3's safety net keeps the page openable meanwhile.
5. **Lock order:** room lock, then the tree lock inside the write's own transaction (committed), then the advisory lock as a try. The worker takes only the advisory lock, and the purge only the snapshot row. No cycle, so no deadlock.
6. ~~**While the compaction runs, the page's own traffic waits**~~ *Not any more (Review fixes 1).* behind the room lock (a few seconds for a page of several MiB). This only happens to a large page whose note changed in Joplin, during an import.

## Done when

- A note of about 4.5 MB of text (a page of about 5.5 MB, which the old rule turned into a file) that changes in Joplin is replaced as text, not turned into a file. *(The plan said 6 MB; see Handoff: its page is 7.3 MB, too large for the cap of question 1.)*
- Right after the import, that page has a snapshot and no live updates. A client that subscribes straight after gets a reply about the size of the new content, and is not dropped.
- The same export imported again changes nothing, without reading the page's fingerprint.
- If the compaction after the write is skipped, unavailable or fails, the replacement stays, the page still opens (stored plus new within three quarters of the queue), and the worker compacts it later.
- The architecture and the self-hosting guide drop the "over about 4 MiB" sentence.

## Out of scope

- Writing the merged state as the snapshot directly in the replacement's transaction. That would skip the compactor's guarantees (archive, verification, watermark rules), or copy them.
- Compacting the conflict copy or a new page: they have one update, so there is nothing to merge.
- Any change to the compaction worker's thresholds.

## Questions

1. **The safety net if the compaction right after the write cannot run:**
   - Old plus new at most three quarters of `Sync:MaxQueuedBytes` (12 MiB by default): the page still opens, with a quarter of the queue left for other traffic, until the worker compacts it. A 6 MB note that changes is text (6 + 6 MB = 11.4 MiB). *(Wrong: a note of 6 MB of text has an update of 7.3 MB, so old plus new is 13.9 MiB. The cap lets through updates up to 6 MiB, about 5 MB of text.)* **Recommended.**
   - No net: rely on the compaction. If it fails, a page of old plus new may be too large to open until the worker gets to it (its failure backoff starts at an hour).
   - Half the queue: today's rule, so nothing would change.
2. **Which replacements are compacted at once:**
   - Only a large page (stored plus new over `Sync:MaxDiffBytes`, 2 MiB): the change stays confined to what it fixes. **Recommended.**
   - Every replacement: one path, but every changed note of a re-import gets a compaction under the page lock, and the small-page path changes too.

## For the trial

- Change a note of several MB in Joplin, export, and import again. The report says it was updated (no file), and the page opens at once on the phone and on the laptop with the new text.

## Answers

1. **The safety net:** old plus new at most three quarters of `Sync:MaxQueuedBytes`. After the real numbers came in (below) it was asked again, and kept.
2. **Which replacements are compacted at once:** only a large page (stored plus new over `Sync:MaxDiffBytes`). *Changed by the review (`/code-review`, "fix all"): only when old plus new is over `Import:MaxNoteUpdateBytes`, and the worker takes any page with over 2 MiB of live updates.*

**What the real numbers said (found by the Playwright test, not the plan)**
- A note of 6 MB of text (`generateLargeJex`, 30,000 paragraphs) has an update of **7,301,194 bytes**: about a fifth more than the text. Old plus new is 13.9 MiB, over the cap of 12 MiB, so that note still becomes a file when it changes. The plan's "6 + 6 MB = 11.4 MiB" ignored the overhead.
- With the cap as it is, a note stays text when its update is up to 6 MiB (about 5 MB of text), where the old rule stopped at an update of 4 MiB (about 3.5 MB of text). The maintainer chose to keep the cap rather than raise it to 7/8 of the queue (the 6 MB note would fit by 0.1 MiB) or drop it (a failed compaction could leave a page unopenable for an hour or more).
- The issue's "about 6 MB" done-when is therefore met for 4.5 MB of text, not for 6 MB. Raising the cap later is a change of `MaxOldAndNewBytes` plus its tests.

### Review fixes (`/code-review`, 10 findings, all fixed)

1. **No compaction inside the hub's page lock.** It held every client of the page, whose socket then stops answering pings and is dropped after 8 s. The import compacts after the lock. The few seconds until then are what the three-quarters net is for: a client opening the page meanwhile is sent old plus new, which fits.
2. **A cancellation after the write** no longer throws inside the commit callback. The compaction runs after the write's bookkeeping, so a shutdown just stops the import there.
3. **A page whose compaction could not run** is compacted before its next replacement, so a later change is not turned into a file, or skipped, because of the old log.
4. **`Import:CompactionWait` is gone.** The import does not wait for the worker: a page the worker has is the worker's.
5. **Compacted by the import only when needed:** old plus new over `Import:MaxNoteUpdateBytes` (it was: over `Sync:MaxDiffBytes`).
6. **No measuring compaction.** The page after the compaction is bounded by old plus new, which the net already bounds. One full merge of a large page fewer in the sidecar.
7. **The general case:** the worker takes a page with 2 MiB or more of live updates at its next round (`Compaction:LiveBytesThreshold`), so a large page that clients edit is not sent with its whole log for minutes either. The import's own compaction stays, to make the window seconds instead of up to 30 s.
8. **The tests use `Compactor.LockClass`** (internal now) instead of a copy of it.
9. **One place for the limits and queries** of the large-page tests: `LargePages`, and the harness's `LiveUpdatesAsync` and `SnapshotOfAsync`.
10. **No unbounded polling:** the wait test and its hooks are gone with the waiting. The test of the worker holding the page waits for the import with a timeout.
