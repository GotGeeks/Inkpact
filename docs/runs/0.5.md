# Run 0.5: compaction stress test

**Model:** O·high → S·high (plan by Opus 5.5; implementation by Sonnet high or Opus)

## Goal

50,000 random edits with repeated compaction. After every compaction, the plain text and the Yjs state must match an uncompacted replay. Storage must not grow without bound after compaction.

## Inputs

- `docs/architecture.md`: "Compaction guarantees" (transactional, watermark, advisory lock per page, idempotent, verified against a full replay, archive instead of delete), "Sync flow" step 5, Phase 0 gate.
- Run 0.2: `page_updates`, `SyncHub`, subscribe-race test.
- Run 0.4: `ICrdtCodec`, `YjsSidecarCodec` (the recommended codec), fixture generator, contract tests.

## Done when

- The stress test passes for several seeds: 50,000 edits, compaction every few hundred updates, running concurrently with appends, with crashes injected at every stage.
- Every guarantee in "Compaction guarantees" has a test.
- Live storage (snapshot plus not-yet-compacted updates) stays within a fixed factor of the document's own size. The archive grows, and is deleted by age later (1.10).

## Plan

### Storage (spike schema, created on startup like 0.2)

```sql
create table if not exists page_snapshots (
  page_id   text primary key,
  state     bytea  not null,   -- Yjs v1 full-state update
  watermark bigint not null,   -- highest page_updates.id folded into state
  version   int    not null,   -- +1 per compaction
  updated_at timestamptz not null default now());

create table if not exists page_updates_archive (   -- 30-day safety net; purge is 1.10
  id bigint primary key, page_id text not null, data bytea not null,
  created_at timestamptz not null, archived_at timestamptz not null default now());
```

### Compaction (`Compactor.CompactAsync(pageId)`), one Postgres transaction

1. `pg_try_advisory_xact_lock(hashtextextended(page_id, 0))`. If another compaction holds it, return `Skipped`: no waiting, the next round picks the page up.
2. Read the snapshot row (`for update`) and all `page_updates` for the page, ordered by id. Updates newer than this read are not seen; that is the watermark.
3. If there are no updates, return `NothingToDo`. This keeps compaction idempotent.
4. `merged = codec.Merge([snapshot.state, ...updates])`.
5. **Verify** with an independent replay. Load the old snapshot in a fresh doc, apply the updates **one per transaction**, and compare it with `merged`. Also compare with an append-only replay of archive plus live updates, without any snapshot, while the archive is complete (always in the spike). A mismatch aborts the transaction and logs an error; nothing changes. _(As built: compared as a Yjs snapshot fingerprint, state vector plus delete set, not as text; see "Changes from the plan".)_
6. Upsert the snapshot with `watermark = max(id)` and `version + 1`.
7. `insert into page_updates_archive select … where page_id = $1 and id <= watermark`, then `delete from page_updates where page_id = $1 and id <= watermark`.
8. Commit.
9. Fault hooks between every step (test only) throw, to simulate a crash. The transaction rolls back and the state is unchanged.

### Reading a page (`IUpdateStore.LoadPageAsync`)

- Snapshot plus updates `id > watermark`, read in **one `REPEATABLE READ` transaction**. Without that, a subscribe that reads the snapshot before a compaction commits, and the updates after it, misses the archived updates. That is a real data-loss race, and it gets its own test.
- `SYNC` then carries `[snapshot, ...updates]`. The client side is unchanged: it merges whatever it gets.

### Trigger

`CompactionWorker` (a `BackgroundService`) polls every few seconds for pages with at least N live updates (default 500) and compacts them. Idle-time compaction is 1.10. The sidecar is started once by the server: `YjsSidecarCodec` as a singleton, path from config.

### The stress test (`CompactionStressTests`, Testcontainers Postgres + sidecar)

1. **Edits come from Yjs.**
   - `spike/client/scripts/compaction-stream.ts` generates N edits by 3 concurrent clients on a TipTap document. It reuses the 0.4 generator: mixed inserts, deletes, formatting, paragraphs, emoji.
   - The output is a length-prefixed binary stream in arrival order, written to a temp file at test start. It is deterministic per seed and not committed.
2. **A writer appends the stream** through `IUpdateStore.AppendAsync`, the same path the hub uses.
3. **A compactor loop runs at the same time**, every ~300 updates on average. 1 in 5 runs injects a crash at a random stage; 1 in 10 runs two compactions in parallel.
4. **After every compaction**, and on the final state:
   - `LoadPageAsync` → `Merge` → text and state vector must equal the oracle: the sidecar merging every update appended so far, never compacted.
   - Live rows equal the appended count minus the watermark count; archive plus live rows equal the appended count (nothing lost, nothing duplicated).
5. **Storage:** record snapshot bytes plus live update bytes per checkpoint. After a compaction, live storage must be at most 2× a fresh `encodeStateAsUpdate` of the oracle doc, plus the updates since the watermark. The run card gets the numbers.
6. Seeds: 3 seeds with 50,000 edits (the gate), plus a fast 5,000-edit seed for everyday runs.

### Guarantee tests (`CompactorTests`)

- **Transactional:** a fault at each stage leaves the snapshot, live updates and archive byte-identical to before.
- **Watermark:** updates appended while a compaction is between steps 2 and 8 stay live and are folded in by the next run. This uses a fault hook that blocks instead of throwing.
- **Advisory lock:** two concurrent compactions of one page give exactly one `Compacted` and one `Skipped`, with no double archive.
- **Idempotent:** compacting twice equals compacting once, and the second run is `NothingToDo`.
- **Verification:** a codec wrapper that corrupts the merge makes compaction abort with an error log, with no state change.
- **Subscribe race:** a client subscribing while compaction runs gets every update, in the snapshot or the update list, never neither. This is the 0.2 race test with a compactor in parallel.

## Changes from the plan

1. **Verification compares CRDT documents, not text.** Running the real worker on a page that wasn't a TipTap document made the sidecar's ProseMirror text extraction throw, so compaction (safely) failed on every tick. A page doesn't have to be a TipTap document, and text equality can't see a lost deletion anyway. `ICrdtCodec.Fingerprint` is now a Yjs snapshot (state vector plus delete set, written in sorted order), equal exactly when two states are the same document. Text extraction stays for search and returns an empty string for an empty fragment.
2. **The sidecar's `merge` applies updates one at a time (a Yjs finding, below).**
3. **Same numbers of tests as planned, plus** a non-TipTap page test, a hub test (a subscriber after compaction gets the snapshot, then the newer updates), and fingerprint cases in the codec contract.
4. **The 0.4 fixtures are regenerated.** The base document got a random Yjs client id on every run, so `crdt:fixtures` never reproduced itself. It now uses a fixed id, so fixtures and the stress streams are byte-identical per seed. All 81 codec tests, including the pinned `Known_divergence_*` cases for yrs, pass on the new fixtures. Log and snapshot sizes in `docs/runs/0.4.md` differ by under 1% (for example the 10k-update snapshot is now 103,827 bytes, not 104,751); the conclusions are unchanged.

## A Yjs finding: one transaction can lose a deletion

The stress test (seed 43) failed once with the new fingerprint check: the merge of `[previous snapshot, ...updates]` differed from a replay of the same inputs. Pure Yjs, no .NET or yrs involved:

- Applying a snapshot and the updates after it in **one `Y.transact`** can end without a deletion that every browser has. In the case found, exactly 1 item out of 996 deleted items was live in the merge. The text is identical, so only a comparison of delete sets sees it.
- Applying the same inputs **one update at a time**, as a browser does, matched a snapshot-free replay of the raw stream in all of **1,012** chained compactions over 30 random compaction schedules (`pnpm compaction:chain-check`). The one-transaction chain differed in 1 of them.
- It is rare (about 1 in 1,000 compactions), depends on where the snapshot cuts the stream, and the old text-and-state-vector check passed it. A persisted snapshot built that way would differ from every browser's document.
- Minimal reproduction (`pnpm compaction:repro`): a 14 KB snapshot plus 52 updates, in `Spike.Server.Tests/Fixtures/yjs-one-transaction-repro.json`. A test pins both halves: the sidecar's `Merge` equals a one-at-a-time replay, and `MergeInOneTransaction` differs.
- Not diagnosed to a root cause and not reported upstream.

This also changes a 0.4 detail: for yrs, one write transaction was the stable choice; for Yjs, one at a time is the correct one. Another reason the sidecar (Yjs itself) is the right place to merge.

## Results

Gate: 3 seeds of about 50,000 updates (50,110, 50,115 and 50,116 updates from 50,500 edits by 3 concurrent clients on a TipTap document), appended while a compactor runs. Run with `INKPACT_STRESS=1 dotnet test spike/server --filter CompactionStressTests` (about 40 s per seed; skipped by default). After the fix: 15 runs of about 50,000 updates in 5 rounds, all green.

| Per seed | Value |
| --- | --- |
| Compactions | 55–62, one every 100–500 appended updates |
| Crashes injected at a random stage | 20–26, each leaving snapshot, watermark and archive unchanged |
| Two compactions of one page at once | 7–8, and in every one exactly one was skipped |
| Checks against the uncompacted Yjs oracle | about every 3rd compaction: the whole page, and the snapshot alone |
| Final snapshot | 372–441 KB, **exactly the size of a fresh encode** of the same document |
| Log | 1.22 MB of updates |
| Peak live updates between compactions | 60–90 KB |
| Archive | every folded update, exactly once |

- **Storage:** live storage is the snapshot (equal to a fresh encode, so it grows with the document and not with the edit history) plus the updates since the last compaction (bounded by the compaction cadence). The archive grows with the history until the 30-day purge, which is run 1.10.
- **Race checked by breaking it:** with the page load changed from repeatable-read to read-committed, the subscriber-race test fails 5 times out of 5. So the data-loss race is real, and the test catches it.
- **The real worker:** with the server run as a developer would (`dotnet run`), 700 edits from a real client were folded into a 715-byte snapshot by the timer; a fresh client then read all 700 characters back, and the page that had failed earlier was compacted on its own.

## Handoff

- **Done:**
  - Schema (`page_snapshots`, `page_updates_archive`), `Compactor` (transaction, advisory lock, watermark, verification by fingerprint, archive), `CompactionWorker`, consistent `LoadPageAsync` used by the hub.
  - 15 guarantee tests plus the hub test and 4 stress tests (one per seed, plus a 5,000-update run for everyday use) on top of the 0.2 tests, 39 server and 81 codec tests in all.
  - Deterministic fixtures and streams; chain-check and reproduction scripts.
- **Left for 1.10:**
  - Sample the full-history verification: it reads and replays the whole page history on every compaction, which is fine at 50,000 updates but grows without bound.
  - The idle-time trigger (the worker polls a threshold), the 30-day archive purge, FsCheck property tests (a new dependency, so not added).
  - Supervision of the sidecar (restart on crash) and binary framing instead of base64 JSON.
  - A multi-page design for the worker (it compacts pages one after another).
- **For 1.09 and 0.7:**
  - The server could now answer sync step 1 with a diff, using the sidecar (8 ms for 10,000 updates). Whether to keep the 0.2 client-computed diff is a 0.7 decision.
  - The architecture should say that compaction merges one update at a time, never in one transaction.
- **Surprising:**
  - The old check passed a compaction that was subtly wrong; only the stronger one caught it. Trusting text equality for "same document" is a trap.
  - The first sign of the Yjs problem was a verification exception inside a step of the stress test that expected a simulated crash. The check had fired for real, at the first compaction that started from a snapshot.
  - Two of my own checks were wrong before they were right: the "final compaction must find work" assertion was a race (the last periodic compaction can already have folded in the final update), and the first verification compared text, which hid the lost deletion.
