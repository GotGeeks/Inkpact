**Model:** S·high in the roadmap. Planned on Opus 5.5 high; 1.17a built on Sonnet 5.5 high, 1.17b builds on Sonnet 5.5 medium (questions answered, ready to build). `/code-review` at high on Opus before each PR merges: search crosses the permission line (a page you may not read must never show up, not even as a title or a snippet).

## Goal

Typing a few letters finds a page by its title, its tags or its text, in the workspace you are in, while you type. Accents and case don't matter, so `cafe` finds `Café` and `CAFÉ`, and a word you only half typed (`vergad`) already finds `vergadering`. The first results come back within 200 ms on 10,000 pages. A page in the trash, or under one, is never found.

## What the code is now (found while planning)

1. **The text is there, the index is not.** `pages.content_text` exists since 1.10b. The compactor writes it, and so does the import (new pages and replacements). There is no `tsvector`, no index and no endpoint.
2. **The text of a page lags behind typing.** Only compaction refreshes `content_text`, and a page is compacted after 500 updates or 10 minutes without a new one (`Compaction:IdleAfter`). A word typed now is found 10 to 11 minutes after you stop typing. A title is found at once, since it is a column of its own.
3. **A `tsvector` can hold at most 1 MB.** `to_tsvector` fails with "string is too long for tsvector" above that. A note can have 8,000,000 bytes of text (`Import:MaxNoteTextBytes`). An index built from the whole text would make the compactor and the import fail on large pages, and the migration fail on a database that has one.
4. **Tags are in their own tables** (`tags`, `page_tags`), written only by the import: a new page's tags, the re-import's set operations, and a tag renamed in Joplin. A generated column cannot read another table.
5. **`unaccent` is an extension.** It ships with PostgreSQL (the official images and `postgres:18-alpine` have it) and has been a trusted extension since PostgreSQL 13, so the owner of the database can create it. `deploy/inkpact.sh init` and the self-hosting guide make the `inkpact` role the owner.
6. **Nothing in Inkpact uses Ctrl+K yet,** and the editor has no binding on it.

## Decisions

1. **Two runs.**
   - **1.17a, server:** the migration, the query, the endpoint, tags in the index, the timing test. Testable with HTTP alone.
   - **1.17b, web:** the search dialog, search-as-you-type, the entry points, both languages, Playwright.
2. **A text search configuration of our own, `inkpact_search`:** a copy of `simple` with `unaccent` in front of it, for every word token type. `simple` does not stem, so English and Dutch behave the same, and prefix matching covers what stemming would (`note:*` finds `notes`). The migration runs `CREATE EXTENSION IF NOT EXISTS unaccent` and creates the configuration.
   - Weighed: `english` or `dutch` configurations. A note is often in both languages, and a stemmer for one mangles the other.
   - Weighed: an immutable wrapper function around `unaccent()`. The configuration does the same thing, and `to_tsvector(regconfig, text)` is already immutable, which a generated column needs.
3. **Two new columns on `pages`** (migration `AddSearch`):
   - `tag_text` (text, not null, default `''`): the page's tag names, one space between them, in name order;
   - `search_vector` (`tsvector`), **generated and stored**: `setweight(to_tsvector('inkpact_search', title), 'A') || setweight(to_tsvector('inkpact_search', tag_text), 'B') || setweight(to_tsvector('inkpact_search', left(content_text, 200000)), 'C')`. EF maps it with `HasComputedColumnSql(..., stored: true)`.
   - A GIN index on `search_vector`.
   - **Only the first 200,000 characters of a page's text are indexed** (about 30,000 words, 100 printed pages), which keeps the vector well under 1 MB whatever the text is. The rest of a longer page is not found. The constant is in the migration, and the architecture and the self-hosting guide say so.
   - Weighed: the vector written by the application. A generated column is right after every write, in every code path (rename, compaction, import, and B.2's tags later), with no code to forget.
4. **`tag_text` is written in one place:** a small `PageSearchText.RefreshTagsAsync(db, pageIds)` (or the like) that sets it from `page_tags`. The import calls it after a new page's tags, after the re-import's set operations, and for every page of a tag that was renamed. B.2 will call it too.
   - Weighed: a trigger on `page_tags` and `tags`. It cannot be forgotten, but it is logic the C# tests and readers do not see, and the conventions keep SQL to the tree and compaction.
5. **The query** (raw SQL, as the visible tree is a recursive query, like `TreeService`):
   - The client's text is split into words on everything that is not a letter or a digit (Unicode categories, in C#). At most 8 words, each cut at 64 characters; a text with no words gives an empty list. Each word becomes `word:*`, joined with `&`, and goes to `to_tsquery('inkpact_search', @q)` as a parameter. Since a word holds only letters and digits, the user's text can never be tsquery syntax.
   - Only pages of the workspace, not in the trash and with nothing above them in the trash.
   - Ordered by `ts_rank(search_vector, q)` (the default weights put a title above a tag above the text), then the newest `updated_at`, then id. At most 30 results; no paging (the list is for finding, and a longer search narrows it).
   - Highlights from `ts_headline` with the same configuration, **only for the 30 results** (it parses the text again): the title with every match marked, and up to two fragments of the text (`MaxFragments=2`, about 20 words each), over the same first 200,000 characters. The marks are two control characters that the query strips from the text first; the server turns the string into segments, so the client never parses markup and never needs `v-html`.
   - Implementer's choice: the visible tree top-down (as `GetTree`) joined with the matches, or the matches first and their ancestors checked upward. The timing test decides.
6. **The endpoint:** `GET /api/workspaces/{workspaceId}/search?q=...`, `RequireWorkspaceRole(Viewer)`, as the tree. A workspace you have no role in answers 404, as for the tree. The answer:
   ```json
   { "results": [ { "id": "…", "title": [ { "text": "Weekly ", "match": false }, { "text": "meeting", "match": true } ], "snippet": [ … ] } ] }
   ```
   An empty title comes back as an empty list (the client shows "Untitled"). An empty snippet when the match is only in the title or a tag. No new error codes: an empty or wordless `q` answers an empty list.
7. **A word you type is found about two minutes after you stop typing:** `Compaction:IdleAfter` goes from 10 minutes to 2. Compaction keeps its guarantees at any moment (the watermark and the advisory lock are there for an edit that arrives during it), so this changes when it runs, not what it does. Question 2 below.
8. **The search dialog (1.17b)**, a Reka UI dialog over the page, as in the designs (question 1):
   - **Opened** from a "Search" row at the top of the sidebar (showing `Ctrl K`, or `⌘ K` on a Mac), from a search button in the phone's header, and with Ctrl+K or Cmd+K anywhere, also inside the editor. B.4 later adds commands and recent pages to the same dialog.
   - **A combobox:** the field, and the results as a list under it. Arrow keys move through the results, Enter opens one, Escape closes. Full screen on a phone, a centred panel from `md`.
   - **Search as you type:** from 2 characters, 150 ms after the last key. A new request aborts the one before it, and only the answer to the newest text is shown. The old results stay while the new ones load.
   - **A result:** the title with its matches marked (or "Untitled"), the path of the pages above it from the tree store (as the sidebar has it), and the snippet with its matches marked. Marks are `<mark>` elements with theme-token classes.
   - **States, each with its own text:** fewer than 2 characters (a hint), nothing found ("Nothing found for “…”"), no connection or a server error ("Search needs a connection to the server").
   - **Opening a result** goes to the page and closes the dialog, and the drawer on a phone. Opening the dialog again shows the last search, selected, so it can be typed over.

## Handoff

### 1.17a, server (built on Sonnet 5.5)

**Done:** decisions 1 to 7 and every "Done when" item of 1.17a. One migration (`AddSearch`). 1.17b (the dialog) is next.

**What was built:**
- **Migration `AddSearch`:** `tag_text`; `CREATE EXTENSION unaccent`; the configuration `inkpact_search` (`simple` with `unaccent` in front, for the nine word token types); `tag_text` filled for pages that have tags; the generated columns `search_vector` (title A, tags B, `left(content_text, 200000)` C) and `title_vector` (title A, tags B), each with a GIN index; a `Down`.
- **`Search/SearchWords`:** a text becomes at most 8 words of at most 64 letters or digits (NFC first, so an accent typed as two characters is one letter), each `word:*`, joined with `&`. Nothing else reaches `to_tsquery`.
- **`Search/SearchService`:** one query, described below; `SearchHeadline` turns the headline strings into `{ text, match }` segments (marks are `\x01` and `\x02`, a fragment ends with `\x03`, all three are taken out of the page's own text first, so none of its own can pass for one).
- **`GET /api/workspaces/{id}/search?q=`** (`SearchEndpoints`, viewer role, 404 for a stranger as for the tree). Answer `{ results: [{ id, title: [{ text, match }], snippet: [...] }] }`; an empty title is an empty list; no snippet when the match is only in the title or a tag.
- **`Search/PageSearchText`:** keeps `tag_text`. The import calls it for a new page that has tags, after the field step changed a page's tags, and for every page of a tag that was renamed. B.2 calls it when the tag interface lands.
- **`Compaction:IdleAfter`** 10 minutes → 2.
- **Docs:** `docs/architecture.md` (the `pages (search)` row, the compaction idle time), `docs/self-hosting.md` (a "Search" section: when a word is findable, the 200,000 characters, the extension), `CLAUDE.md` (the raw-SQL line).

**Where the plan changed, and why:**
1. **A second vector, `title_vector`, and a two-part ranking.** The first version (one query, `ts_rank` over every match) took 441 ms at the 95th percentile on 10,000 pages. Measured with `EXPLAIN ANALYZE`: the matches are found by the index in 6 ms; what costs is reading each page's vector to rank it (about 19 µs a page, 10,000 pages for a two-letter prefix), plus `ts_headline` over the large pages. A weighted `@@` per row was worse (the index cannot check weights). So: pages that match in their title or tags come first, found and ranked on the short `title_vector` (title above tag, then the newest edit); pages that match in their text only are ranked (`ts_rank` on the whole vector) among the 150 edited last. A narrow search (few matches) is therefore ranked exactly; a broad one (two letters) shows the newest matches. Now 33 ms median, **43 ms at the 95th percentile**, 70 ms slowest.
2. **The snippet is made from the first 20,000 characters of the text** (`SearchService.SnippetWindow`), not the 200,000 that are indexed: `ts_headline` costs what it is given, 190 ns a character measured. A match further in is found, listed, and has no snippet. Test: `A_match_beyond_the_start_of_a_long_text_is_found_but_has_no_snippet`.
3. **`search_vector` and `title_vector` are not in the EF model** (decision 3 said they would be). EF asks the database for a generated column after every write of a row (`RETURNING`), which would send up to a megabyte for every rename. `Page.TagText` is mapped; the vectors are in the migration and the query only. `MigrationIntegrationTests` lists the columns.
4. **The query is raw SQL** (as decision 5 said); `CLAUDE.md` says so now, with `PageSearchText`.

**Choices the plan left open:** the visible tree is walked from the top (`live`, as `GetTree`), then joined with the matches: 10,000 pages cost about 10 ms, and it was not the part that was slow. A search with a result in a tag and the same page in the text is one result.

**Timings** (10,000 pages in 100 notebooks, a vocabulary built so that two-letter prefixes match nearly every page, 20 pages of 8,000 words, one to three prefixes, over HTTP): median 33 ms, 95th percentile 43 ms. The 7.5 MB note (`SearchImportTests`): imports as content, compacts and is found by a word at its start, not by one at its end.

**Checked by tests:**
- C# unit: `SearchWordsTests` (accents, apostrophes, query syntax, 8 words, 64 letters, a letter outside the basic plane, a lone surrogate), `SearchHeadlineTests`.
- C# integration (`SearchEndpointTests`, 29 tests, several of them theories): accents and case, half words, all words must match, English and Dutch, tags, a rename, ranking (title, tag, text; ties by edit), at most 30, trash and the pages under it, restore, another workspace, a stranger (404 and the same body as for a workspace that does not exist), a viewer, nobody signed in (401), query syntax never an error, marks in title and snippet, control characters in a page, a title match among 200 text matches, a match past the snippet window, one word in the title and another in the text.
- `SearchImportTests`: a note by its text, by its tags, a tag Joplin renamed, a tag added and one removed, a note changed in Joplin, the 7.5 MB note. `SearchCompactionTests`: not found before a compaction, found after, title and tags kept; `CompactionWorkerTests` pins the new two-minute default. `SearchMigrationTests`: pages already there (one with a million characters of different words) get a vector, `tag_text`, the extension, the configuration and both indexes; `Down`. `SearchTimingTests` (`Category=Slow`).

**Not covered by a test:** a database owned by a role that may not create the extension (the guide says what to do); two searches racing a compaction.

**For 1.17b:** the answer has no path of the page (the client has the tree), no total (30 is the end of the list), and nothing for "created a minute ago": a page found by its title is found at once, its text after about 2 minutes. The marks in `title` and `snippet` are segments; the client renders them as text and `<mark>`, never as markup.

### 1.17a, review fixes (on Opus 5.5)

`/code-review` found eight things. All are dealt with; the migration changed in place, as it is not released yet.

1. **Words joined by punctuation were not found.** Postgres' parser keeps `report.pdf`, `user@example.com`, `3.14` and `2026-11-03` as one token, which a search split into letters and digits (`pdf`, `11`) could never match. The vectors are now made from the text with `. , : ; / \ @ # & % + = ? ~ _ -` turned into spaces, so the index splits as the search does. Tests: ten kinds of joined words, a title with them.
2. **A match beyond the snippet window had no snippet.** `ts_headline` is gone. The snippet is about 400 characters of the text around the first matching word, which a regular expression finds as the index would (every case and accent of each letter, at a word start). The server marks the words in it and in the title itself (`SearchHeadline.Mark`, which also marks `pdf` in `report.pdf`). No control characters are carried in the text any more, so the page's own can never pass for marks. The regular expression reads the text it is given to the end, so it looks at the first 4,000 characters first and at the 200,000 only when the match is not there. A test with the word at character 110,000 and one at the very end.
3. **Only the 150 newest text matches were ranked.** Now 1,000, and the answer has `more` when more pages matched than are listed. Measured: 150 → 96 ms, 500 → 65 ms, 1,000 → 77–101 ms, 2,000 → 103 ms at the 95th percentile (one run each, noisy); 1,000 keeps half of the budget free for a slower server.
4. **`tag_text` was kept by application code.** Now by triggers on `page_tags` (insert, update, delete, also a cascade) and on `tags` (a rename), with one SQL function `refresh_tag_text`. `PageSearchText` and its three calls in the import are gone. `TagTextTriggerTests`: tagging, untagging, a rename on every page that has the tag, deleting a tag, moving a tag row, deleting a page with tags.
5. **The idle time of compaction went from 10 minutes to 2.** That was the maintainer's choice and stays. What changed: the compactor writes `content_text` only when it changed, so a compaction that changes nothing in the text does not build the vectors again (test: the row's `xmin` does not move). `docs/runs/1.10b.md` notes the new default.
6. **The visible-tree walk was copied from `TreeService`.** It is the SQL function `live_pages(workspace)` now (migration), which `GetTreeAsync` and search both read. The tree's tests pass unchanged.
7. **Title matches past 30 could fall into the text part.** They could not reach the list (a full `by_title` fills it), which a test now proves: 35 title matches and 20 newer text matches give the 30 newest title matches and `more`.
8. **The migration rewrote the table twice.** The two vectors are added in one `ALTER TABLE`. `docs/self-hosting.md` says the first start after this update can take a minute or two on a very large library.

**Also found while fixing:** the setup race test (`Two_setups_at_the_same_moment_make_exactly_one_administrator`) and once `A_viewer_can_read_but_not_change_anything` answered a 500 on `/api/auth/state` under the full suite's load and passed every time alone, also in a run with the server's log. Not caused by search, as far as the logs show; left for an issue if it comes back.

**Timings now:** median 59 ms, 95th percentile 77 ms, slowest 101 ms (106 searches, 10,000 pages, the 20 large pages in nearly every result list).

### 1.17b, review fixes (on Opus 5.5)

`/code-review` found nine things. All are fixed.

1. **Enter could open a result of the text before.** During the pause after the last key, and while the next search loads, the list on screen is the old answer. Enter then runs the search at once instead, and opens the first result of the new answer when it is there; typing on in the meantime forgets the Enter. A click still opens the result that was clicked.
2. **Ctrl+K stacked the search over another dialog.** On a narrow screen the drawer closes first (as the Search row in it does); over any other dialog (moving a page, say) the shortcut does nothing.
3. **A failed search left the old list under the error,** where Enter or a click could open it. The list is emptied on an error.
4. **The path of each result was worked out on every render,** with a map of every page per call. It is now one `computed` per list, walking up `tree.byId`.
5. **Hovering a result scrolled the list.** Reka's listbox (finding 9) scrolls on a keyboard move only.
6. **Every failure said the connection was gone.** `network_error` keeps the search's own message; any other code is said as the app says it everywhere (`useErrorMessage`), so a 500 says something went wrong on the server.
7. **The shortcut missed layouts without Latin letters.** `isSearchShortcut` (`search/shortcut.ts`): the letter K on any Latin layout (Dvorak too), and the key in the place of K where the layout has no Latin letters (Cyrillic, Greek).
8. **Pressing the shortcut again searched again.** `show()` does nothing when the dialog is open, and clears a pending search before it searches.
9. **The combobox and list were hand-built.** Now Reka's `ListboxRoot`, `ListboxFilter` and `ListboxItem`: the cursor stays in the field, the arrow keys move and wrap, Home and End go to the ends, and the list is always there (also empty), so the field's `aria-controls` points at it. The highlighted result has `data-highlighted` and the field's `aria-activedescendant`.

**Tests added:** Home and End; `aria-controls` before any result; no scroll on hover; Enter before the answer opens the new first result, and is forgotten when the text changes; a server error in the app's words; the old list gone after an error; the shortcut once however often it is pressed; the drawer closing first; nothing over another dialog; `isSearchShortcut` for Ctrl, Cmd, Alt, Shift, Cyrillic, Greek and Dvorak. The jsdom setup gets a `scrollIntoView` stand-in.

### 1.17c, plan: search inside a note stored as a file (issue #50) (proposed on Opus 5.5 high, to build on Sonnet 5.5 high)

**Goal:** a word from anywhere in the first 200,000 characters of a note that the import keeps as a file (`stored_as_file`, run 1.16d) finds its page, also after the page is compacted and after the note changes in Joplin.

**What the code is now:**
- `BuildAsFileAsync` keeps the body as a `.md` or `.html` attachment (no external id) and makes a page of file nodes. The page's `content_text` holds the file names only, which is all the sidecar's text walk sees.
- The compactor rewrites `content_text` from the document, so anything else put there is lost at the next compaction (the issue's second point).
- `search_vector` is generated from `title`, `tag_text` and `left(content_text, 200000)`; the snippet's regular expression reads `content_text`.

**Decisions:**
1. **A column of its own, `pages.file_text`,** beside `content_text` and `tag_text`: the text of the note a page keeps as a file, at most 200,000 characters, or empty. The compactor never touches it, so it survives compaction.
   - Weighed: the text on the attachment row, kept on the page by a trigger as `tag_text` is. A changed note adds a new body file and leaves the old row (attachments are never deleted yet), so a trigger would keep the old note's words findable too. Only the import knows which body file is the current one.
2. **The text:** Markdown through Markdig's `Markdown.ToPlainText`, HTML through `ContentRules.TextOfMarkup`; NUL removed; cut at 200,000 characters. Markdig is already a dependency.
3. **Written by the import, in the three places that write `content_text`:** a new page, a replacement (`ReplaceContentAsync`) and a conflict copy. `BuiltNote` gets `FileText` (null for content), so a note that changes in Joplin gets its new text, and one that shrinks back under the limits and becomes content again gets an empty `file_text`.
4. **Migration `AddFileText`:** the column (text, not null, default `''`), and `search_vector` made again from `left(content_text || E'\n' || file_text, 200000)` (title A, tags B, that C; `title_vector` unchanged), with its index, in one `ALTER TABLE`. Same 1 MB bound as now: the text part stays at 200,000 characters.
5. **Search** reads the same `content_text || E'\n' || file_text` for the snippet, so a match in the file's text has one. `SearchService` keeps the 200,000 in one constant.
6. **Pages that are already stored as files** (the trial's import) get their text once, at start-up: a small hosted service finds pages with an empty `file_text` that have a Joplin body file (source `joplin`, no external id, `.md` or `.html`) whose name is in the page's `content_text` (so the page still shows it), takes the newest such file, reads it from the attachment store and writes the text. It does nothing once every such page has its text, logs how many it filled, and a page whose file is missing from the store is logged and skipped.
   - Weighed: raising `ConverterVersion`, which converts every untouched note again at the next import: much more work and page history for a handful of pages.

**Out of scope:** text of other attachments (PDFs, uploads); taking the words away when a person deletes the file node from the page by hand (the file stays on the page as an attachment anyway; noted in the guide).

**Done when:**
- A word from the middle of a stored-as-file note finds its page, with a snippet, for a new page, a replacement and a conflict copy.
- It is still found after the page is compacted.
- A note that changes in Joplin is found by its new words and not its old ones; one that shrinks back to content keeps no file text.
- Start-up fills the text of a page stored as a file before this change, once, and skips a page whose file is gone.
- A 200,000-character file text with a long content text migrates, imports and compacts without the vector overflowing.
- The search timing test stays under 200 ms; the 5,000-note import under 5 minutes.

**Tests:** `ImportSizeTests` (small limits, as there) for the three paths and the shrink; a compaction of such a page; the start-up fill (a page made the old way, a missing file, a page whose content no longer names the file, running twice); the migration on a database with such a page; the snippet from file text in `SearchEndpointTests`; `MigrationIntegrationTests` lists the column.

**Docs:** architecture (`pages (search)` row; the 1.16d sentence "The page then has no search text beyond the file names"), self-hosting ("Search": a note kept as a file is found by its text), this card's handoff; close #50 from the PR.

### 1.17c, search inside a note stored as a file (built on Sonnet 5.5)

**Done:** issue #50, as planned, with the corrections below. One migration (`AddFileText`).

**What was built:**
- **`pages.file_text`** (`Page.FileText`), written by the import in the three places that write `content_text`: a new page, a replacement (`ReplaceContentAsync`) and a conflict copy. `BuiltNote.FileText` is the text when the page keeps the note as a file and null when it holds it as content, so a note that shrinks back gets an empty `file_text`. The compactor never touches the column.
- **`NoteFileText.Of(body, isHtml)`:** Markdown through Markdig's `ToPlainText` (pipe tables on), HTML through `ContentRules.TextOfMarkup`; NUL taken out first, `CleanText`, trimmed, at most 200,000 characters (cut again clean of a half pair); the first 1,000,000 characters of the body are read at most; a body Markdig refuses (nested very deep) is used as it stands.
- **Migration `AddFileText`:** the column, and `search_vector` made again from `left(left(content_text, 200000) || E'\n' || file_text, 200000)` (title A, tags B, that C), with its index; `title_vector` is unchanged. A `Down` that puts the old vector back.
- **Search:** matching needs nothing (the vector has it). The snippet of a result whose content has no match comes from a second small query, only for hits with a `file_text` (`SearchService.AddSnippetsFromFilesAsync`): `content_text`, a line break and `file_text`, at most 200,000 characters, the same regular expression as for content.
- **`FileTextBackfill`** (hosted service, also resolvable, `RunAsync`): at start-up, for each page with an empty `file_text`, a blank content (at most 32 characters, and white space only) and a Joplin body file (`.md` or `.html`, no external id), it reads the newest such file from the store and writes the text, only while the column is still empty. It logs how many it filled, and a file missing from the store (logged, skipped) is tried again at the next start. A page with text of its own is left (an old body file stays on the page when a note becomes content again).
- **Docs:** `docs/architecture.md` (the `pages (search)` row and the 1.16d sentence), `docs/self-hosting.md` ("Search").

**Where the plan was wrong:**
1. **A page stored as a file has no text of its own, not its file names:** the sidecar's text walk reads text nodes, and a file node has attributes only. So the backfill cannot tell such a page by its content naming the file; it tells it by a blank content instead (decision 6).
2. **The query is not one query.** A single query that read `file_text` for every result (the text the vector is made from, built per hit) raised the 95th percentile of the 10,000-page timing from about 90 ms to about 130 ms, whatever its shape (measured four ways). The second query for hits that have a `file_text` costs nothing for the rest: 92 and 93 ms, as before.

**Checked by tests:**
- `SearchFileNoteTests` (13, small limits as in `ImportSizeTests`): a word from the middle of a note kept as a file, with a snippet that has the match; plain text and not Markdown; an HTML note, its words and not its tags; found after a compaction; a note changed in Joplin (new words yes, old no); a note that shrinks back to content (empty column); a note that grows into a file; a conflict copy (found, the edited page left alone); the same export again; and the start-up fill: a page from before, once only (a second pass does nothing), the newest of two files, a page that is not a file, a file gone from the store, a page with text of its own.
- `NoteFileTextTests` (7): Markdown, a table, HTML with entities and scripts, control characters and NUL, the cut at 200,000 without splitting a pair, nothing but markup, a list nested 500 deep. `FileTextColumnTests` (3): the vector from both texts; 200,000 characters of distinct words in each do not overflow it (what is past the first 200,000 of the two together is not indexed); a file's words at the end of 30,000 words.
- `SearchMigrationTests`: pages from before are still found after the migration, and a `file_text` is found at once; the undo. `MigrationIntegrationTests` has the column.
- The timings, alone: search 76 to 93 ms at the 95th percentile (three runs); the 5,000-note import 46.5 s, again 0.7 s, 500 changes 8.4 s.

**Not covered by a test:** the hosted service starting by itself with the app (only `RunAsync` is called); a real 8 MB note kept as a file (the 7.5 MB note of `SearchImportTests` is content; the limits are small in the file tests).

**For the trial:** search for a word from your largest note (the one that shows "stored as a file" in the import report), and then check that it is found after a restart of the container, which compacts nothing but runs the start-up fill once: it logs "Search text read from the files of N imported pages".

### 1.17c, review fixes (on Opus 5.5)

`/code-review` found ten things. All are dealt with; the migration changed in place, as it is not released yet.

1. **Embedded data could fill the text.** A note is mostly large because of a picture inside it as a `data:` address, and the 1,000,000-character cut could end inside it, leaving base64 as the text. `data:` addresses are now taken out of the whole body first, then up to 4,000,000 characters are read; the white space markup leaves is made small (spaces to one, blank lines to one), so indentation does not use up the 200,000.
2. **The HTML in a Markdown note lost its words.** Markdown is now rendered to HTML with the converter's own pipeline (`MarkdownConverter.Pipeline`, now shared: task lists, footnotes, maths too), and the HTML is read as a browser shows it (`TextOfHtml`, AngleSharp, a stack of its own): white space in text is one space, a block ends a line, inline markup leaves a word whole (`ex**am**ple` stays `example`), scripts, styles and SVG give nothing. Markup deeper than the converter follows is read without parsing, as the converter does.
3. to 6. **The start-up fill guessed which file a page shows, raced the import, and read every page's text at each start.** It is gone. The migration instead marks the import items of the pages kept as files (blank text, a Joplin `.md` or `.html` file without external id) as converted by an older converter (`converter_version = 1`). The next import converts such a note again when nobody changed its page here (the existing rule of `ImportOptions.ConverterVersion`) and writes the text of the note as Joplin has it then, so it is always the right file, and no query runs at start-up. A page that is no file after all (a note that is only a link to a `.md` file) is converted again unchanged. The cost: the text of an older file note is searchable after the next import from Joplin, not at once; the guide says so.
7. **The second snippet query skipped the main query's rules.** It now only looks where a word is in the text (`search_vector @@ in_text`, not a title or tag match only) and looks at the first 4,000 characters first.
8. **The cut and the 200,000 were done twice.** `ContentRules.Cut` (drops half a pair, puts nothing in its place); `NoteFileText.MaxLength` is gone, it uses `SearchService.IndexedText`, which says where the migrations write the number out.
9. **The NUL replace ran over the whole body,** and the start-up fill read whole files. NUL now goes after the cut; the fill is gone. The `data:` addresses are taken out of the whole body, which the import has in memory anyway.
10. **The docs.** The guide says that each update that changes the search columns rewrites the pages table, and when the text of an older file note becomes searchable; the `InkpactDbContext` comment names both migrations, both vectors and the triggers; the architecture's 1.16d sentence says how older notes get their text.

**Tests changed:** the four start-up-fill tests are four import tests (an older file note gets its text at the next import of the same export; it gets the text of the note as Joplin has it then, after A, B and A; a page someone changed here is left alone; a content note marked by mistake is converted again unchanged); `NoteFileTextTests` gets a 5,000,000-character `data:` picture in Markdown and HTML, HTML in Markdown, task lists, footnotes and maths, white space, a word with markup inside it, and the cut on a pair; `SearchMigrationTests` checks which items the migration marks (a file note yes; a content note, a note with only a resource file, a page of no import no).

**Timings:** the 10,000-page search 88 ms at the 95th percentile.
