# Run B.5: Version history, restore, and retention

**Model:** O·high → S·high in the roadmap. This is a critical sync and data-safety run: have the plan or the finished code reviewed on Opus at high before the PR merges, as the roadmap requires.

**Status:** Not done. The foundation (schema, retention job, policy API and a tested snapshot builder) was merged to main in #122 before the review this card requires; automatic capture, history viewing and restore are **not** available. The retention worker is off by default until versions are captured. Do not rely on history to preserve edits.

## Goal

A person can see and preview earlier versions of a page, restore one without losing their current work, and undo that restore. A workspace owner can control how much history is kept. History stays bounded, and neither its retention job nor a restore can compromise the live document, its collaborators' edits, or compaction.

## Starting point before B.5

1. **The current snapshot is not version history.** A page is its one `page_snapshots` row plus *all* live `page_updates`, read together in a repeatable-read transaction. Compaction replaces that row and archives exactly the updates it read; the separate archive is a 30-day compaction safety net, not a list of restorable versions. There is no `page_versions` table or history setting yet, and old archive rows may already have been purged.
2. **Compaction does not capture every edit as a version.** The worker normally compacts after two minutes without an update, 500 updates, or 2 MiB of live updates, and processes bounded batches. A batch can leave other live updates behind; its snapshot alone is not necessarily the whole current page.
3. **A title is not in Yjs.** It is page metadata with its own version and workspace tree lock. The architecture says both titles in a rename conflict stay visible in history. Tags, position, to-do fields and favorites are separate again.
4. **There is a replacement path, but it has races to address.** The sidecar can read a document as editor JSON and make a replacement update from the current state; the import publishes that update through the hub after checking for intervening stored edits. It must not swap a historical Yjs blob into the live snapshot. The existing offline-copy recovery checks for lost local edits on a **Sync**, not an ordinary live **Update**, and its current check excludes formatting items. The hub's lock and `LastSeq` check alone therefore do not protect a collaborator's update that is still in flight when a restore is broadcast, or prove that formatting-only and deletion-only edits are recoverable.
5. **Old content has more than text.** It can contain links, tables, formatting and attachment ids. Large Joplin notes can be kept as files, with separate `file_text` for search. `ReadAsync` counts schema elements it could not represent; silently restoring such a partial read would lose data.
6. **There is no workspace settings screen.** The user menu has per-device language and theme settings; a history policy must instead be stored on the workspace and available to its owner from both desktop and phone, even when the workspace has no pages.

## Decisions

These are planning defaults for B.5. If proving them safe requires a different design, change the plan before building it; update the frozen architecture only when the implementation proves a decision there wrong.

1. **What a version means.** A version is an immutable, independently readable full Yjs state of one page, its title at that capture, capture time, and the information needed to restore its search state, including the large-file-note case. It keeps attachment references by id, not copies of attachment URLs or file bytes. A creator may be unknown: an automatic capture containing several people's edits is labelled as such, not attributed to the last editor. A saved version does not depend on the 30-day update archive, the current snapshot, or a later replay of live updates.
   - Add `page_versions` and workspace policy fields with an EF migration, appropriate page/time indexes and page-deletion cleanup. Versions belong to their page and workspace; removing a user must not remove a page's history. Keep referenced attachments available for as long as a version can be restored.
   - Capture the title and the complete stored document from one consistent observation: the current snapshot **and all live rows**, including a late-committed row below the watermark. Do not treat a partial compaction batch as a full version. Verify that the independently decoded result has the same content as the captured replay; a state vector alone misses deletions, and a fingerprint alone is not proof of the document's text and formatting.
   - A committed title change is represented even if the body did not change; two competing renames must leave both resulting titles visible while history is enabled. Capture the title as metadata, never as the first heading. Other page metadata is not rolled back by a version.

2. **When versions are made.** Do not snapshot every keystroke. Make a version after a changed page becomes idle, using the existing compaction cadence, and make a continuously edited page eligible for capture once its oldest uncaptured change is five minutes old. Process eligible pages fairly in bounded background batches; the five minutes is an eligibility threshold, not a promise when the server or sidecar is down or a backlog exists. Also record committed title changes and the state immediately before a restore. Avoid duplicate automatic versions when content, title and relevant file-note search state are unchanged.
   - Normal edits and sync must not wait for Yjs decoding on every update. A capture racing an edit, rename or compaction must have a consistent title and body, and a later change must remain eligible for another capture. Keep any information needed to finish a promised title capture durably, rather than losing it to a crash or archive purge.
   - Existing pages get their first version from a successful capture after history is enabled; there is no invented pre-upgrade history or unbounded synchronous migration/backfill. Show an honest empty or pending state. A sidecar failure, invalid document, full history budget or capture backlog must be visible and logged without exposing note content; retry transient failures with bounded work and backoff. Do not display a partial capture as restorable or block ordinary editing indefinitely.

3. **Retention is per workspace.** Enable history by default. An owner can change the following ordered, positive windows; the defaults are the architecture's policy:

   | Age of a captured version | Default retained |
   | --- | --- |
   | Less than 24 hours | Every version |
   | From 24 hours to 30 days | The newest version per page per UTC calendar day |
   | From 30 days to 365 days | The newest version per page per UTC ISO week |
   | 365 days or older | Removed |

   Use one server `TimeProvider`, UTC bucket boundaries and a stable `(created at, id)` tie-break. Validate the windows on the server as well as in the form: the daily boundary cannot precede the granular boundary, and the expiry cannot precede the daily boundary. The implemented API accepts positive windows up to 3,650 days (the granular window is in hours), and the cap is a positive whole MiB whose byte conversion fits a signed 64-bit integer. The 24-hour promise is about **captured versions**, not every Yjs update.
   - The owner can also set an optional workspace-wide cap in whole MiB, or turn new history capture off. The cap counts stored version payload bytes, including any saved file-note search text, not Postgres overhead or attachment files; say that in the UI. With a cap, remove oldest unprotected versions first, even if they are younger than the normal window, and warn before saving a lower cap or shorter windows. Increasing a limit cannot bring deleted versions back.
   - Turning history off stops new ordinary captures, not the live update log or compaction. A capture already in progress rechecks the policy before committing, so it cannot add a version after the setting is off; say what happens to any pending capture. It does not immediately delete existing versions; they remain readable and are thinned under the saved policy, with safety versions still protected. Restore is unavailable while history is off, because it requires a before-restore safety version; an owner can turn history back on.
   - The pre-restore safety version is protected for 24 hours. Reject a cap below the bytes already protected, with an actionable error. If the configured cap cannot accommodate a new safety version after pruning other eligible versions, refuse the restore without changing the page. A capacity problem must not be reported as a successful capture.
   - The retention job runs in bounded, restartable, idempotent transactions. It rechecks the current policy and protected/selected versions when deleting, so a concurrent policy change, capture or restore cannot make it delete the wrong row. It touches neither live updates, the current snapshot nor the compaction archive; the archive's existing independent 30-day safety net stays in place. Log failures and retry rather than silently abandoning a batch.

4. **Restore is a new edit, not a time machine for the tree.**
   - Show the historical title and a safe, read-only rendering of the historical body before confirmation. Confirm that restoring replaces the body **and title**; do not change parent, sibling order, trash state, tags, favorites, to-do fields, reminders or import identity. A page in the trash may be inspected, but must be restored from the trash before a history version can be applied.
   - Read the target through the sidecar and refuse a restore if anything was skipped, the snapshot is corrupt, an attachment required for it is unavailable, or the sidecar cannot answer. Build and verify a replacement update against the *current* page. Never assign the old snapshot to `page_snapshots`, delete live updates, reset a state vector, or replace a connected client's Yjs document.
   - Before changing anything, keep a full version of the exact current title and body. In the same atomic operation, validate the target, page permission, live tree state, history policy/capacity, current content and page metadata version; store that safety version, the replacement update, the restored title through the existing tree rules, and a restore event/version. Update the search and backlink state consistently, including `file_text` for a file note. If any step fails or is cancelled, none of those writes may be committed.
   - Check the existing page, sidecar and sync frame/queue size limits before committing. Support the existing large-page limits where safe; if a restore cannot fit, give a translated error and leave both versions intact, rather than truncate the content or silently turn it into a file.
   - The server must reject a stale preview if content or title changed, rather than overwrite newer stored work. Coordinate with the hub's page lock, the workspace tree lock and compaction in a documented order; neither `LastSeq` nor the watermark alone is a substitute for proving the check covers all writes. A durable operation id makes a retry after a lost response return the original result, even if the target has since been pruned, not restore a second time over subsequent edits. Reject reuse of an id for a different request.
   - Publish the committed replacement to subscribers through the sync path. Protect **both** offline edits and edits still in flight on an online client, including formatting-only and deletion-only changes: extend the existing lost-edit detection/recovery or the sync protocol as needed, and keep affected work in a clearly announced copy when Yjs would delete its old block. Do not assume the current `Update` handler or the existing Sync check already covers every case. A reconnect, an old open tab running the previous client, a crash after commit, and a client which cannot make its copy must all have an explicit, tested outcome. If compatibility with an old tab cannot be made safe, stop and agree on a safe gate before release; do not silently discard its edits. Since B.6, an offline edit can also come back from IndexedDB days after a restore, in a fresh tab that has no memory of the session and may run a newer client: the recovery must cover a document hydrated from local storage, including one whose recovery copy is still pending, and not only a tab that stayed open.
   - Refresh the page/tree state and announce success without disturbing unrelated navigation or a draft title. The restore counts as an Inkpact edit for a later Joplin re-import; it must not rewrite the import's comparison base as if the restored content came from Joplin.

5. **API and permissions.** Add paged, newest-first list and individual preview endpoints under the page, plus a restore endpoint. The list returns metadata, not every snapshot blob; use a stable cursor when timestamps tie. The preview and restore look up the version **within the requested page**, so a guessed id cannot expose another page. Add workspace history-policy read and update endpoints. Use the existing permission service and CSRF conventions: a viewer may read accessible history, an editor or owner may restore a live page, and only the workspace owner may change retention. No access is 404; insufficient role is 403. Recheck permissions and existence at commit, not only at preview; return translated error codes for pruned versions, conflicts, disabled history, insufficient capacity and unavailable/corrupt content.

6. **Interface.** Add a labelled History action on the page and a responsive drawer/dialog using the existing design tokens. List versions with localized times and honest automatic/actor labels; select one to preview it without joining the live Yjs room or mutating the editor. The current editor remains recoverable on close. A viewer can inspect but cannot restore; an editor gets a confirmation and a single-flight Restore action. If the page changed, keep the preview, explain the conflict and offer to refresh. Never render unsanitised HTML, trust historical link addresses, or bypass attachment permissions.
   - Put the workspace history setting in the existing user menu, reachable without a current page; only an owner can save it. Show the schedule, optional cap, disabled/full/pending states, validation and the effect of shortening retention. Use both locales and `Intl` for dates, numbers and sizes. The controls work with keyboard, screen reader and touch, in both themes and at 320 pixels. Keep focus inside dialogs and return it to the opener.

## Done when

- A changed page gets independently readable versions at the stated capture points; a title-only rename and competing renames are represented. Earlier-than-upgrade history is not claimed.
- A version can be previewed and restored, including its title and supported rich content; the before-restore state can itself be restored. A failure, stale preview, duplicate request or pruned target never leaves a partial restore.
- Current edits and collaborators' stored, in-flight and offline edits are preserved or explicitly recovered. All clients converge; no restore breaks the fixed first paragraph, compaction, attachments, search, backlinks or later Joplin re-import.
- The default and configured retention windows, cap, disable/re-enable behavior and protected safety version behave as stated, including concurrent jobs and policy changes. Current content and the independent archive are never pruned by the history job.
- Permission, error, empty, pending and capacity states are usable in English and Dutch on desktop and phone, by keyboard and screen reader, in both themes; CSP remains strict.
