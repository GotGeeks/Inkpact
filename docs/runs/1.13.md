# Run 1.13: Docker image, compose file and the first deployment

**Model:** S·med (planned on Opus 5.5, built on Sonnet). No critical path in application code; the risk is in the packaging (permissions, read-only filesystem, a sidecar that must start) and in a workflow that publishes to GHCR. `/code-review` at medium, with the Dockerfile and the workflow read line by line.

## Goal

Inkpact runs from one `docker compose up`: an image that contains the server, the built web bundle and the Yjs sidecar, runs as a non-root user on a read-only root filesystem, and starts against a Postgres next to it. Every merge to main publishes an `edge` image to GHCR for amd64 and arm64. At the end the maintainer runs it on Unraid behind Traefik on a test subdomain. The e2e suite and the image prove the same thing: that the packaged app is the app the tests ran against.

## Things the code already tells us (they shape the design)

1. **`pg_dump` must be in the image.** Migrations back the database up first (`BackupOnMigrate` defaults to true) and fail loudly when `pg_dump` is missing, so a plain runtime image would refuse to upgrade. The client must be version 18 or newer to dump a Postgres 18 server (Debian's own repository has an older one; the PGDG apt repository has 18).
2. **A read-only root filesystem needs writable mounts for exactly two paths:** `data/keys` (Data Protection keys; losing them logs everyone out) and `data/backups` (the pre-migration dumps). Plus `/tmp` as a tmpfs for Kestrel and .NET. Everything else is read-only. The keys and backups go on one named volume (`/data`), pointed at with `DataProtection__KeysDirectory` and `Database__BackupDirectory`.
3. **The sidecar is started with an empty environment and `--permission`,** so the image cannot rely on `NODE_PATH` or environment variables; `node_modules` must sit where `SidecarPermissions.ReadablePaths` already allows reading.
4. **Node on the PATH or `Sidecar:NodePath`.** The runtime image is the .NET `aspnet` image (Debian) with Node 24 added, or the other way round; see decision 1.
5. **`/api/health` does not check the database or the sidecar.** A container health check against it only proves Kestrel is up. Decision 4 says what to do.
6. **Cookies:** `Auth:CookieSecure=auto` follows the scheme the forwarded headers report, so behind Traefik on HTTPS it is Secure, and on a LAN over HTTP it still works. The trusted-proxy default already covers Docker and Unraid private ranges.

## Decisions to propose

Proposed, not yet agreed. Each says what I recommend and what else was weighed.

1. **Base image: `mcr.microsoft.com/dotnet/aspnet:10.0` (Debian) plus Node 24 copied from the official `node:24-bookworm-slim` image** in a multi-stage build, plus `postgresql-client-18` from PGDG. Final stage runs as the image's non-root `app` user (UID 1654), which the aspnet image already provides.
   - Weighed: the `node:24` image with the .NET runtime added (the .NET runtime has more moving parts than Node's single binary tree); Alpine (rejected in the spike, musl and the sidecar); chiseled/distroless (no shell, no apt, and no `pg_dump`, so it fails the backup requirement).
   - Pin by tag and digest in the Dockerfile; Dependabot's `docker` ecosystem keeps them current.
2. **Four build stages:** `web` (Node, `pnpm install --frozen-lockfile`, `pnpm --filter web build`), `sidecar` (`pnpm deploy --filter sidecar --prod /out`), `server` (`dotnet publish` of `Inkpact.Api`, Release, framework-dependent, no single-file), `final`. Layout in the image: `/app` (the published server, `sidecar/` next to it), `/app/wwwroot` (the bundle), `/data` (volume). `.dockerignore` keeps `node_modules`, `bin`, `obj`, `spike/`, `docs/`, `.git` and test projects out of the build context.
   - `pnpm` comes through Corepack from the `packageManager` field, as in CI. No `onlyBuiltDependencies` change is needed; if the install wants one, stop and ask.
3. **Compose file `deploy/docker-compose.yml`** with `app` and `postgres:18-alpine`, same major as dev and CI. `app`: `read_only: true`, `tmpfs: /tmp`, `cap_drop: [ALL]`, `security_opt: [no-new-privileges:true]`, `depends_on` Postgres healthy, volume `inkpact-data:/data`, port `8080`. Configuration is environment variables (`ConnectionStrings__Inkpact`, `Auth__SetupCode`, `Network__TrustedProxies` optional), read from an `.env` file, with a `deploy/.env.example`. Postgres has its own named volume and a healthcheck; it publishes no port.
   - The optional Redis the architecture mentions is **not** added: nothing uses it before phase 2.
   - The setup code has no default. Without `.env` the compose file refuses to start (`${AUTH_SETUP_CODE:?set AUTH_SETUP_CODE}`), so nobody ends up with a known first-admin code.
4. **A real health check.** The image's `HEALTHCHECK` calls `/api/health`. Ask first whether to extend that endpoint to `SELECT 1` on the database; I recommend **not** in this run (it changes the server, and compose's `depends_on` plus the migration at start-up already makes "up" mean "migrated"). The check uses `dotnet`-free tooling: the aspnet image has no `curl`, so either a tiny `healthcheck` subcommand on the app, or `wget` installed with the PGDG client. Recommend installing `curl` (a few hundred kB) over adding code.
5. **GHCR workflow `.github/workflows/image.yml`:** on push to main (and manual trigger), buildx with QEMU for `linux/amd64,linux/arm64`, tags `edge` and `sha-<short>`, `packages: write` only on that job, `GITHUB_TOKEN` for login, actions pinned by SHA as in `ci.yml`, and the Docker layer cache in GHA cache. Not on pull requests (the free plan, as for the slow suites), but pull requests that touch `Dockerfile`, `deploy/` or the workflow get an **image build without push** so a broken Dockerfile is found before main.
   - **arm64 is built under QEMU,** which makes the first run slow (the `dotnet publish` and the PGDG install are the heavy parts). Weighed: a native arm64 runner (free for public repositories, check the repo is public) against QEMU. Recommend QEMU first and switching if the build passes 20 minutes.
   - Release tags (`x.y.z`, `latest`), cosign, SBOM and provenance are **B.8**, not here.
6. **Trivy scan** of the built image in the same workflow, failing on fixed `HIGH` and `CRITICAL` findings, with a `.trivyignore` that needs a reason per line. Weighed: leaving Trivy to a later run. The architecture lists it under every pull request, and 1.13 is where an image first exists, so it is added here, on main and image-touching PRs only.
7. **Smoke test in CI, on the built image:** start the compose stack from the image just built (amd64 only), wait for healthy, create the administrator through the setup endpoint, open a page, then run the sync scenario against it. The cheapest honest version: run the existing Playwright `desktop` project with `E2E_BASE_URL` pointing at the container instead of the dev server. The architecture says the e2e run goes "against the container from 1.13"; this run does that **on main**, and leaves the local `pnpm check` on the dev server (no Docker build in the inner loop).
   - If making the Playwright config accept an external base URL takes more than a few lines, fall back to a shell smoke test (health, `GET /`, security headers, one WebSocket upgrade refused without a cookie) and record the Playwright version as the follow-up.
8. **Unraid, by hand:** the template XML is B.8, so this run only documents the compose file on Unraid (Compose Manager plugin) and the Traefik labels as an example in `docs/self-hosting.md`: the router, the entrypoint, TLS, and **no** security headers set in Traefik except HSTS (the app sets the rest). The WebSocket needs nothing special in Traefik; the `Origin` check needs the `Host` header passed through unchanged, which Traefik does by default.

## Done when

- `docker build .` produces an image that is non-root, runs with `--read-only`, and starts; `docker compose -f deploy/docker-compose.yml up` brings up the app and Postgres, applies the migrations, and `/api/health` answers.
- The sidecar starts inside the container (a page edited in two browsers compacts and its `content_text` fills), proving Node, the permission model and `node_modules` are in the right place with the read-only filesystem.
- A restart keeps the sessions (Data Protection keys on the volume) and an upgrade to a newer image writes a `pg_dump` into `/data/backups`.
- The workflow publishes `ghcr.io/<owner>/inkpact:edge` for amd64 and arm64 on a merge to main; Trivy is clean or every ignore has a reason.
- **Needs you:** the instance is running on Unraid behind Traefik on the test subdomain, and you have signed in, created a page and edited it from a phone.

## Design

### Dockerfile (repo root, `Dockerfile`) and `.dockerignore`

- Stage `web`: `FROM node:24-bookworm-slim`, `corepack enable`, copy `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml` and the two package manifests first (layer cache), `pnpm install --frozen-lockfile --filter web...`, copy `web/`, `pnpm --filter web build` to `web/dist`.
- Stage `sidecar`: same base, `pnpm install --frozen-lockfile --filter sidecar...`, `pnpm --filter sidecar deploy --prod /out`.
- Stage `server`: `FROM mcr.microsoft.com/dotnet/sdk:10.0` (the SDK matches `global.json`; `rollForward: disable` means the Docker SDK image must be the same patch, or the build fails; pin the tag to it), restore with the central package files first, `dotnet publish server/src/Inkpact.Api -c Release -o /out --no-self-contained`.
- Stage `final`: aspnet 10 Debian; `COPY --from=node` the Node 24 binary and its `lib` (or install from NodeSource; choose the copy, it is verifiable by digest); `apt-get install postgresql-client-18 curl` from PGDG with the signing key checked in the Dockerfile; `COPY` the publish output to `/app`, the sidecar to `/app/sidecar`, the bundle to `/app/wwwroot`; `/data` created and owned by `app`; `USER app`; `ENV ASPNETCORE_URLS=http://+:8080 DOTNET_EnableDiagnostics=0`; `EXPOSE 8080`; `HEALTHCHECK`.
- OCI labels (`org.opencontainers.image.source`, `licenses=AGPL-3.0-only`) so GHCR links the package to the repository.

### Compose (`deploy/docker-compose.yml`, `deploy/.env.example`)

- As decision 3. The image name is a variable with a default (`ghcr.io/gotgeeks/inkpact:edge`), so someone building locally can set `INKPACT_IMAGE`. A `build:` section is **not** in the file, so the file users copy is only about running; a `docker-compose.build.yml` override is allowed if it stays under ten lines.
- Comments say why each hardening line exists, in the style of `docker-compose.dev.yml`.

### Workflow (`.github/workflows/image.yml`)

- Jobs: `build` (all events, push only on main), `scan` (Trivy against the loaded amd64 image), `smoke` (decision 7). Minimal permissions per job. A concurrency group cancels superseded runs on a pull request, never on main.
- The `changes` script (`.github/scripts/changed-areas.sh`) learns an `image` area (`Dockerfile`, `.dockerignore`, `deploy/**`, `server/**`, `web/**`, `pnpm-lock.yaml`, the workflow) so a docs-only pull request still waits for nothing.

### Docs

- `docs/self-hosting.md` (new, short): requirements, the `.env`, `docker compose up`, the first-run setup code, Traefik labels, where the data is and what to back up (`/data` and the Postgres volume), what a migration does to `/data/backups`, how to update (`pull` and `up -d`).
- `README.md` and `CONTRIBUTING.md`: a "Run it" section pointing there.

## Tests

- **Image checks, in the workflow and runnable locally:** `docker run --read-only --user` shows UID not 0; the container starts with only `/data` and `/tmp` writable; `docker exec` `node --version` is 24; `pg_dump --version` reports 18 or newer; `/app/sidecar/node_modules/yjs` exists.
- **Smoke test** (decision 7): health, the shell and its security headers, setup, sign in, a page, two clients converging, and a compaction run (`Compaction` can be given a short interval through an environment variable in the smoke compose file, not in the shipped one).
- **Upgrade check:** start the previous `edge` image's schema, run the new image against it, and expect a file in `/data/backups`. Skipped (and said so) while there is only one migration set; the real migration upgrade test is B.8.
- **No new application code, so no new Vitest or xUnit tests.** If making a path configurable needs code (for example a missing `Database__BackupDirectory` binding), it gets a unit test with it.
- **Existing tests stay:** `pnpm check` is unchanged and must stay green.

**Deviations and findings**
- **Base image is Ubuntu 24.04, not Debian.** `mcr.microsoft.com/dotnet/aspnet:10.0` and `10.0-noble` are the tags that exist for .NET 10 here; no `-trixie` or `-bookworm` tag was found. It is glibc like Debian, PGDG supports it, and the Node binary from the Debian-based `node:24-bookworm-slim` image runs on it.
- The base image already listens on 8080 (`ASPNETCORE_HTTP_PORTS`); setting `ASPNETCORE_URLS` as well only produced a warning, so it is not set.
- `.dockerignore` must keep `web/e2e`: `vue-tsc` in `pnpm build` type-checks `playwright.config.ts`, which imports `e2e/credentials`.
- The health check uses `curl` and `/api/health`, which still does not check the database (decision 4: left as it is).
- Upgrade check (a backup file after an image upgrade) was not run: there is one migration set. The pre-migration `pg_dump` path is covered only by running `pg_dump 18` in the container against Postgres 18. The migration upgrade test is B.8.
- The `.trivyignore` is empty on purpose.
- Docker layer cache for the two platforms is scoped (`amd64`, `arm64`) in the GitHub Actions cache; expect the first arm64 build under QEMU to be slow. Switch to a native arm64 runner if it passes 20 minutes.
