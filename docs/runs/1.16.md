# Run 1.16: Joplin import, part 2

**Model:** O·high → S·high. Opus plans (this card) and reviews; Sonnet high builds (planned on Opus 5.5 high; questions answered, ready to build). Re-importing writes into pages a person may have changed since, so a wrong rule loses their work: this is the "re-import merge" the architecture names as critical. `/code-review` at high on Opus before each PR merges.

## Goal

Importing a Joplin export again brings Inkpact up to date without losing anything on either side, so the two apps can be used side by side during the trial:
- a note changed only in Joplin is updated, also while it is open in an editor;
- a note changed only in Inkpact is left alone;
- a note changed in both keeps Inkpact's version, gets Joplin's as a conflict copy beside it, and the report lists it.

Links between notes (`:/noteId`) become links to the imported pages. A very large note still imports, and opens. 5,000 notes import in under 5 minutes.

## What the code is now (found while planning)

1. **What `import_items` keeps is not enough for a three-way comparison of fields.**
   - It keeps a SHA-256 of the whole item file (title, body and every `key: value` line), and for a note the page's state vector right after the import.
   - The hash only says that *something* changed in Joplin, not what. Joplin rewrites `updated_time` and other bookkeeping lines without a visible change, so a whole-file hash also "changes" more often than the note does.
2. **The server can write a page's updates but cannot tell open editors.**
   - 1.15 wrote straight to `page_updates`, which was fine for pages nobody had open yet.
   - `SyncHub` only relays updates from one client to the others (`Broadcast(message, except)`).
   - An update the server writes into an existing page would reach an open editor only after its next reconnect. Until then, the person keeps typing into a page that is out of date: nothing is lost, since Yjs merges when they resync, but they don't see the change.
3. **The large-note ceiling in the architecture (50 MB) is above what the hub can send.**
   - The hub drops a client whose send queue goes over `Sync:MaxQueuedBytes` (16 MiB). One sync reply larger than that drops the client every time it subscribes, so the page never opens.
   - The sidecar's diff has a 2 s timeout (`Sidecar:DiffTimeout`); above that the hub falls back to sending the stored updates, which are just as large.
   - The sidecar runs with a 512 MB heap. A 50 MB note as ProseMirror JSON is several times that size while it is built.
4. **`:/noteId` links have nowhere to point yet.** `links.ts` allows only absolute `http`, `https` and `mailto` addresses, so a link inside the app has no shape. B.1 (links with backlinks) will build on whatever this run chooses.
5. **A note in Joplin's trash is only counted** (`SkipReason.Trashed`). A note that was imported earlier and then deleted in Joplin therefore stays live in Inkpact with no word in the report.

## Decisions to propose

1. **Three runs:**
   - **1.16a, content:** the comparison of a note's content, updating a page through the hub, conflict copies, re-converting untouched pages after a converter change, and the storage all of 1.16 needs.
   - **1.16b, metadata:** the three-way comparison of titles, places in the tree, to-do fields and tags; notes deleted in Joplin; the report and the page's new strings for both a and b.
   - **1.16c, links and size:** `:/noteId` links, large notes, and the 5,000-note timing.
   - About 14, 12 and 12 files.
   - Weighed: two runs (content with metadata, then links and size), but the first would be about 24 files.
   - 1.16a leaves metadata exactly as 1.15 does (an existing item's title, place, tags and to-do fields are not touched), which is safe on its own.

2. **`import_items` keeps the base: what Joplin had, field by field, when it was last imported** (1.16a migration `AddImportBase`).
   - **Columns:**
     - `base` (`jsonb`): for a note, `title`, `parentId` (Joplin's notebook id), `bodyHash` (SHA-256 of the body only), `isTodo`, `todoDue`, `todoCompleted` and `tagIds` (sorted); for a notebook, `title` and `parentId`; for a tag, `title`.
     - `converter_version` (`int`).
   - The whole-file `content_hash` stays as the fast path: when it is equal, nothing at all changed in Joplin, and the item is passed over without being parsed. That is what keeps a re-import of 5,000 unchanged notes quick.
   - Rows made by 1.15 have no base. Such a row counts as "unknown", never as "unchanged":
     - its content is compared through the whole-file hash;
     - its metadata through 1.16b's rule for an unknown base (decision 9).
   - Weighed: keeping the item file itself. It costs a second copy of every note in the database, for a three-way text merge that is not planned.

3. **"Changed in Inkpact" for content means the page's state vector has gone past the stored one.**
   - The current state vector comes from the sidecar (the snapshot plus the updates after it, which `CompactAsync` already returns).
   - It is compared clock by clock with the stored one, decoded in C#: a state vector is a list of `varuint` pairs, so this needs no Yjs, and it does not depend on the order Yjs writes clients in.
   - It is asked only for notes whose Joplin body changed, so an unchanged export needs no sidecar call.
   - Anything that wrote to the page counts as a change, also an edit that was undone. That errs towards a conflict copy, never towards overwriting.

4. **Changed only in Joplin: the page's content is replaced by a new update, through the hub.**
   - **The update:** a new sidecar operation, `OP_REPLACE` (5). From the page's current state and the new ProseMirror JSON it makes one update that:
     - deletes every top-level element of the `default` fragment;
     - inserts the new content, with the trailing empty paragraph as in `OP_BUILD`;
     - has the same allow-list, refusals and nesting limit as `OP_BUILD`;
     - leaves the fixed first paragraph alone (client 1, already deleted), so a client applying it again still changes nothing.
   - **Writing it:** a new `SyncHub.PublishAsync(pageId, update, userId)` appends the update as a `page_updates` row (the importing person as its user) and sends it to every connection subscribed to the page, the way a client's update is relayed. 1.15's direct insert of a new page's first update stays as it is: nobody has that page open yet.
   - **A person typing at that moment:** their concurrent edit merges with the replacement (Yjs), so it is not lost. It may survive as a fragment inside the new text, which the report cannot see. The window is one note's build time.
   - **After the update:** the item's `base`, `content_hash`, `converter_version` and `state_vector` become those of this import, so the next re-import compares against it.
   - **Files:**
     - a resource the page already has, with the same SHA-256, is reused (the same attachment row);
     - one whose bytes changed gets a new row, and the old row gives up its external id;
     - the old row stays, because the page's earlier states may still show it.
   - **Text and title:** the page's search text (`content_text`) is refreshed in the same transaction. Its title is metadata (1.16b).
   - **Weighed:** a minimal diff that keeps unchanged blocks. It would keep a cursor in place and make history smaller, but it needs a tree diff in the sidecar. A note that changed in Joplin is replaced as a whole; the diff can come later if it ever matters.

5. **Changed in both: Inkpact keeps its version, and Joplin's becomes a conflict copy.**
   - **Where the copy goes:** a new page, the next sibling after the original, built with `OP_BUILD` from Joplin's version, with Joplin's to-do fields and no tags.
   - **Its title:** Joplin's title plus ` (Joplin)`. That is a product name, not a word in a language, so the server's "no user-facing language" rule holds. The original keeps its title.
   - **The copy is not linked to the Joplin id** (no `external_id`, no `import_items` row), so a later import never touches it. The report lists it with the copy's page id and the original's.
   - **The original's item:**
     - `base`, `content_hash` and `converter_version` move to this Joplin version: this version has been seen, so the same export does not make a second copy;
     - `state_vector` stays at the old base, so Inkpact's edits still count as changes. The next time the note changes in Joplin it gets another copy, and is never overwritten.
     - Setting the state vector to the page's current one instead would let the next Joplin change overwrite Inkpact's edits, so it is not done.
   - **Weighed:** a three-way text merge of the two versions. It gives better results when it works and silent damage when it does not; out of scope.

6. **A newer converter re-converts pages nobody has touched.**
   - `ImportOptions.ConverterVersion` is a constant in code: 1 for 1.15, and 2 once 1.16c turns note links into links.
   - When an item's `converter_version` is lower and its page is unchanged in Inkpact, its content is rebuilt from the export (decision 4) even though Joplin did not change. A page that was changed in Inkpact is left alone.
   - This is how notes imported before 1.16c get their links, and how a later conversion fix reaches pages imported before it.

7. **Reporting re-imports** (codes for the client to translate; the strings arrive in 1.16b):
   - **New counts:**
     - `updated`: content or fields taken from Joplin;
     - `reconverted`: decision 6;
     - `keptInInkpact`: changed only in Inkpact, left alone;
     - `conflicts`: copies made.
   - `alreadyImported` keeps meaning "unchanged".
   - **New statuses:** `updated` (listed only when something about it is worth a line) and `conflict_copy` (with `pageId` of the copy and `originalPageId`).
   - **New reasons:** `content_conflict`, and 1.16b's field reasons (decision 9).

8. **Notebooks and tags in 1.16a:** passed over as now (their fields are 1.16b). Notes under a notebook that is new in this export are imported as before.

9. **1.16b, metadata, per field:** for each field the three values are the base (2), Joplin's now and Inkpact's now.
   - **The rule:**
     - changed only in Joplin → taken;
     - changed only in Inkpact, or in both → Inkpact's stays;
     - when both changed and the values differ, the report says so (`field_kept:<field>`).
   - **Title:** Joplin's title, cleaned as on import, against the page's title.
   - **Place:** Joplin's notebook (`parentId`) against the page's parent.
     - It moves only when the page is still under the page of its base notebook.
     - It moves as a tree operation does: through `TreeService`, under the workspace lock, to the end of the new parent, raising the page's version and `tree_version`.
     - A new parent in the trash, or one that would make a cycle: the page stays, and the report says why (`notebook_in_trash`, `notebook_cycle`).
   - **To-do fields:** `isTodo`, `completedAt` and `dueAt`, each on its own (the architecture's "last write wins per field", here "Inkpact wins").
     - A changed due date moves the reminder that has not been delivered yet.
     - A to-do that gains a due date gets a reminder; one that loses it has the reminder removed.
   - **Tags, as a set:**
     - a tag Joplin added since the base is added, unless the page has it;
     - a tag Joplin removed since the base is removed, if the page still has it;
     - tags added in Inkpact are never touched.
     - A tag renamed in Joplin is renamed here only when the Inkpact name still is the base name, and no other tag here has the new name; otherwise the report says so.
   - **Notebooks:** title and place, by the same rule.
   - **An unknown base** (a 1.15 row): a field that differs between Joplin and Inkpact keeps Inkpact's value. The report lists it once per item (`base_unknown`); the next import has a base.

10. **Notes deleted in Joplin (1.16b).**
    - **In the export, with `deleted_time` set:** the page goes to Inkpact's trash, where it can be restored, when it is unchanged in Inkpact (content and fields); otherwise it stays, and the report says so (`deleted_in_joplin_kept`). A notebook goes to the trash only when every page below it would.
    - **Not in the export:** nothing happens. A JEX can be the export of one notebook, so a missing note proves nothing.

11. **1.16c, links between notes: a link mark to the page's address, `/p/<pageId>`.**
    - **`links.ts`** also allows exactly `^/p/<uuid>$`, a path inside the app.
    - **Clicking it in the editor** goes to the page through the router, in the same tab.
    - **The converter** turns `[text](:/<32 hex>)` (and `<a href=":/<id>">` in HTML) into that link when the id is a note or notebook of the export or of an earlier import, and drops `#anchor` with a reason (`note_link_anchor_dropped`). A link to anything else keeps its text with `note_link_missing`.
    - **Page ids are decided before anything is written,** so a link to a note later in the file has its target:
      - an item imported earlier keeps the id it has;
      - a new one gets a name-based UUID (version 8, from SHA-256 of the workspace id, `joplin` and the Joplin id).
      - So a link written now still points to the right page when its target fails in this run and is imported by a later one.
    - **Paste:** `sanitize.ts` keeps such a link like any other allowed link, so it can be pasted between pages.
    - The converter version becomes 2 (decision 6).
    - **Weighed:** a separate `pageLink` mark holding the id. Cleaner, but it needs a schema change on both sides and a way to make one, which is B.1's work. B.1 can find links by their address in the extracted text, and 1.18's export can map `/p/<id>` back to a file path.

12. **1.16c, large notes: the ceiling is set by what the hub can send, not 50 MB.**
    - **Two checks:**
      - A body over `Import:MaxNoteTextBytes` (8 MB by default) is not converted at all.
      - A converted note whose built update is over `Import:MaxNoteUpdateBytes` (8 MiB by default) is not written as content either.
      - Start-up refuses a setting at or above half of `Sync:MaxQueuedBytes`, so the reply plus the traffic around it fit.
    - **Such a note** becomes a page whose content is one file: the body as `<title>.md` (`text/markdown`, served as a download). The report says `stored_as_file`. A body over the attachment limit (50 MB) is skipped (`item_too_large`), as now.
    - **The editor** shows a notice above a page whose Yjs state is over 5 MB after its first sync, saying it may be slow (client strings).
    - **Weighed:** raising the hub's queue limit. One reply of 50 MB would still take the sidecar's diff past its timeout and the browser's editor past usable, and a single slow client could then hold that much memory.
    - **Architecture update:** the "Attachments" bullet gets these numbers, in the same PR.

13. **1.16c, timing:**
    - **A fresh import:** a generated 5,000-note export (the same generator as 1.15b's 1,000-note test, 50 notebooks, notes with formatting, a picture in one in ten) must take under 5 minutes in the test, as the app runs (pooled connections).
    - **A re-import of the same file** must take under 30 seconds (the hash fast path).
    - **A re-import after 500 notes changed:** the time is written in the handoff.
    - These run with the server tests, marked so they can be skipped while working (`Category=Slow`), and always in `pnpm check`.

### 1.16a, content (built on Sonnet 5.5)

**Done:** decisions 2 to 7 for notes, and the 1.16a items in "Done when". Notebooks, tags and every field except a note's content are as in 1.15 (decision 8).

**Two changes to the card, agreed before building:**
- **A page fingerprint beside the state vector.** A Yjs deletion adds to the delete set and creates no item, so it moves no state vector: with the state vector alone, a page where someone only deleted text counts as untouched and Joplin overwrites it. `import_items.page_fingerprint` holds the SHA-256 of the sidecar's replay fingerprint (state vector and delete set); "changed in Inkpact" is a different fingerprint. The state vector (`StateVectors.HasGonePast`, decoded in C#) is only the fallback for 1.15 rows, which have no fingerprint, and for those a pure deletion stays invisible.
- **`SyncHub.PublishAsync(pageId, update, commit)`** takes the caller's commit instead of appending itself. Under the page's lock it runs `commit`, then relays the update to every subscriber; `commit` can decline (returns false) and nothing is relayed. The importer's one transaction therefore holds the `page_updates` row, `content_text`, the attachment rows and the item's new base and fingerprint, and a crash cannot leave a replaced page with an old base (which the next import would take for a change in both).

**What was built:**
- **Sidecar:** `OP_REPLACE` (5), `replaceDocument` in `build.ts` sharing `elementsOf` with `buildDocument`. Parts in: the content JSON, then the page's snapshot and updates; out: the update, and the page after it (state vector, fingerprint, text), checked in the sidecar by replaying the inputs and the update. An empty note leaves one empty paragraph.
- **Server:** `IYjsCodec.ReplaceAsync`; migration `AddImportBase` (`base` jsonb, `converter_version` int default 1, `page_fingerprint` bytea); `ImportBase` (the base's JSON); `ImportOptions.ConverterVersion` (1); report fields `updated`, `reconverted`, `keptInInkpact`, `conflicts`, statuses `updated` and `conflict_copy` (with `originalPageId`), reason `content_conflict`. New items of 1.16a on already write their full base (title, notebook, body hash, to-do fields, sorted tag ids), which 1.16b compares against.
- **`ImportRunner`:** `ReimportNoteAsync` → `ReplaceContentAsync` or `MakeConflictCopyAsync`; the building of a note's files and content is one function (`BuildNoteAsync`) for a new page, a replacement and a copy. The item rows are read once at the start (`run.Existing`) and kept up to date, so a changed note costs no extra query.
- **Client:** the new counts, statuses and reason in English and Dutch, a link to the kept page on a conflict copy's line, and the "importing again" sentence of the start page says what a re-import does now (moved here from 1.16b by the review).

**Choices the card left open:**
- A conflict copy gets **no reminder** for a due date: it is a duplicate, and a second reminder would only be noise.
- A note whose Joplin file changed but whose **body did not** (metadata only) is counted as already imported, and its `content_hash` moves to the new file so the next import takes the fast path again (the review: otherwise the fast path wears away). Its base keeps the old fields. So a field changed in Joplin before 1.16b is not seen by 1.16b's fast path; it is seen once 1.16c raises `ConverterVersion` to 2, which makes every note be parsed again, before the trial.
- An outdated converter version on a page that **was** edited here: left alone, counted as `keptInInkpact` once, and its version is brought up so it is not asked again.
- A 1.15 row (no base): any change of its file counts as a change in Joplin, so a bookkeeping-only change on an untouched page rewrites identical content (harmless), and on an edited page makes a conflict copy (noise, nothing lost).

**The review (`/code-review` high, ten findings, all fixed):**
1. **Text typed into an old block during a replacement was deleted with the block** (pinned in `build.test.ts`). The replacement is now written only when no update was stored since the page was read (`PageContent.LastSeq`, checked inside `PublishAsync`'s commit, under the page lock, where no client update can be stored); otherwise the note is compared again and becomes a conflict copy.
2. **A page trashed during the run was still replaced:** the commit takes the workspace lock and checks the page is live (`TreeService.IsLiveAsync`, the whole chain).
3. **A conflict copy only looked at the original's own `DeletedAt`:** it now uses `IsLiveAsync` too, so no copy goes under a trashed notebook.
4. Client strings (above).
5. Metadata-only changes and the fast path (above).
6. **Three replays per changed note:** now a fingerprint (one replay) and the replacement, which returns the page after it (one replay); the item rows come from the start of the run.
7. **Unchanged files were stored again:** a file whose size and SHA-256 (hashed from the export) match the page's row is reused without writing.
8. The copy's key uses `TreeService.NextKeyAfterAsync`.
9. **Room handling in the hub** is in `EnterRoomAsync`/`ExitRoom`, shared by subscribe, leave and publish; a wait that is cancelled no longer leaves an empty room.
10. `YjsSidecar.Parts` takes an optional leading part.

**The second review (`/code-review` high, ten findings, all fixed):**
1. **An edit the compactor folded away between the read and the commit was not seen:** `PageContent.LastSeq` now includes the snapshot's watermark, and the commit also refuses when a snapshot's watermark is past it.
2. **`sync.destroy()` kept the lost edits:** after a session ended they could be written into the next person's workspace. They are cleared.
3. **Formatting items counted as lost edits:** Yjs deletes redundant formatting itself. Only content items count now.
4. **`tree.create` returned null when the reload after a successful POST failed,** so the copy would be made twice. `change()` now returns what the server made, whatever the reload does.

**The third review (`/code-review` high, eight findings, all fixed):**

### 1.16b, plan (proposed on Opus 5.5 high, to build on Sonnet 5.5 high)

**What the card did not see (found while planning):**
1. **Tags are not in the note's file.** A JEX keeps a note's tags as separate `note_tag` items, so adding a tag in Joplin leaves the note's `content_hash` as it was, and the fast path never looks at it. `ContentHashOf` adds the note's sorted tag ids, as it adds the versions of its files. A note with no tags and no files still hashes as its file alone, so 1.15 rows keep working. Every tagged note is parsed once on the first 1.16b import, then takes the fast path again.
2. **The base moves to Joplin's value once that value has been seen, also when Inkpact's value is kept.** That is what the content already does (a conflict copy moves `ContentKey`) and what decision 9 says for an unknown base. "Changed in Inkpact" then means "Inkpact's value differs from the base". So a kept field is reported once, not on every import, and a person who later sets Inkpact's value to Joplin's gets Joplin's next change. The doc comment on `ImportBase` ("a field moves only when its value has been taken over") changes to match. One exception: **a move that is refused** (target notebook in the trash, missing or failed, or a cycle) moves neither the base's `parentId` nor `content_hash`, so the next import tries again.
3. **The order inside one note decides what a crash leaves behind.** `content_hash` is the fast path, so it must move only in the note's last write: if it moved first, a crash before the fields are written would skip them for good. Fields go first, in their own transaction, and do not move `content_hash` unless the content is unchanged. The content step (1.16a) follows and moves the hash as it does now. The content step must take the base that the field step **returns**, not `row.Base` read at the start: `baseInfo with { ContentKey }` would otherwise write the old fields back.
4. **Two Joplin tags can be one tag here** (the same name in another case). The tag rule works on Inkpact tag ids: `added = map(now) − map(base)`, `removed = map(base) − map(now)`, so removing one of two variants removes nothing.
5. **The 1.15 rows that the fourth review gives a base** (the note's file unchanged) get their title, notebook and to-do fields exactly, but their tags from today's export, and tags are not in the file. In that branch `TagIds` counts as unknown, which follows the unknown-base rule.

**The field rule: `Import/ThreeWay.cs` (new, pure, unit-tested).**
- `Decide(base, joplin, here, baseKnown)` returns `Take`, `Keep` (report) or `Same` (no write, no report). `Same` covers: Joplin unchanged, or both changed to the same value.
- With an unknown base, a value that differs between Joplin and Inkpact is `Keep` with `base_unknown`, once per item.
- Values compared:
  - title: Joplin's title, cleaned as on import;
  - place: Joplin's notebook id, against the page's parent. Inkpact's base place is `PageOf[base.parentId]`, or the top level when that notebook was not imported;
  - to-do fields: `isTodo`, `completed` and `due`, in milliseconds as the base keeps them. A page that ends up not being a to-do gets `null` completed and due.
- **Tags as a set**, in Inkpact ids (point 4). They cannot conflict, so they give no report line.

**Notes: `ReimportNoteAsync`.**
- After the parse, `ApplyFieldsAsync` runs in one transaction:
  1. `LockAsync` (the workspace lock), then read the page, its tags and its undelivered reminders again under that lock;
  2. decide each field, and write what is taken;
  3. raise `Version` and `UpdatedAt` when the title or place changed;
  4. write the new base (point 2), and `content_hash` only when the content is unchanged (the 1.16a metadata-only branch, now the place where fields are taken).
- **A move:** to the end of the new parent (`NextKeyAsync`), checked by a new `TreeService.CheckMoveAsync(pageId, workspaceId, parentId)` that runs on the caller's transaction (same scope, same `DbContext`):
  - the parent is in this workspace and live;
  - the move makes no cycle.
  - `MoveAsync` uses it too, so there is one copy of these rules; that is the only change to `TreeService`.
- **Refusals:** `move_target_in_trash`, `move_cycle` and `move_target_missing`. These are new codes, because the strings of `notebook_in_trash` and `notebook_cycle` describe the first import.
- **Reminders:**
  - a due date taken from Joplin moves the importing person's undelivered reminder whose `RemindAt` is the old due date;
  - a to-do that gains a due date gets one;
  - a lost due date, or a page that is no longer a to-do, removes it;
  - reminders anyone set by hand (later phases) are left alone.
- **1.15 rows** (no base) go through the same function with `baseKnown: false`.

**Notebooks: `ImportNotebookAsync`.**
- When the notebook's file hash changed: title and place by the same rule and the same transaction shape.
- The target is the plan's resolved parent (`step.ParentId`). What counts as changed in Joplin is the base's raw `parentId`.
- A cycle made by two moves, one in each app, is refused by `CheckMoveAsync` and reported.

**Tags: `ImportTagAsync`.**
- When the tag's file hash changed, its name follows the rule.
- A rename is taken only when all three hold:
  - Inkpact's name still is the base name;
  - the tag was made for this Joplin tag (`tags.external_id`): a tag matched by name to one made by hand is not renamed from Joplin;
  - no other tag has the new name.
- Otherwise the report says `tag_name_kept`.

**Deleted in Joplin (decision 10): a pass after the steps, `TrashDeletedAsync`.**
- **Candidates:** trashed notes and notebooks in `Plan.Skipped` whose item has a live page. They are no longer counted as `trashed`; every other trashed note still is.
- **A note goes when** both hold:
  - its fields equal the base (with an unknown base it stays);
  - its content is untouched: `page_seq` is the last update in the page's log, otherwise its fingerprint is checked.
- **A notebook goes when** its own fields equal the base and every live page below it goes. A page made here, or a note Joplin did not delete, keeps it.
- **Only the highest page that goes is trashed,** so restoring the notebook restores everything under it. This runs in a transaction under the workspace lock that reads the page's `Version` again: a page that changed since the decision stays.
- **Counts:** a new count `movedToTrash`. A page that stays counts as `keptInInkpact` and gets a line with `deleted_in_joplin_kept`.

**Report.**

  - anything taken from Joplin (content, a field, a tag or a move): `updated`;
  - otherwise, when Joplin changed something and Inkpact's value was kept: `keptInInkpact`;

3. **Page ids today:** a notebook gets the entity's default id, a note `Guid.CreateVersion7()`. Both become the name-based id for a new item. Conflict copies keep a random id: no Joplin id is theirs.
4. **`ConverterVersion` 2 makes the first 1.16c import convert every note again.** Every page nobody touched gets its content replaced through the hub (counted `reconverted`). Every page touched here keeps its content without a line, counted `keptInInkpact`, and keeps its links as text. That import is slower than the next ones, and it also picks up fields changed in Joplin between a 1.16a and a 1.16b import (1.16b's handoff).
5. **`note_link_pending` stays in the client.** Reports already stored contain it. The server stops writing it.
6. **The importer reads items up to 64 MB** (`JexArchive.MaxItemSize`), and an attachment may be 50 MB. A body between the two cannot be stored as a file, so it is skipped with `item_too_large`, as now (1.16d).
7. **Copied links become absolute.** Browsers put full addresses on the clipboard, so a page link copied from one page and pasted into another arrives as `https://<host>/p/<id>`. The click rule treats a link to this origin's `/p/<uuid>` as a page link.
8. **Known limit, not fixed here:** a client's copy of offline edits (sync flow, step 7) sends the whole page in one request, limited to `Sync:MaxMessageBytes` (2 MiB). A page larger than that cannot get its copy, which then waits until the session ends. Large pages only come from imports, so this is rare. I propose a follow-up issue rather than widening 1.16d.

### 1.16c, review fixes (on Opus 5.5)

`/code-review` found ten things. Nine are fixed; the tenth is a cost of decision 11, written down instead.

1. **A link on a read-only page opened twice** (the router, then the browser following `target="_blank"`). The handler now takes the DOM `click` event, so `preventDefault` stops the browser.
2. **A page could take the id an import works out in advance** (through the create-page `id`) and block that note for good. `POST /api/workspaces/{id}/pages` refuses a version 8 id (`id_invalid`). If one is taken anyway, the import gives the page a random id instead of failing (`NewPageIdAsync`).

5. **A file that could not be stored** gives `resource_missing`, not `note_link_missing`.
6. **Editing links:** a plain click or tap no longer leaves the page. It places the cursor, and a small menu under the link (`LinkMenu.vue`, "Open page" or "Open link") opens it. Ctrl or Cmd with the click opens it at once in a new tab, and on a read-only page a click opens it. This changes the answer to question 2 in one respect: opening a link while editing is two steps, so that its text can still be edited on a phone.

### 1.16d, plan (proposed on Opus 5.5 high, to build on Sonnet 5.5 high)

**What the code says (found while planning):**
1. **The start-up check as written would refuse the defaults.** 8 MiB is exactly half of `Sync:MaxQueuedBytes` (16 MiB). So the rule is "**above** half is refused", and 8 MiB is allowed. The options are plain singletons bound in `AddImport` and `AddSync`; there is no `IValidateOptions` anywhere. The check is a throw in `AddImport` that reads both sections, with a message naming both settings. A test starts the factory with a setting above half (`InkpactFactory` takes `settings`).
2. **`BuildNoteAsync` is the single place.** New pages, replacements (1.16a) and conflict copies all go through it, so both checks live there:
   - **The text check comes before anything is stored:** a body over `MaxNoteTextBytes` (UTF-8 bytes) is neither converted nor sent to the sidecar.
   - **The update check comes after `BuildAsync` or `ReplaceAsync`:** over `MaxNoteUpdateBytes`, the note is built again as a file. The files stored for the first build are kept as rows (see point 3), so nothing is stored twice.
3. **"Lose nothing" means the note's files too.** A note stored as a file still uses its pictures and attachments, and its Markdown points at them by `:/id`, which nothing here can resolve. So the page made for it holds:
   - the body as a file (`<title>.md`, or `<title>.html` for an HTML note);
   - then, one block each, every file of the export it uses, as image or file nodes, made by `ConversionContext.ResourceNode`.
   - That document is small whatever the note was. The report says `stored_as_file` (detail: the body's size).
4. **The body file goes through `AttachmentService.StoreAsync`,** as resources do. Its type follows its name (`DetectType`): `text/markdown` or `text/html` if ASP.NET's extension table has them, else `application/octet-stream`. It is never inline, so it is served as a download. The row gets the Joplin source type and **no external id**: a resource's re-import rule matches files by external id, and the body is no resource. A later import that replaces the page makes a new row, and the old one stays, as for any file.
5. **A body over the attachment limit (50 MB) cannot be stored,** so the note is skipped as `item_too_large`, before the sidecar is asked anything. Today such a note (up to the 64 MB the importer reads) goes to the sidecar and fails there.
6. **The client already stops sending a change over 2 MiB** (`tooLarge`, run 1.13), so editing a large page works as long as each change is small. Pasting a large block into it was already refused. Nothing changes there.
7. **The notice's measure** is `Y.encodeStateAsUpdate(doc).byteLength`, once, when `PageEditor`'s `everSynced` first becomes true: one encode of the document, tens of milliseconds at 6 MB. The size is shown with `formatFileSize`. The notice sits where `newerVersion` is (a `<p role="status">`), stays while the page is open, and is not a toast.
8. **The 1,000-note test** (`ImportRunnerTests.A_thousand_notes_…`) becomes the 5,000-note test in a new `ImportTimingTests`, marked `[Trait("Category", "Slow")]` with its two siblings.
