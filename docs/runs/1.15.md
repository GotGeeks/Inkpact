# Run 1.15: Joplin import, part 1

**Model:** O·high → S·high. Opus plans (this card) and reviews; Sonnet high builds. The import is a critical path: it writes thousands of pages at once, decides what content they start with, and must lose nothing. `/code-review` at high on Opus before each PR merges.

## Goal

A JEX export from Joplin desktop becomes a tree of Inkpact pages: notebooks and notes with the same nesting, their content as real editor content, images inline and other resources as files, tags, to-do state, due dates and timestamps. Every import ends with a report of what was imported and what was not or only partly. Importing the same export again duplicates nothing. Updating already imported notes (the three-way comparison), internal `:/noteId` links and large notes are 1.16.

## The JEX format, as far as it matters here

A JEX file is an uncompressed tar of Joplin's raw items: one `<id>.md` per item, and the resources' bytes under `resources/<id>.<ext>`. An item's file is its title, a blank line, its body, a blank line, and then `key: value` lines, ending in `type_`:

| `type_` | Item | Fields used |
| --- | --- | --- |
| 1 | Note | `id`, `parent_id` (its notebook), body, `markup_language` (1 Markdown, 2 HTML), `is_todo`, `todo_due`, `todo_completed`, `user_created_time`, `user_updated_time`, `encryption_applied`, `is_conflict` |
| 2 | Notebook | `id`, `parent_id` (empty at the top), title |
| 4 | Resource | `id`, `mime`, `filename`, `file_extension`, `size`, title |
| 5 | Tag | `id`, title |
| 6 | Note–tag link | `note_id`, `tag_id` |

Other types (settings, searches, revisions, keys) are counted and skipped. Body and title can contain the metadata separator pattern, so the metadata block is read from the end of the file, not the start. Joplin's alarms are kept on each device, not in the export; a to-do's alarm time is its `todo_due`.

**This is from Joplin's source and documentation, not from a real export yet.** A small real export (a few notebooks, a to-do, a tag, an image, a PDF, an HTML note) is the first fixture; see the questions.

## Decisions to propose

1. **Two runs: 1.15a (conversion) and 1.15b (the import).**
   - **1.15a:** Markdown and HTML to editor content, server-side, and the sidecar operation that turns it into a Yjs update. Pure functions with no database, and the part that decides whether content survives. About 12 files.
   - **1.15b:** reading the JEX, the tables, the import job, the endpoints, the import page and the report. About 15 files.
   - Weighed: one run (about 27 files, over the run size), or splitting by "notes first, resources later" (each half would touch everything).
   - **Split again when 1.15b started** (it came to about 35 files): **1.15b** is the server (reader, migration, job, endpoints, C# tests, docs) and **1.15c** is the page (upload with progress, the report, strings, router and menu, Playwright). 1.15b can be tried with `curl` and is merged first.

2. **The conversion happens on the server, not in the browser.**
   - The JEX is uploaded once, and a background job imports it. A browser tab does not have to stay open for five minutes, the report lives on the server, and 1.16's re-import can compare against what is stored without the client.
   - **The chain:** Markdig parses the Markdown, and AngleSharp parses HTML (whole HTML notes and HTML inside Markdown). Our own C# mapper turns both into ProseMirror JSON, using exactly the editor's node and mark names, and an allow-list does the sanitising (decision 4). The sidecar then builds the Yjs update from that JSON (decision 3).
   - **Weighed: converting in the browser** with TipTap's own schema (`generateJSON` and y-tiptap's `prosemirrorJSONToYXmlFragment`). It matches the editor exactly, but it needs the tab open for the whole import and puts the import's state in the browser. And the "server-side check" would be the client checking itself, which is no check at all.
   - **Weighed: Markdown in the sidecar** (markdown-it). That puts a parser of user content inside the one process we sandbox for Yjs, and HTML there would need a DOM.

3. **A new sidecar operation, `OP_BUILD`: ProseMirror JSON → a Yjs update.** It starts from the page's first paragraph (decision 5), then writes the content the way y-prosemirror stores it:
   - a node becomes an `XmlElement` named after its type, with its attributes;
   - text becomes `XmlText`, with each mark as a format attribute: the mark's name, holding its attributes or `{}`.
   - It refuses node and mark names that are not in the editor's schema, so the server can never write something that makes clients refuse the page (1.11's content check).
   - **Proven by a contract test in `web/`:** for fixture documents covering every node and mark, the sidecar's update is loaded into a real TipTap editor, and `getJSON()` must equal the input. The test imports the sidecar's builder through a workspace dependency (`"sidecar": "workspace:*"` as a dev dependency of `web`; no new package from npm). A second test compares the builder's allow-list with the names in the editor's schema, so a new extension cannot drift away from it.
   - Weighed: building the Yjs XML in C#. There is no Yjs in .NET (YDotNet was rejected in 0.4).

4. **One allow-list for both sides.** `sanitize.ts`'s tags and attributes move to `web/src/editor/allowList.json`. `sanitize.ts` imports it, and a server test reads the same file and compares it with the C# mapper's list. Links follow `links.ts` (`http`, `https`, `mailto`, absolute only); attachments are by id only.
   - Anything else keeps its text and loses its element, and the report says so: an unknown tag, a `style`, a `file://` or `joplin://` link, an external image (it becomes a link to its address, as text with a link), math, `==highlight==`.
   - `<script>`, `<style>`, `<iframe>`, `<object>`, `<embed>` and event handlers go entirely, text included.
   - Joplin note links (`:/<32 hex>`) keep their text for now, and the report counts them as "linked in 1.16".

5. **Every imported page starts from the fixed first-paragraph update.** The sidecar applies the same update (client id 1, an empty paragraph with an empty text in the `default` field), deletes that paragraph, and inserts the content after it. A client that applies the first paragraph again then changes nothing, because the deletion is in the delete set.
   - A contract test checks that the sidecar's first-paragraph bytes equal `firstParagraphUpdate()` from `web/`; it is the same dev dependency as in decision 3.
   - An empty note keeps the first paragraph as it is.

6. **What each Markdown construct becomes** (1.15a's table-driven tests list every row):
   - **Same as in the editor:** headings 1–6, paragraphs, hard breaks, bold, italic, strike, inline code, code blocks with their language, quotes, rules, bullet and numbered lists (with `start`), task lists (`- [ ]` and `- [x]`), tables (cells hold paragraphs, the first row is the header), autolinks.
   - **Resources:** `![alt](:/<resourceId>)` becomes an `image` node when the stored resource is one of the four inline types; any other resource becomes an inline `attachment` node. A `[text](:/<resourceId>)` link to a resource becomes an `attachment` node, and the text is lost if it differs from the file name, which the report notes.
   - An image inside a paragraph splits the paragraph, as the editor does.
   - **Not in the schema:** footnotes, definition lists, math, mermaid (kept as a code block with its language), emoji shortcodes (left as text), `<details>`.
   - **HTML notes** (`markup_language: 2`, mostly from the web clipper) go through the same HTML path as HTML inside Markdown.

7. **Storage written by the import (1.15b, one migration):**
   - `tags` (workspace, name, unique per workspace case-insensitively, external id) and `page_tags` (page, tag), which are stored now and shown in B.2.
   - `reminders` (page, user, remind at, delivered at), filled for to-dos with a due date, for the importing user; delivery is phase 2.
   - `attachments` gains `external_source_type` and `external_id`, as `pages` already has them.
   - `imports` (workspace, user, started, finished, state, counts and report as JSON).
   - `import_items` (import source, external id, kind, Inkpact id, a hash of the Joplin content as imported, the page's Yjs state vector right after the import). This is exactly what 1.16's three-way comparison needs ("changed in Inkpact" means the page has gone past the state vector; "changed in Joplin" means the hash differs). Writing it now means 1.16 needs no data from before it existed.

8. **Where the pages go and in what order.** Top-level notebooks are added at the end of the top level of the workspace, below what is already there. Children keep their nesting. Siblings are sorted by title (`Intl`-like, case and accents ignored), because Joplin's own custom order is per device. Keys come from `FractionalIndex.KeysBetween` in one go per parent, not one tree operation per page.
   - **Timestamps:** `user_created_time` and `user_updated_time` become the page's created and updated times.
   - **To-dos:** `is_todo`, `todo_completed` (as `completed_at`) and `todo_due` (as `due_at`).
   - **Joplin conflict notes** (`is_conflict: 1`) are imported, with "(conflict)" added to the title, and listed in the report.

9. **The import job (1.15b):**
   - `POST /api/workspaces/{workspaceId}/imports/joplin` (editor role, `AcceptsFileUpload`) streams the JEX to `/data/imports/<id>.jex`, under its own limit (`Import:MaxFileSize`, 2 GB by default; the attachment limit is for single files). The answer is 202 with the import's id.
   - A single background worker (a queue in memory) reads the tar with .NET's built-in `System.Formats.Tar`, in two passes: first the index of items, then folders, resources, notes and tags.
   - **One transaction per note** (the page, its first update, its tag links, its import item), so a crash leaves whole notes only. Resources are stored before the notes that use them. The file is deleted when the job ends.
   - **Importing the same export again** skips every item whose external id is already there and reports it as "already imported (updates arrive in 1.16)". Nothing is ever duplicated: the unique indexes on the external ids make a duplicate a database error, too.
   - An import that was running when the app stopped is marked failed at start-up; running it again finishes it, because of the skip rule.
   - **When the sidecar is down,** the job waits for it, up to a limit, and then fails with `sidecar_unavailable`. Pages are never written without content.
   - **Encrypted notes** (`encryption_applied: 1`) are skipped and reported: the architecture asks for an export made decrypted in Joplin desktop.
   - `GET /api/imports/{importId}` (whoever started it) gives the state, the progress and, at the end, the report.

10. **The import page (1.15b):**
    - It opens from "Import from Joplin" in the user menu.
    - **Before the upload:** what to export from Joplin desktop (File → Export all → JEX) and a file picker.
    - **During the upload:** progress through `XMLHttpRequest`, since `fetch` has no upload progress.
    - **While it imports:** progress, polled every second.
    - **At the end:** the report, with counts per type (notebooks, notes, to-dos, tags, images, files) and a list of every item skipped or converted imperfectly. Each row gives the note's title and a link to the page, and the reasons are translated codes.
    - Strings in English and Dutch, keyboard and screen reader labels, a phone layout.

**Findings**
1. **The real export (`D:\Downloads\test export joplin.jex`, 320 notes, 16 notebooks, 42 resources, 2 tags) differs from the card:**
   - A resource's `filename` is empty; the file name is its title. The bytes are `resources/<id>.<file_extension>`.
   - `todo_due` and `todo_completed` are milliseconds since the epoch, as numbers (`1793358000000`); `user_created_time` is ISO text. 0 means none.
   - Notebooks carry an `icon` (JSON with an emoji). Notes have `deleted_time` (0 here; a trashed note has a time and should not be imported as live), `order`, `source_url`, `markup_language`, `is_conflict`, `conflict_original_id`, `application_data`, `extracted_resource_ids`.
   - 311 of the 320 notes are to-dos (259 completed), one with a due date. 20 of the 42 resources are SVG: SVG is not an inline type (it can carry script), so each becomes a file in the text rather than a picture.
   - **Converted as a throwaway check (not committed): all 320 notes convert and build through the sidecar with no failures, 372 ms in all, slowest note 145 ms.** The report would list 120 removed inline `svg` elements, 8 relative links, and one lost link text, all from the web-clipper note.
   - That export is the user's real notes, so it is **not in the repository**. Its `TEST` notebook is the intended fixture (a PDF, an image, a 510 KB web-clipper note, a to-do with a due date, tags `TEST` and `TEST2`); 1.15b should cut a small fixture out of it (without the clipper note's page, which is someone else's content) or generate one in the same shape.
2. **The editor adds a trailing paragraph and repairs ragged tables**, each by writing to the document when the page is open. Two clients opening an imported page would each write one. So the builder appends the empty paragraph itself when the content does not end in one, and the mapper makes tables regular. The contract test checks that opening a document in the editor changes nothing in the Yjs state. (The editor repaired no ragged table on open in the check; the table plugin only does so on a later change, so the regular tables are a safeguard.)
3. **Parser limits.** Markdig throws on deep nesting (even 1,000 nested lists) and AngleSharp's time grows with the square of the depth (100,000 nested `div` took 43 s, 100,000 nested lists 6 minutes; no stack overflow). Markup deeper than 3,000 levels (counted without parsing) and Markdown Markdig refuses become plain paragraphs with `nesting_flattened`. Below that, blocks nested over 15 levels are flattened (the sidecar stops at 64). Markdig on 10,000 nested `[` took 4 s: one pathological note can still be slow, so 1.15b's job should not assume a note converts quickly.
4. Joplin shows a line break in the text as a line break, so a soft break becomes a hard break. Markdig only reads a definition list with `:` and three spaces; with one space (which Joplin reads as a definition) the text stays as it is, nothing is lost.
5. Inline `code` excludes every other mark in the schema, so code inside a link keeps the link (`mark_dropped:code`), and bold code is code only.
6. Custom elements (a hyphen in the tag, as the tweakers.net clipper note has) and `time` are silent containers.
7. **Code review (high, on Opus) found ten issues, all fixed:**
   - **The depth count could be fooled.** `<div/>`, stray closing tags, and closing tags the parser ignores (`<span><div></span>`) each looked shallow while AngleSharp nested them 200,000 deep. `ContentRules.MarkupDepth` now never counts lower than the parser builds. Only a void element (and only outside SVG, MathML and `select`) opens nothing. A closing tag only closes the innermost element, and only when it names it. It adds the table parts the parser adds, and it skips the content of a script or style. An FsCheck property compares it with AngleSharp's tree on random tag soup (3,000 cases in the suite, 200,000 once by hand). A 50,000-case run found AngleSharp opening an element for `</br>` in MathML, which is handled too. The price: sloppy hand-written HTML (unclosed `p` or `li`) counts higher than it is, so in theory a very long, sloppy note becomes plain paragraphs. The real export's deepest HTML note counts 15.
   - The text of markup too deep to parse is read in one pass, without a regex, so an open `<!--` or `<script>` can no longer time it out.
   - A void element in Markdown that is removed (`<embed>`) no longer hides the rest of its paragraph. Markdown and HTML now report removed elements from one list.
   - HTML inside Markdown starts at the Markdown's block depth, so the two together stay under the sidecar's 64 levels.
   - Tables: a column span that runs into a row span from above stops before it, and a row with no cells of its own is left out, with the row spans across it one shorter. A second FsCheck property checks that every column of every row has exactly one cell, as ProseMirror's `TableMap` requires, and that no cell is lost.
   - The list and table building shared by both converters is now in `Shapes.Lists` and `Shapes.Table`. Each conversion uses one HTML parser, and a link's text is only read when needed.

### 1.15b: the import job and its API

Built on Sonnet 5.5 (high). Questions answered before building: split into 1.15b (server) and 1.15c (page); items in Joplin's trash are skipped and counted; notebook icons are ignored; an item over 64 MB is skipped and listed (a plain safety cap that 1.16's large-note handling replaces).

**As built** (`server/src/Inkpact.Api/Import/` unless said otherwise)
- `JexItem` reads an item's file (title, body, `key: value` lines from the end), `JexArchive` indexes the tar once with `System.Formats.Tar` (nothing is extracted; only `<32 hex>.md` and `resources/<32 hex>[.ext]` entries are looked at; links, directories and other names are skipped), `ImportPlan` decides the tree (iterative, so a file cannot overflow the stack; cycles are cut at the lowest id; a parent that is not in the file means the top level).
- `ImportRunner` carries out one import; `ImportWorker` runs them one at a time from `ImportQueue` and, in `StartAsync` (so before the first request), marks queued and running imports `interrupted` and removes `.jex` files older than five minutes; `ImportEndpoints` has the three endpoints; `ImportOptions` (`Import:Directory`, `MaxFileSize` 2 GB, `SidecarWait` 2 min, `SidecarRetryDelay`, `MaxConsecutiveFailures`).
- Data (`Inkpact.Data`, migration `AddImport`): `tags`, `page_tags`, `reminders`, `imports`, `import_items`, and `attachments.external_source_type/external_id` (unique per page). `import_items` does not cascade from `imports`, so what a later import compares with outlives the report.
- Changes to existing code: `AttachmentService.AddAsync` takes the external ids; `TreeService.LockWorkspaceAsync` is shared, so every imported page is made under the lock a tree operation takes; the Dockerfile sets `Import__Directory=/data/imports`.
- Docs: `docs/self-hosting.md` ("Importing from Joplin"), `docs/architecture.md` (core tables, "How the import runs").

**The API, for 1.15c**
- `GET /api/imports/limits` gives `{ maxFileSize }`.
- `POST /api/workspaces/{id}/imports/joplin?name=<file name>`: the raw file as `application/octet-stream` with the CSRF token (like an attachment upload). 202 with `{ id }`. Errors (`{ code }`): 400 `import_empty`, 400 `import_invalid` (not a tar), 413 `import_too_large` (also without a Content-Length), 409 `import_in_progress` (this workspace has one queued or running), 415 for any other content type, 403 for a viewer, 404 for a stranger, 401 signed out. The file is checked and kept only if it starts like a tar.
- `GET /api/imports/{id}`, for the person who started it only (anyone else: 404): `{ id, workspaceId, fileName, state, errorCode, totalItems, processedItems, createdAt, startedAt, finishedAt, counts, report }`. `state` is `queued`, `running`, `completed` or `failed`; `report` is null until the import has ended.
- `counts`: `notebooks, notes, todos, tags, images, files` (made now), `alreadyImported, trashed, skipped, failed` and `unlisted` (lines left out of a report of more than 5,000).
- `report` is a list of `{ kind: notebook|note|tag, externalId, title, status, reasons: [{ code, detail, count }], pageId? }`. `status` is `imperfect` (imported, not as it was), `conflict` (a Joplin conflict note, "(conflict)" added to its title), `skipped` or `failed`. `pageId` is there when a page was made, for the link.
- **Codes to translate** (en and nl): `errorCode` of a failed import: `import_invalid`, `import_empty`, `import_too_many_items`, `sidecar_unavailable`, `import_failed`, `interrupted`, `workspace_missing`. Reasons: everything in `NoteCodes` (the 1.15a list, and now `encrypted`, `item_too_large`, `resource_too_large`, `resource_empty`, `notebook_missing`, `notebook_cycle`, `parent_failed`, `conversion_failed`, `item_failed`); `detail` says which tag, scheme or file name, and is data, not a sentence.
- There is no list of imports and no push: the page has to keep the id (in its route, say) to find its import again after a reload, and read the tree again (`tree.load()`) when the import has ended, because the sidebar does not hear about pages made by the server.

**Findings**
1. **The real export** (`D:\Downloads\test export joplin.jex`, 320 notes) imports completely through the real database and sidecar (a throwaway test, not committed): 16 notebooks, 320 notes (311 to-dos, 259 completed, one with a due date and so one reminder), 2 tags, 42 attachments (21 pictures, 21 files, of which 20 are SVG), no failures, 8.2 s. The report has one line, the web-clipper note (`removed_element/svg`, `link_removed/relative`). The conversion's `note_link_pending` and `resource_link_text_lost` of 1.15a's check are gone: the resources resolve now.
2. **Speed:** a generated 1,000-note export with 20 notebooks takes about 11 s with pooled database connections, as the app runs (about 90 notes a second, one transaction and two sidecar calls per note); the first measurement, 22 s, was with the test database's unpooled connections. Five thousand notes would take about a minute, inside the 5-minute target; 1.16 checks it.
   - The import tests use pooled connections (`CreateDatabaseAsync(pooled: true)`). Unpooled, the 1,000-note test opened thousands of connections, ran the machine out of ports and failed other tests of the same run (`CompactorTests` with "only one usage of each socket address"); it also lost a note once. A test of an import has to pool.
3. A resource is copied onto each page that uses it (one `attachments` row per page, one stored file). The ids a note uses are found by looking for `:/<32 hex>` in its body, so an id inside a code block makes an attachment that nothing shows; harmless, and cheap to tighten later.
4. A note that fails is rolled back, but the files it already stored stay in the attachment store (unreferenced; the cleanup job of the architecture deals with them).
5. A tag of the same name that is already there (any case) is reused, not made again.

**Decisions to know about**
- Within a notebook, its sub-notebooks come first and then its notes, each by title (accents and case ignored, without the system's culture data). The card said "siblings by title"; mixing notebooks and notes alphabetically looked odd in a tree, so this is a small step beyond it.
- "(conflict)" is added to the title in English. It is data written at import time, not interface text, so it is not translated.
- A person who adds a page under a notebook while it is half imported could take a key the import has set aside; the database refuses the second one, and the import's note is reported as failed (`item_failed`) and finished by the next import. Very unlikely, and nothing is lost.
- No audit event: the import's own row says who, when, which file and how it ended.
