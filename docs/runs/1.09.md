# Run 1.09: sync hub

**Model:** O·high (planned and built on Opus 5.5)

## Goal

The production WebSocket sync hub from the spike: one multiplexed socket per client session, authenticated by the session cookie, checked for its Origin, limited in size and rate, with a permission check on every subscribe. Yjs updates are stored in order and relayed, never decoded. The spike's sync scenarios that need no editor become integration tests.

## Inputs

- `docs/architecture.md`: "Sync flow", "Security from day one" (WebSocket hardening, sessions), "Permission resolution".
- `docs/spike-findings.md`: the 1.09 row of "For the 1A runs" and the sync scenarios; the spike hub at the tag `phase0-spike`.
- Runs 1.05 and 1.06: the Postgres ticket store and the permission service. Run 1.07: pages, and edits to trashed pages are kept.

## Done when

- `GET /api/sync` opens a socket only for a signed-in user from the app's own origin.
- Subscribing needs viewer rights; changing needs editor rights; anything else is refused per page, without closing the socket.
- Every update is stored once, with its author, before it is relayed to the other subscribers.
- Logout closes the session's sockets; too big, too fast, malformed or too slow closes only that socket.
- The scenarios late join, page isolation, store once, subscribe during streaming, presence and restart pass as integration tests.

## Decisions (confirmed)

1. **The sidecar waits for 1.10.** The hub sends the stored log and the client works out what the server lacks, as in the spike. The subscribe carries the state vector already, so 1.10 can answer with a diff without changing the protocol. `spike-findings.md` and the architecture say so now.
2. **Server only.** The TypeScript sync client and the browser scenarios (typing together, offline, silent death, offline and online events) need the editor, so they move to 1.11; the roadmap row says so.
3. **Sessions end live.** Logout and logout everywhere close the sockets of those sessions at once, and a periodic check catches sessions that ended some other way.
4. **Roles are checked on subscribe.** A role that changes while a socket is open (sharing, phase 2) is not seen until the next subscribe.
5. **Limits**, all under `Sync:` in the configuration: 2 MiB per message, 100 messages a second with a burst of 500, 100 pages per socket, 20 sockets per user, 1,000 queued messages or 16 MiB per socket, keep-alive every 15 s with a 20 s timeout, a session check every 5 minutes.
6. **`CLAUDE.md` fixed:** it named YDotNet as the decoder; the spike chose the Yjs sidecar.

## As built

- **Table `page_updates`:** `seq` (identity, also the future compaction watermark), `page_id` (cascade with the page), `data`, `user_id` (set to null when the user goes), `created_at`; index on `(page_id, seq)`. Snapshots come in 1.10. The load runs in a repeatable-read transaction, ready for the snapshot read.
- **Protocol** (`Sync/Frame.cs`): `[varuint type][varstring pageId][payload]` in lib0, as in the spike. Subscribe 0 (payload: state vector), Unsubscribe 1, Update 2, Sync 3, Awareness 4, Ping 5 and Pong 6 (one byte each), and new: Error 7 with a code (`page_not_found`, `read_only`, `too_many_pages`). The page id must be a GUID in its one canonical spelling.
- **Endpoint** (`Sync/SyncEndpoints.cs`): `SignedIn` policy; 400 `websocket_required` for a plain request, 403 `origin_invalid` for a missing or foreign Origin (compared with the scheme after the forwarded headers and the Host), 429 `too_many_connections`.
- **Hub** (`Sync/SyncHub.cs`): a room per page with subscribers, the awareness cache and a lock; subscribe, store-and-relay and leave happen under it. A room without subscribers is removed, and a subscriber that waited on a removed room starts over. Permission questions get a fresh scope each, because the permission service caches its answers.
- **Connection** (`Sync/SyncConnection.cs`): one send loop over a queue with a count and a byte limit; a client that falls behind is dropped. A close is queued behind what is already waiting, and a client that does not answer it within 5 s is dropped.
- **Close codes:** 1000 normal, 1001 `server_stopping`, 1008 `protocol_error` or `rate_limited`, 1009 `message_too_big`, 1011 `server_error` (a database failure; the update was neither stored nor relayed), 4401 `session_ended` (the client goes to the login page rather than reconnecting).
- **Sessions:** the ticket store adds the session key to the properties of the ticket it returns, so a request knows its session; it raises `SessionEvents` when it removes sessions, and has `IsActiveAsync` for the periodic check.

## Tests

- **Integration, 31** (`SyncHubTests`), on the test server against Postgres:
  - **Security:** no cookie, a foreign or missing Origin, a plain request, the connection cap; a missing page and a page in another workspace give `page_not_found` and leak nothing; a viewer gets `read_only` and nothing is stored; an editor's update carries their id; a trashed page stays editable; an update for a page not subscribed closes the socket.
  - **The spike's scenarios:** late join (6), page isolation on one socket (7), stored once and not echoed (8, the server's side), 300 updates while a subscriber joins, each exactly once (9), presence relayed, cached and removed at the same clock (11), restart with the log from the database alone (3, the server's side).
  - **Limits:** size, rate, pages per socket, malformed messages, a non-canonical page id, text messages.
  - **Sessions:** logout closes only that session's sockets, logout everywhere closes all of the user's and nobody else's, a session deleted in the database is caught by the check, a stopping server closes with 1001.
- **Property (FsCheck):** 150 random sequences of valid and broken frames: the hub always answers or closes with `protocol_error`, never with a server error, and ends with no connections and no rooms left.
- **Unit:** frames and lib0 (12), awareness cache (5), the send queue against a socket that sends only when told (5), the Origin rule (10 cases), the session events in the ticket store (4), the new table (2).
- **e2e** (`sync.spec.ts`, and a line in `plain-http.spec.ts`): in Chromium, Pixel 7, iPhone (WebKit) and plain HTTP on a non-localhost name the app's own page opens the socket with no CSP violation, and a second tab receives the first one's update. 178 tests pass.

## Found while building

- **Cookie authentication with a session store does not keep the session id in the principal.** The claim exists only in the cookie's own small ticket; the principal comes from the stored one. The ticket store now puts the key into the properties of the ticket it hands back.
- **Cancelling a .NET WebSocket receive aborts the socket,** so a server-side close cannot be done by cancelling the receive loop. Closes go through the send queue instead, with a timeout that aborts.
- **The local SDK was 10.0.403** while `global.json` pinned 10.0.402 with roll-forward disabled. The pin is now 10.0.403, as agreed; CI must be able to download it (it could not when 10.0.402 was pinned).

## Not covered by a test

- The server keep-alive (Kestrel's ping and its timeout): the test server has no real socket. The setting is passed through; a check on a real Kestrel is worth adding with the client in 1.11.

## Handoff

- **For 1.10 (compaction):** the sidecar answers sync step 1 with a diff for the state vector in the subscribe payload (today ignored). `PageUpdateStore.LoadAsync` is where the snapshot read joins the update read in the same repeatable-read transaction. `seq` is global and increasing, usable as the watermark.
- **For 1.11 (editor and client):** connect to `/api/sync` from the same origin; ping every few seconds and treat any message as life; on Error frames show the translated code; on close 4401 go to the login page; on 1008, 1009 or 1011 reconnect with backoff and resync (subscribe again, then send the diff against the received state). The browser scenarios 1, 2, 4 and 5 from the spike become Playwright tests there.
- **For phase 2 (sharing):** roles that change while a socket is open are only seen at the next subscribe; a role change will have to close or resubscribe the affected sockets.
