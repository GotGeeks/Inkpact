# Run 0.4: YDotNet (yrs) versus a Yjs sidecar on the server

**Model:** O·high (Opus 5.5 for the whole run)

## Goal

Try YDotNet for merging updates and decoding a snapshot to plain text; note what works; if it falls short, prototype a minimal Node sidecar.

## Inputs

- `docs/architecture.md`: "Server CRDT handling", "Compaction guarantees", risk "Yjs decoding in .NET is immature".
- Run 0.2 handoff: the server can't diff yet, so the client computes the diff.

## Done when

- Every server-side operation is checked against real Yjs output, for both candidates.
- There is a recommendation backed by tests and numbers.

## How to run

```bash
pnpm --dir spike/client crdt:fixtures   # regenerate the Yjs fixtures (deterministic seeds)
dotnet test spike/server                # 65 codec tests + the 20 sync-hub tests (needs Docker and Node 24)
pnpm --dir spike/client crdt:verify     # feeds yrs' outputs into real Yjs
dotnet run spike/server/tools/minimize-yrs-repro.cs   # from the repo root: rebuild the minimal repro
```

## Method

- **Fixtures written by real Yjs.** `spike/client/scripts/crdt-fixtures.ts` builds a TipTap document with the real StarterKit schema through `@tiptap/y-tiptap`: headings, marks, nested lists, code block, quote, rule, Dutch accents, emoji. Three clients then edit it concurrently and sync at random moments. The fixtures record every update in the order the server would receive it, plus the expected plain text (ProseMirror's own `textBetween`), the state vector, and a half-synced client's state vector.
  - Four fixtures: `tiptap-small` (298 updates), `tiptap-10k` (9,926), `no-format-2k` (no marks), `insert-only-2k`.
  - Plus a deliberate split emoji, and the minimal repro below.
- **One contract, two implementations.** `ICrdtCodec` (merge, diff, state vector, text) is implemented by `YrsCodec` (YDotNet 0.6.0, in process) and `YjsSidecarCodec` (Node + Yjs over stdio). Both run the same contract tests (`CodecContractTests`).
- **Round trip into Yjs.** `crdt-verify.ts` loads what yrs produced (snapshots, diffs, half-snapshots) into real Yjs and compares, because a snapshot the browsers can't read correctly is the worst outcome.

## Results

| Operation | yrs (YDotNet 0.6.0) | Yjs sidecar |
| --- | --- | --- |
| Merge a log in arrival order; text matches ProseMirror | ✅ | ✅ |
| State vector matches Yjs | ✅ | ✅ |
| Merge a snapshot again: byte-identical (idempotent) | ✅ | ✅ |
| Snapshot plus updates it already contains | ✅ | ✅ |
| Incremental compaction: snapshot plus newer updates | ✅ | ✅ |
| Diff for a client's state vector, applied by Yjs | ✅ | ✅ |
| Snapshot, diff and half-snapshot read back by Yjs (`crdt-verify`) | ✅ | n/a |
| Updates applied out of causal order | ❌ | ✅ |
| Merged multi-client diff applied on top of an existing state | ❌ | ✅ |
| A deletion that arrives before its content | ❌ (deletion lost) | ✅ |
| Half of an emoji deleted (`a😀b`, low surrogate removed) | ❌ (`a😀`: **`b` lost**) | ✅ (`a�b`, as Yjs) |

**The yrs bug, minimised.** Delta debugging with the sidecar as reference, starting from a shuffled `tiptap-small`, found a 2-update reproduction (`Fixtures/yrs-out-of-order-repro.json`):
1. A delete set for 3 characters (`é, `).
2. The base document containing them.

Yjs keeps the deletion pending until the content arrives; yrs drops it, so the deleted text comes back. Turning off garbage collection doesn't change this. The same happens on Windows x64 and in a Linux x64 container. The yrs build has no version number: it's a git submodule inside the YDotNet repo, built in February 2026, and the YDotNet README calls the project "early, may contain bugs".

**Numbers** (`tiptap-10k`: 9,926 updates, 220 KB of log, Windows x64):

| | yrs | Yjs sidecar (incl. JSON + base64 over stdio) |
| --- | --- | --- |
| Merge | 14 ms (20 ms on Linux x64) | 33 ms |
| Text extraction | 5 ms | 8 ms |
| Diff for a state vector | 4 ms | 8 ms |
| Snapshot size | 104,751 B | 104,751 B |
| Memory | in process | sidecar working set 104 MB (peak 107 MB) |

- For comparison, `Y.mergeUpdates` (merging without loading a doc) takes 632 ms and gives 138 KB, because it can't garbage-collect deleted content. Compaction should load a doc and encode its state, not merge updates.
- Applying the log in one write transaction gives a byte-identical snapshot. One transaction per update was slower and not byte-stable when merged again.

**Deployment notes:**
- `YDotNet.Native.Linux` ships `linux-x64`, `linux-arm64`, `linux-arm`, `linux-musl-x64` and `linux-musl-arm`, but **no `linux-musl-arm64`**. An Alpine arm64 image can't load yrs.
- The package uses a non-standard runtime folder name (`linux-x64-musl`), which causes SDK warning NETSDK1206 on every build.
- arm64 was not tested.

## Recommendation (to confirm in 0.7)

**Use the Yjs sidecar for everything that applies updates on the server: compaction, its verification, and text extraction. Don't use YDotNet in 1.10.**

- **Why:**
  - In steady state the log is in causal order and yrs gets it right. But the cases where it isn't (a database restore, reconnecting clients' diffs after data loss, a merged multi-client update) are exactly the ones where losing data is least acceptable.
  - The yrs failure is silent: a wrong snapshot that every browser would load.
  - The compaction verification ("compare with a full replay") can't catch it if the replay also runs in yrs.
  - The sidecar is Yjs itself, the same code the browsers run, so there is nothing to diverge from.
- **The 0.2 deviation can be undone.** The sidecar diffs against a state vector in 8 ms for 10k updates, so the server can answer sync step 1 as the architecture describes.
- **Costs:**
  - Node in the container image, plus about 100 MB of memory for the sidecar. That still fits the 500 MB idle target, but leaves less room.
  - A supervised child process (restart on crash, health check).
  - An IPC format: binary framing instead of base64 JSON for production.
  - A Debian-based image either way, since Node and glibc yrs are both happiest there.
- **Re-evaluate yrs when YDotNet updates.** The `Known_divergence_*` tests pin today's behaviour, and one of them failing means the bug changed.

Proposed update to `docs/architecture.md` → "Server CRDT handling", for 0.7 to confirm: "a small Node sidecar running Yjs handles compaction, diffs and text extraction; YDotNet was evaluated in spike 0.4 and diverges from Yjs on out-of-order updates."

## Handoff

- **Done:**
  - Yjs fixtures from TipTap's real schema and a contract test suite run against both codecs: 65 tests, green in 3 repeated runs, plus the Yjs round trip.
  - The minimal 2-update yrs repro and the delta-debugging tool.
  - A sidecar prototype over stdio.
  - A Linux x64 check of yrs.
- **Left for 0.5:** the compaction stress test (50,000 edits, repeated compaction, compared with an uncompacted replay) should use the sidecar. The fixture generator and contract tests are its starting point.
- **Left for 0.7:** confirm the decision and update the architecture. The upstream yrs bug was not reported; the repro is ready if someone wants to file it.
- **Surprising:**
  - yrs's in-order results are byte-identical to Yjs, which made the out-of-order bug easy to miss: the first version of these tests only applied logs in order.
  - Windows decodes a child process's stdout in the console code page, so the sidecar needs explicit UTF-8.
