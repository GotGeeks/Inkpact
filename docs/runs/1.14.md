# Run 1.14: Attachments

**Model:** S·high in the roadmap; planned and built on Opus 5.5 high at the maintainer's choice. Touches two security lines (safe serving, the JSON-only rule) and the permission service, so `/code-review` at high.

## Goal

A file can be added to a page and comes back to the people who may read that page, and nobody else. Images show inline in the editor; other files show as a download. Files are stored once per content (SHA-256), behind a storage interface whose first implementation is the data volume, with a size limit and serving headers that keep an uploaded file from ever running as part of the app. This is the base the Joplin import (1.15) writes its resources into.

## Decisions

Proposed by the planner and taken as recommended, since the maintainer asked to build straight after the card.

1. **Two runs: 1.14a (server) and 1.14b (editor).** One run would touch about 25 files. 1.14a is the storage, the endpoints and the serving rules, testable with HTTP alone; 1.14b is the image and file nodes, upload from the picker, paste and drop, and the slash menu and toolbar entries. The import (1.15) needs only 1.14a's service and 1.14b's nodes.
2. **Storage interface `IAttachmentStore`**, content-addressed: `PutAsync(stream)` returns the SHA-256 and size, `OpenReadAsync(hash)`, `ExistsAsync(hash)`. No delete yet (decision 10). The local implementation writes to a temporary file in the same directory tree while hashing, then moves it to `<root>/<aa>/<bb>/<sha256>`; if the target exists the temporary file is dropped (same content, so a race between two uploads of one file is harmless). Leftover temporary files are removed at start-up. Root: `Attachments:Directory`, default `data/attachments`; the image sets `/data/attachments`.
   - Weighed: a separate volume for attachments. The setting allows one (mount a second volume there), but the default stays inside `/data`, so the backup advice stays "back up `/data` and the database".
3. **The `attachments` table** (migration `AddAttachments`): `id` (UUID v7), `page_id` (cascade), `file_name` (≤ 255), `content_type` (≤ 127), `size`, `sha256` (64 hex characters, the storage key), `created_at`, `created_by` (set null). Indexes on `page_id` and `sha256`. One row per upload, so the same file on two pages, or twice under two names, is two rows and one stored file.
   - Import identity (a Joplin resource id, for re-import) is not added here; 1.15 adds the columns it needs.
4. **Upload: `POST /api/pages/{pageId}/attachments?name=<file name>`**, editor role on the page, the raw file as the body with `Content-Type: application/octet-stream`, the CSRF header as for every call. Answer 201 with `{ id, fileName, contentType, size, inline }`.
   - **The JSON-only rule gets one exception, by endpoint metadata, not by path:** an endpoint marked `AcceptsRawUpload` accepts `application/octet-stream` and nothing else. A cross-site form still cannot reach it: it cannot send that type without a preflight, and it cannot set the CSRF header.
   - Weighed: multipart. It needs form parsing (and minimal APIs' automatic antiforgery on `IFormFile`), and gains nothing for one file per request.
   - **The client's type is not trusted.** The server reads the first bytes and recognises PNG, JPEG, GIF and WebP by their signature; those are the only types shown inline. Anything else gets a type from its extension, is stored as such, and is always served as a download. SVG is never inline (it can carry script).
   - **The name** is cleaned: path parts, control characters and the characters Windows refuses are dropped, it is cut to 255 characters (keeping the extension), and an empty one becomes `file`.
5. **Size limit `Attachments:MaxFileSize`, 50 MB by default.** A `Content-Length` over it is refused before reading (413, `attachment_too_large`); a body without one is counted while streaming and refused the moment it passes the limit, with the temporary file removed. Kestrel's own body limit is raised to the setting for this endpoint only. An empty file is refused (`attachment_empty`).
6. **Download: `GET /api/attachments/{attachmentId}`**, viewer role on the attachment's page. The permission service gets `GetAttachmentRoleAsync` (attachment → page → the page's role) and the filter a `RoleScope.Attachment`, so 2.2's shares reach attachments without touching the endpoint. No access, or no such attachment: 404, as for pages.
   - Weighed: `/api/pages/{pageId}/attachments/{id}`. An image copied to another page would then carry the wrong page in its address; with the id alone it keeps working wherever it is pasted, for whoever may read the page it was uploaded to.
7. **Serving headers,** on top of the global ones (`nosniff`, `Cross-Origin-Resource-Policy: same-origin`):
   - `Content-Type` as stored; `Content-Disposition: inline` for the four image types and `attachment` for everything else, with an RFC 5987 `filename*`;
   - its own `Content-Security-Policy: default-src 'none'; img-src 'self'; style-src 'unsafe-inline'; sandbox`, replacing the app's, so a file opened on its own is a sandboxed document that runs nothing (the style source is what the browser's own image viewer needs);
   - `Cache-Control: private, no-cache` with the SHA-256 as `ETag`, so the browser revalidates (a cheap 304) and access taken away in phase 2 is never served from a cache. The JSON-only middleware's `no-store` is skipped for endpoints marked as downloads, by metadata.
   - Range requests on, so a large PDF or video can be read in parts.
8. **The editor (1.14b): two nodes of our own, not `@tiptap/extension-image`.** That extension stores an address (`src`); ours store `attachmentId` and nothing that could point elsewhere:
   - `image` (block): `attachmentId`, `alt`. Rendered as `<img src="/api/attachments/{id}">` only when the id is a UUID, checked when it renders, because content from other clients arrives through Yjs (the same reason links are checked on render). A bad id renders as a broken-image placeholder, never as an address.
   - `attachment` (inline atom): `attachmentId`, `fileName`, `size`. Rendered as a download link with the name and a size formatted with `Intl`.
   - No new dependency.
9. **Adding files (1.14b):** the slash menu and the toolbar get "Image" and "File", which open the file picker; pasting or dropping files uploads them. While a file uploads the editor shows nothing in the document; when it is done the node goes in at the place the caret was, kept as a Yjs relative position, so edits by others in the meantime do not move it. A failure shows a translated notice (`attachment_too_large`, network). Several files go in one after another. Pasted HTML still drops an `img` from another site: it is not ours to load (and the CSP would block it). One of the app's own (a valid id, never a `src`) is kept, so an image or file copied between pages survives; who may then see it is in architecture → "Attachments" (changed after review).
10. **Not in this run: the daily cleanup of unreferenced files.** Finding them means reading which ids every page's content holds, which is the sidecar's job and best done in compaction, next to `content_text`. Deleting files is also the one irreversible step here. It moves to a run of its own after the trial starts; the architecture gets a line saying so.

## Done when

**1.14a**

- An editor uploads a file to a page and gets its id; the same bytes uploaded again are stored once on disk.
- A viewer of the page downloads it; anyone else gets 404, as for a page. The coverage test names no endpoint without a policy.
- PNG, JPEG, GIF and WebP (by signature, whatever the client claimed) are served inline; SVG, HTML and everything else as a download, all with the sandboxing CSP and `nosniff`.
- A file over the limit is refused with `attachment_too_large`, with and without `Content-Length`, and leaves nothing on disk.
- The image writes attachments to `/data/attachments` with the read-only root filesystem.

**1.14b**

- Image and File from the slash menu and toolbar, paste and drop: the file uploads and the node appears where the caret was, in both browsers of a sync scenario.
- An image node with an id that is not a UUID (put in through Yjs) renders no address.
- No CSP violation, keyboard reachable, labels in English and Dutch.

**Findings and decisions made while building**
- The 1.13 handoff's `Network` and Traefik checks stay for the trial (see "For the trial"); nothing here needs Traefik settings, as Traefik has no body limit by default.
- No rate limit or quota on uploads yet: a signed-in editor can fill the disk. Quotas are phase 2 (2.9); until then the trusted-administrator model applies.
- A tab still on a bundle from before 1.14 shows "this page needs a newer version" for a page with an image or file in it (1.11's content check), and changes nothing.
- An attachment belongs to the page it was uploaded to. Copied into another page it keeps working for anyone who may read the first page. The architecture now says a paste into another page must get its own row before pages can be deleted for good or shared (2.2).

**After `/code-review` (medium)**, ten findings, all dealt with:
1. The file picker kept a plain position while it was open; the place is now a Yjs relative position from the moment the picker opens.
2. A click on a file could download it twice (the link's own click as well); the click is cancelled and one detached link downloads it, in editable and read-only pages alike.
3. A finished upload moved the caret; it no longer does (`updateSelection: false`), and the next file's place comes from the transaction's mapping, not the selection.
4. A large body the server does not read can reach the browser as a reset connection; the client asks for the limit (`GET /api/attachments/limits`, signed in) and refuses too large and empty files before sending (`attachmentApi.ts`).
5. Ownership of copied attachments: written into architecture → "Attachments" (above), with the trigger for giving a copy its own row.
6. Enter on a selected file downloads it; in a read-only page the link is reached with Tab.
7. The picker is kept in the page (hidden) until it answers or is cancelled, for iOS Safari.
8. Files that cannot be placed any more (the page closed or became read-only, or their place was deleted) are reported once (`attachment_not_added`).
9. Half a surrogate pair in a name is dropped instead of throwing; Windows device names (`CON`, `NUL.txt`, `COM1`) get a `_` in front.
10. The store returns the first bytes it read, so the type needs no second read, and keeps no file for an empty upload. Not changed: the download still asks for the attachment twice (the role check, then the row), both by primary key; the permission service stays the only thing that decides access.
- Not changed: a CSRF retry sends a file twice. It is rare (a token from before another tab signed in or out) and the second send is the one that counts.
- Two of four full server runs on Windows had one failure each that is not about attachments: a 500 from `/api/auth/state` in a `SyncHubTests` setup, and in `TreeServiceTests` a Postgres connection refused with "Only one usage of each socket address" (local ports used up by the many test databases). Both classes passed on their own, and two full runs passed. Worth a look if it keeps happening: the test databases connect without pooling.
