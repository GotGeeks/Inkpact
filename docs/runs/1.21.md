# Run 1.21: Offline edits on a large page are kept (#48)

**Model:** "S·med; O·high for anything that loses or corrupts data" in the roadmap. This bug loses data, so it gets the O·high treatment. Planned on Opus 5.5 high. Builds on Sonnet 5.5 high: the change is small, and the risk is in the size limits and in a test that passes without really making a large copy. Run `/code-review` at high on Opus before the PR merges.

## Goal

Sometimes a Sync would delete text that someone typed offline. Step 7 of the sync flow then keeps that text in a copy beside the page. Today this works only for pages up to 2 MiB. Since 1.16d, imported pages can be up to 8 MiB, and offline edits on such a page are lost when the session ends. After this run, any page that can be opened also gets its copy, so nothing typed offline is lost.

This is the first bug-fix run from the trial. Issue #48 is the only open `type:bug`.

## What is there now (found while planning)

1. **The limit is the size of one sync message.** `Create` refuses base64 content longer than `MaxMessageBytes` (2 MiB) with `413 content_too_large`. The reason given in the comment ("could not reach the page the other way either") stopped being true in 1.16d. Pages up to 8 MiB now exist, and the hub sends a large page as it is stored.
2. **The real ceiling for a page already exists, but only in the import.** `CheckNoteLimits` allows at most half of `Sync:MaxQueuedBytes` (8 MiB by default), because a larger page could not be opened. The pages endpoint does not use it.
3. **The request body is limited only by Kestrel's global default of 30 MB.** Nothing in `Program.cs` changes that default. The JSON body is read while the parameters are bound, before `Create` runs. So setting `IHttpMaxRequestBodySizeFeature` inside the handler, as the attachment and import endpoints do with their streams, would come too late here.
4. **The client retries a refused copy without end.** In `useKeepLostEdits.ts`, every error except `network_error` first falls back to the top level. Then the copy waits: the person is told once, it is tried again on every reconnect, and it is dropped at sign-out. A 413 is permanent, so for a page over 2 MiB the edits are certain to be lost, but the notice still says "keep this tab open".
5. **No browser test covers the offline copy.** The issue says "like the existing offline-copy test", but the copy is covered only in Vitest (`useKeepLostEdits.test.ts`, `pageCopy.test.ts`) and in the server's `PageEndpointTests`. No Playwright spec makes a copy, at any size.
6. **One server test fixes the old limit in place.** `Content_without_an_id_content_that_is_not_base64_and_content_over_a_sync_message_are_refused` expects 3 MiB of content to be refused.

## Decisions

1. **The issue's option 1: the same single request, with a higher limit.** The guarantee "the page and its content are one request" stays as it is, and so do the idempotent id, the transaction, and the fallback to the top level. Option 2 (content in parts) would undo that guarantee. Option 3 (keep only what was typed) would change what the copy is. Both are larger changes for a rare case.
2. **One name for the ceiling** (question 1). `SyncOptions.MaxPageBytes` is computed, not configured: exactly `MaxQueuedBytes / 2`. (Built first with a floor of one sync message; the review found that this loosened the import's ceiling under a small queue, so the floor was dropped.) `CheckNoteLimits` uses it, so the import and the pages endpoint share one definition. The startup error message of `CheckNoteLimits` stays the same. **Changed while building:** `Create` uses `SyncOptions.MaxCopyBytes`, `MaxPageBytes` and an eighth more (9 MiB by default). The copy is written again from the page's blocks and came out 0.14 % larger than the page in a test with 3,000 blocks, so with the plain ceiling a page right at the limit would still get no copy.
3. **`Create` checks the content twice.**
   - Before decoding: the base64 length must be at most `4 * ceil(MaxCopyBytes / 3)`.
   - After decoding: the content must be at most `MaxCopyBytes` bytes.

   If either check fails, the answer is `413 content_too_large` with field `content`, as now.
4. **A request size limit for this one route,** set as endpoint metadata (`IRequestSizeLimitMetadata`, for example `.WithMetadata(new RequestSizeLimitAttribute(n))`). The routing middleware applies it before the body is read. `n` is the base64 of `MaxCopyBytes` plus 64 KiB for the rest of the JSON (title, ids). That headroom means content just over the limit gets our own `content_too_large` code. Only a body far over the limit gets Kestrel's plain 413. The test server does not enforce a body limit, so a test checks the endpoint's limit metadata, and the real server was probed by hand (see Handoff). The global 30 MB default stays as it is (see Out of scope).
5. **No change to the client's request.** `copyUpdate` and `toBase64` already handle a large page: `toBase64` works in pieces. A Vitest test checks that the copy of a large page is not larger than the page's own state plus a small margin. If it were larger, a page just under the ceiling could not be copied.
6. **The client still retries a copy that is too large, but no longer says "keep this tab open"** (question 3). Only a page over the ceiling can still get the 413, and such a page could not have been opened anyway. In that case the person gets a different notice, once: the offline changes to "{title}" are too large to keep as a copy. The notice uses new keys `editsTooLarge` in `en.json` and `nl.json`. The edits still wait in the tab until sign-out, as before. This changes the words only, not the flow.
7. **The first Playwright spec for the copy:** `web/e2e/offline-copy.spec.ts`, with two tests.
   - **A small page, on every project.** Browser A opens the page, goes offline (`context.setOffline(true)`) and types a marker at the end of the last paragraph. Browser B deletes that paragraph. A comes back online. A notice says the text was kept, and a page "{title} (your offline changes)" appears right after the original, with A's marker in it.
   - **A page of about 6 MB, desktop only, marked `test.slow()`.** The page is made by importing a generated JEX with one large note (`jex.ts`, extended to make one), because that is how such pages come about. The test then runs the same steps, and checks that the copy holds the marker and the first and last lines of the note. The two tests share their setup and steps through one helper, so the only difference between them is the size.

## Done when

- Offline edits on a page of about 6 MB that a Sync would delete end up in a copy beside the page (Playwright, desktop).
- The same works for a small page on desktop, Pixel 7 and iPhone 15.
- Content up to `MaxCopyBytes` is accepted and stored byte for byte. Content one byte over gets `413 content_too_large`. A body over the route limit gets 413 before anything is read into a page. In none of these cases is a page made without its content.
- A copy that is still too large gets its own notice, once, in both languages.
- `docs/architecture.md` step 7 gives the new limit.

## Questions

1. **Which ceiling limits the copy?**
   - Half of `Sync:MaxQueuedBytes` (8 MiB): the ceiling the import already enforces, and the size of a page that can be opened. **Recommended.**
   - `Import:MaxNoteUpdateBytes`: the issue's wording. It ties the pages endpoint to an import setting, so an administrator who lowers the import limit would also limit copies of pages written by hand.
   - A new setting, `Sync:MaxPageBytes`: one more setting to explain, which must be kept at most half the queue anyway.
2. **Other trial findings for this run?** #48 is the only open bug. If the trial has turned up something not yet filed that belongs with it (sync, offline, large pages), file it, and I will add it here. Otherwise it gets a run of its own. **Recommended: #48 alone,** as the roadmap says: one bug or a small group per run.
3. **A copy that is still too large:**
   - Its own notice once ("too large to keep as a copy"), with the retry and the tab as they are. **Recommended.**
   - Leave the "waiting" notice as it is.
   - Also offer the offline text as a download. That is new behaviour, and it would need a design.

### Review fixes (`/code-review`, 10 findings, all fixed)

1. `MaxPageBytes` is exactly half the queue again (no floor of a sync message), so `CheckNoteLimits` is as strict as before and a copy (`MaxCopyBytes`, 9/16 of the queue) always fits the queue.
2. Only the server's own `content_too_large` gives the "too large" notice. Any 413 (a proxy's too) still skips the top-level fallback, but a proxy's 413 is a copy that is waiting.
3. What the person was told is kept per kind (`id:type`), so "too large" is said after "waiting".
4. A copy the server calls too large is not tried again. The base64 content is made once per lost edits and reused for every try; it is dropped with the edits.
5. The content check is `PageEndpoints.ReadContent`, unit-tested in `PageContentTests` with a limit base64 rounds up (10 bytes), so the check after decoding is covered. (Mutation-checked for the client's no-retry guard as well: the test fails without it.)
6. No fixed sleeps in `offline-copy.spec.ts`: it waits for the selectionchange that ProseMirror reads, and for `data-unsent="false"` on the status pill (new: the store's `unsent`, any open page with changes the server has not confirmed). Ran twice on each project, all green.
7. Architecture step 7: the handler enforces the exact limit; the route's limit is a coarse cap.
8. Self-hosting: the garbled parenthesis is gone, and it says that a proxy must pass about 13 MB on every route (nginx's 1 MB default refuses the copy of a page over about 700 KB).
9. One definition of the route's limit (`PageEndpoints.MaxCreateBodyBytes`, with `Base64.GetMaxEncodedToUtf8Length` and the internal `RequestOverhead`), checked in the unit tests against `Convert.ToBase64String`.
10. The toaster's important notices are one set.
