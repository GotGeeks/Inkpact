# Run 1.07: tree API

**Model:** O·high → S·high (planned on Opus 5.5, built on Sonnet)

## Goal

Pages form a tree per workspace, changed only through the REST API. Every operation is applied one at a time and checked against the current state, following "Tree and metadata conflicts". Sibling order uses fractional index keys, so a move writes one row. Every page carries a version number, so conflicts are logged even where the last write wins. Property-based tests drive random sequences of operations and check the invariants after every step.

## Inputs

- `docs/architecture.md`: "Tree and metadata conflicts" (the table, version numbers, ordering), the `pages` row, "Permission resolution" (a move needs editor rights), "Quality standards" (FsCheck for tree operations).
- Run 1.03: `pages` with `parent_id`, `sort_key` (collation `C`) and `deleted_at`. Run 1.06: `IPermissionService`, `RequirePageRole`, `RequireWorkspaceRole`, the endpoint coverage test.

## Done when

- Create, rename, move (including nesting and reordering), trash and restore work through the API, with the rules of the conflict table.
- A move into the page's own subtree is refused, also when two moves race to make a cycle together.
- Siblings never share a key, and no operation rewrites any row but the one it moves.
- The FsCheck model test runs hundreds of random sequences against Postgres, and the tree always matches a simple in-memory model.

## Design

### Fractional index keys (`FractionalIndex`)

- **No maintained .NET library exists.** The only package, `FractionalIndexing` 1.0.1, was last released in July 2024, has no license, and has one author. So, as the architecture allows, the reference implementation is ported: `generateKeyBetween` and `generateNKeysBetween` from `fractional-indexing` (npm, 4.0.0, CC0, by rocicorp), with its base-62 digits.
  - Its order is plain byte order, which is what the `C` collation on `sort_key` gives.
- **Tested against the original:**
  - A one-off script, run in the scratchpad with the npm package (not a project dependency), writes about 2,000 `(a, b) → key` cases, edge cases first: empty, first, last, long runs of the same digit, and keys that need a longer integer part.
  - The JSON goes into the test project as a fixture with a note on how it was made, and the C# port must give byte-identical keys.
  - The reference's own error cases (`a >= b`, invalid keys) must throw.
- **Properties (FsCheck, no database):**
  - for any ordered `a < b`, the key lies strictly between them;
  - `generateNKeysBetween` gives n distinct sorted keys between its bounds;
  - repeatedly inserting at the front, at the back, or always just after the same sibling keeps the keys sorted and their length growing slowly (a bound is checked, so a regression that makes keys balloon shows up).
- **Only the server computes keys.** A client says where a page goes by its neighbours (`afterId`, `beforeId`). It never sends a key, so a buggy or hostile client cannot produce ties or junk keys.

### Schema (migration `AddTreeVersions`)

- `pages.version` (int, default 1): +1 on every metadata change (rename, move, trash, restore).
- `workspaces.tree_version` (bigint, default 0): +1 on every tree operation in the workspace.
  - Every operation takes the workspace row's lock by doing this update first, inside its transaction. So all tree changes in one workspace are applied one at a time.
  - That is what stops two moves that are each valid from forming a cycle together, and two inserts at the same spot from getting the same key.
  - It uses no raw SQL (`ExecuteUpdate`). The client can later use `tree_version` to see whether its tree is out of date.
- **A unique index on `(workspace_id, parent_id, sort_key)` for live pages** (`deleted_at IS NULL`, `NULLS NOT DISTINCT`, so the root level counts too). Two live siblings with the same key is then a database error, not a subtle ordering bug.

### Trash

- **Only the page itself is marked** (`deleted_at`). Its descendants are hidden because an ancestor is in the trash, so they go with it and come back with it, exactly as the table says.
- A child that was trashed on its own earlier keeps its own `deleted_at`, and stays in the trash when the parent comes back.
- "In the trash" therefore means the page, **or any ancestor**, has `deleted_at`. One recursive query answers it (raw SQL, as allowed for tree queries).
- The trash list shows the top-most trashed pages: trashed, and no trashed ancestor. Those are what a person restores.
- **Restore:**
  - If the parent exists and is live, the page goes back to its old place: its old key if that is still free between the current siblings, otherwise right after the nearest key below it.
  - Otherwise (the parent is in the trash itself, or was moved into the trash) it goes to the end of the root level.
  - The answer says which: `restoredTo: "original" | "root"`, so the client can show the notice.
- **Content edits to a trashed page are kept** (sync, 1.09). Metadata operations on a trashed page are refused with `409 page_in_trash`; restore it first.
- **Not in this run:** emptying the trash and the 30-day purge. I'd add them with the trash view in 1.08 (a delete-forever endpoint plus a daily job). They need the content tables (1.09 and 1.10) to delete everything that belongs to a page, so 1.10 might be the better home. Decide in 1.08.

### Operations (`TreeService`, one transaction each, workspace row locked first)

| Endpoint | Role | Body | Rules |
| --- | --- | --- | --- |
| `GET /api/workspaces/{workspaceId}/pages` | Viewer | | The live tree as a flat list (`id`, `parentId`, `title`, `sortKey`, `version`, `updatedAt`) in tree order, plus `treeVersion`. One recursive query that stops at trashed pages |
| `GET /api/workspaces/{workspaceId}/trash` | Viewer | | Top-most trashed pages with `deletedAt` |
| `GET /api/pages/{pageId}` | Viewer | | One page, with `inTrash` |
| `POST /api/workspaces/{workspaceId}/pages` | Editor | `title`, `parentId?`, `afterId?`, `beforeId?` | The parent must be a live page of this workspace (`400 parent_invalid`, `409 parent_in_trash`). Neighbours must be live children of that parent and in the right order (`400 position_invalid`). With no neighbours the page goes at the end |
| `PATCH /api/pages/{pageId}` | Editor | `title`, `expectedVersion?` | Last write wins |
| `POST /api/pages/{pageId}/move` | Editor | `parentId?`, `afterId?`, `beforeId?`, `expectedVersion?` | As create, plus: the new parent may not be the page or one of its descendants (`409 move_cycle`). Moving to another workspace is phase 2 (it needs editor rights on both sides) |
| `POST /api/pages/{pageId}/trash` | Editor | `expectedVersion?` | Trashing what is already in the trash is a no-op that answers the same |
| `POST /api/pages/{pageId}/restore` | Editor | `expectedVersion?` | Only a page that is itself trashed; one that is only hidden by an ancestor gives `409 restore_the_parent` |

More detail:
- **Titles** are trimmed, up to 500 characters, and may be empty; the client shows "Untitled" in the reader's language.
- **Version numbers:** when `expectedVersion` differs from the current version, the change still wins, as the table says. The server logs a `tree_conflict` warning (page, operation, expected, actual) and the answer includes `conflict: true`. Every answer carries the new `version`.
- **Validation order:** permission (the filter: 404 or 403), then existence and workspace, then trash state, then cycle, then position. One error code each, field where it fits.
- **Ids** are Guid v7, created by the server.

### Tests

**`FractionalIndexTests`:** the fixture against the original, the reference's error cases, and the FsCheck properties above.

**`TreeServiceTests`**, Testcontainers, one case per row of the conflict table and every error code:
- rename versus rename;
- move versus move;
- move into own subtree;
- move into a trashed parent;
- trash a parent, then restore it, and the children come back;
- a child trashed earlier stays in the trash;
- restore when the parent is gone, which goes to the root with `restoredTo: root`;
- restore versus move;
- restore into an occupied key;
- metadata on a trashed page;
- the version and conflict flag.

**Concurrency:**
- 20 parallel creates at the same spot give 20 distinct keys, all present.
- A→under B and B→under A in parallel: exactly one succeeds, the other gets `move_cycle`.
- Parallel move and trash of the same subtree end consistent.

**`TreeModelTests` (FsCheck, model-based):**
- Random sequences of 1–40 operations (create, rename, move with random neighbours, trash, restore) on a fresh workspace.
- Each operation is applied to `TreeService` and to a plain in-memory model of the same rules. The answers must agree: the same success or error code.
- After every step:
  - the live tree from the database equals the model, shape and order;
  - no cycles;
  - every live page's parent is live or the root;
  - sibling keys are strictly increasing;
  - every page is either in the live tree or under a trash root, never both, never lost;
  - versions only grow.
- 200 sequences by default, about 30 s. `INKPACT_PROPERTY_RUNS` sets more for a soak run. A failing case is shrunk to its shortest sequence, with the seed printed.

**Endpoints:** the role per endpoint (viewer reads, editor writes, a stranger gets 404), CSRF on every write, and the coverage test passes without changes to its list.

**No client in this run** (1.08). The error codes get their messages when the UI first shows them, so no unused i18n keys.

## Decisions (confirmed)

All six, as proposed: the key algorithm ported and tested byte for byte against the original package; `FsCheck` and `FsCheck.Xunit` 3.6.0 as test dependencies; trash marks only the trashed page; tree operations serialised per workspace by the workspace row lock; version conflicts logged and flagged, never refused; emptying the trash and the purge left out.

## As built: changes from the plan

- **The port is the default-alphabet subset** of `fractional-indexing` 4.0.0. The original also takes custom alphabets, which Inkpact does not need. It is stricter than the original on junk (a character that is not a letter or digit is refused even in a fraction), which cannot matter for keys the server made. The vectors (2,123 single keys, 63 runs, 7 refusals) and the script that makes them are in `server/tests/Inkpact.Api.Tests/Fixtures`. Every vector matched on the first run.
- **Service tests, 54:** one case per row of the conflict table and per error code, and a few that read the database directly (no renumbering, one row changed, byte order of keys, the unique index).
- **Concurrency tests, 8**, with a check that they bite: with the workspace lock turned off, 6 of the 8 fail.
- **The model test:**
  - Its first generator was useless. FsCheck makes small integers, so 838 of about 1,000 operations were creates. A coverage check inside the test caught that. The numbers are now spread evenly, the kinds are weighted, and targets are chosen with the model's knowledge (a trashed page to restore, a parent of something trashed to trash, a real sibling as a neighbour), with the rest left random so refusals happen too.
  - Where a restored page lands among its siblings depends on its old key, which the model does not have. The model checks that the other siblings kept their order, then adopts the service's place.
  - Rare outcomes (a restore into a parent that is gone, a move that makes a cycle, and so on) are **scripted sequences** run through the same model and the same checks, so they happen every run. The random run asserts only robust floors, so it cannot flake.
  - It was checked against four deliberate bugs (no cycle check, a rename that forgets the version, a restore that ignores a trashed parent, a trash that marks the children): all four are caught. The shrinker only drops operations, because shrinking every number as well ran for 15 minutes on one bug.
  - 100 sequences by default, about 15 seconds with pooled connections (`INKPACT_PROPERTY_RUNS` for more). A test class can ask for a small connection pool; the others stay unpooled so they cannot exhaust the server's connections.
- **Endpoint tests, 15,** and **two Playwright tests** that drive the tree API on the real server (needed once, because the tree queries use raw SQL).
- **A trashed page's key is not freed** and a trashed sibling may share a key with a live one; only live siblings are unique.
