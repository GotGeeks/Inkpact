# Run 1.10b: compaction worker

**Model:** O·high → S·high (planned on Opus 5.5, built on Sonnet)

## Goal

A background worker folds each page's live updates into one snapshot, with every guarantee in "Compaction guarantees": one transaction, a watermark, an advisory lock per page, idempotence, verification against a replay, and an archive instead of deletion. The same transaction writes the page's plain-text extract for search. A purge empties the archive after 30 days. Property tests with random edits, concurrent compactions and injected crashes must always end in the document an uncompacted replay gives.

## Done when

- A page with 500 live updates, or with live updates and 10 minutes without a new one, is compacted by the worker without anyone asking.
- A crash at any stage leaves the database exactly as it was; two compactions of one page at once give one skip; compacting twice changes nothing.
- A merge whose fingerprints differ is never committed and is logged as an error.
- Subscribing during a compaction never misses an update (scenario 10).
- The property and stress tests (scenarios 12 and 13) pass: the page always equals an uncompacted oracle, and live plus archived rows always equal what was appended.
- Archived rows older than 30 days are purged.

## Design

### Schema (migration `AddCompaction`)

- **`page_snapshots`**, one row per page:
  - `page_id` (primary key, cascade with the page), `state` (`bytea`), `state_vector` (`bytea`).
  - `watermark` (`bigint`): the highest `seq` it contains.
  - `version` (`int`): +1 per compaction.
  - `update_count` (`bigint`): all updates ever folded in.
  - `history_complete` (`bool`, true): false once the purge has removed any of this page's archived rows.
  - `updated_at`.
- **`page_updates_archive`**: `seq` (primary key, the same value it had live), `page_id` (cascade with the page), `data`, `user_id` (set to null when the user goes), `created_at`, `archived_at`. Index on `(page_id, seq)` for the full-history check and on `archived_at` for the purge.
- **`pages.content_text`** (`text`, not null, default `''`): the plain-text extract. The `tsvector` comes in 1.17.
- Entities `PageSnapshot` and `ArchivedPageUpdate`, configured like `PageUpdate` (except that the archive's `seq` is never generated: it keeps the value the live row had), plus a schema test, as for the earlier tables.

### Reading a page (`PageUpdateStore.LoadAsync`)

- Returns `PageContent(byte[]? Snapshot, IReadOnlyList<byte[]> Updates)` with `Inputs` (snapshot first). It still reads in one repeatable-read transaction, the snapshot row and then **all** live rows of the page in `seq` order.
- **Not `seq > watermark`:** a row that is still in `page_updates` has not been merged, because a compaction moves its rows out in the same transaction that writes the snapshot. Reading all live rows stays right even if rows commit out of `seq` order (see the watermark below).
- The hub passes `Inputs` to `DiffAsync`, or sends them in log mode. A client in log mode merges a snapshot like any other update.

### The compactor (`Compaction/Compactor.cs`)

`CompactAsync(pageId)` returns `Compacted`, `Skipped` (another compaction holds the lock), `NothingToDo` (no live updates), `Unavailable` (the sidecar is down) or `Failed` (undecodable, or verification failed). One transaction, read committed, and disposing it without a commit rolls everything back:

1. **Lock:** `pg_try_advisory_xact_lock(<class id>, hashtext(page_id::text))` with a fixed class id constant for compaction. If false, return `Skipped`: never wait. A hash collision between two pages only causes a skip. This is the one raw SQL statement outside the tree queries; update the CLAUDE.md rule ("Raw SQL only for recursive tree queries and advisory locks").
2. **Read:** the snapshot row **`for update`**, then the live rows (`seq`, `data`, `user_id`, `created_at`) in `seq` order, at most `MaxUpdatesPerCompaction`. None: return `NothingToDo`. That is the idempotence: a second run finds nothing and changes nothing. The row lock matters for the purge: it sets `history_complete = false` on the same row, so it waits for a running compaction and cannot shorten the archive between the compactor reading the flag and reading the archive. Raw SQL again, next to the advisory lock.
3. **Merge:** `CompactAsync([snapshot?, ..updates])`.
4. **Verify:**
   - The state fingerprint must equal the replay fingerprint.
   - When the full-history check is due, the state fingerprint must also equal `FingerprintAsync` of the page's archive plus this batch, in `seq` order, with no snapshot. It is due when the page already has a snapshot, `history_complete` is true and the new version is a multiple of `FullHistoryEvery`.
   - The full-history check catches a wrong earlier snapshot. Its cost grows with the history, so it is sampled (spike finding).
   - A mismatch logs an error with the page id and both lengths, throws `CompactionVerificationException` and commits nothing.
5. **Write the snapshot** (insert or update): `state`, `state_vector`, `watermark` = the larger of the old watermark and the highest `seq` in the batch (a late row with a lower `seq` is compacted on its own and must not move the watermark back), `version + 1`, `update_count + batch size`.
6. **Archive** the batch rows as they were read (EF `AddRange`, `archived_at` = now).
7. **Delete** exactly the batch: `page_id = X and seq = any(batch)` (`ExecuteDeleteAsync` with `Contains`).
8. **Text:** `pages.content_text` = the extract (`ExecuteUpdateAsync`). `version` and `updated_at` are not touched: they belong to the title and the place.
9. **Commit.**

**Why the watermark deletes exactly the read rows.** `seq` is a sequence, so a row can get a lower `seq` and commit after a row with a higher one. Deleting `seq <= watermark` could then remove a row that committed after the read and was never merged: lost data. Today the hub appends one page's updates one at a time under its lock, so it cannot happen. But the Joplin import (1.15) will also write updates, so the compactor must not depend on that. Deleting the read set still meets "only updates at or below the watermark are removed". Put this reasoning in a comment and in the architecture's watermark line.

**Stages:** a `CompactionStage` enum (`Locked`, `Read`, `Merged`, `Verified`, `SnapshotWritten`, `Archived`, `Deleted`, `TextWritten`) and an `ICompactionHooks` service, a no-op singleton in the app, awaited after each stage. Tests replace it to throw (a crash) or to block (to let appends in).

**Errors:**
- `YjsUnavailableException`: `Unavailable`.
- `YjsRejectedException` or `CompactionVerificationException`: `Failed`, logged as an error.
- A database error is thrown on to the worker.
- Every one of them rolls back.

### The worker (`Compaction/CompactionWorker.cs`)

- A `BackgroundService` on a `PeriodicTimer` (`PollInterval`) with the `TimeProvider`.
- **Each round:**
  - Find candidates in one EF `GroupBy` over `page_updates`: pages with at least `UpdateThreshold` live updates, or whose newest live update is older than `IdleAfter`. Oldest newest-update first, at most `PagesPerRound`.
  - Compact them one at a time. The sidecar is one process, so doing them in parallel would gain nothing.
  - If a compaction returns `Unavailable`, back that page off and end the round: the sidecar is restarting.
- **Backoff:** a page that returns `Failed`, or `Unavailable` (a compaction that times out kills the sidecar, and the oldest-first order would pick the same page again every round), is skipped for `FailureBackoff` (in memory, doubling up to 24 h, reset by a success). A broken page cannot keep the sidecar busy, and the other pages still get compacted. A restart retries it once; that is fine.
- **Purge** (`Compaction/ArchivePurge.cs`), every `PurgeInterval`, run by the worker:
  - Delete archived rows whose `archived_at` is older than `ArchiveRetention`, in batches of 10,000, one transaction per batch.
  - In the same transaction, set `history_complete = false` on the snapshots of the affected pages, so their full-history check stops (the history it needs is gone).
- **A round that throws** is logged, and the next tick tries again.
- **`CompactionOptions`** (section `Compaction:`): `Enabled` true, `PollInterval` 30 s, `UpdateThreshold` 500, `IdleAfter` 10 min, `PagesPerRound` 100, `MaxUpdatesPerCompaction` 5,000, `FullHistoryEvery` 10, `FailureBackoff` 1 h, `ArchiveRetention` 30 days, `PurgeInterval` 1 h. The test factory turns `Enabled` off and tests call the compactor, the worker's round and the purge directly.

### Edit streams for the tests

- A test-only script in the sidecar package, `server/sidecar/scripts/edit-stream.ts <edits> <seed> <file>` (next to `yjs-fixtures.ts`, so `tsconfig` and Prettier already cover it), writes a seeded stream of real Yjs updates. It builds paragraphs on `Y.XmlElement` directly, so it needs no TipTap and no new dependency.
- It simulates three clients on one `XmlFragment` that sync now and then: insert and delete text, split and join paragraphs, formatting attributes, emoji, and some updates delivered out of causal order.
- The .NET tests run it through `node` and cache the result per `(edits, seed)`, as the spike's `UpdateStream` did. It is not shipped and not part of the protocol.

## Tests

- **Guarantees, integration against Postgres and the real sidecar** (`Compaction/CompactorTests`, scenario 12):
  - **Crashes:** a crash at each stage, as a theory over the enum, leaves `page_snapshots`, `page_updates`, `page_updates_archive` and `content_text` exactly as before.
  - **Updates during a compaction:** updates appended while the compaction blocks at `Merged` stay live, and snapshot plus live equals the oracle.
  - **Concurrent compactions:** two at once give one `Compacted` and one `Skipped`.
  - **Idempotence:** compacting twice gives `NothingToDo` and no change.
  - **Corrupted merge:** a codec substitute whose fingerprints differ makes the compaction fail, log an error and change nothing.
  - **Full-history check:**
    - a tampered snapshot row is caught by the next due check;
    - with `history_complete` false the check is skipped.
  - **Odd documents:**
    - a non-TipTap page compacts, with empty text;
    - a page whose log holds an undecodable update returns `Failed` and stays as it was.
  - **Commit order:** a row with a lower `seq` that commits after the compaction's read (two open transactions in the test) stays live and is part of the page afterwards.
  - **Large logs:** `MaxUpdatesPerCompaction` splits a long log over several compactions with the same final result.
  - **Text:** `content_text` holds the extract after a compaction.
- **Scenario 10, in `SyncHubTests`:** a subscriber that joins while a compaction commits gets every update, in the diff or live, never neither. Check it in diff mode and in log mode.
- **Test setup:** each test class that needs the sidecar uses `IClassFixture<YjsSidecarFixture>` next to `[Collection(postgres)]`, since a class can be in only one collection.
- **Property test (FsCheck)** (`Compaction/CompactionPropertyTests`, scenario 12 as a model test):
  - **Schedules:** random sequences of `Append(n)`, `Compact`, `CompactWithCrashAt(stage)`, `CompactTwiceAtOnce` and `Load` over a generated stream.
  - **Checked after every step:**
    - the fingerprint of snapshot plus live equals the fingerprint of everything appended so far (the oracle never touches the database);
    - the stream holds updates delivered out of causal order, and a schedule may compact while one is still held back; the fingerprint does not see Yjs's pending structs, so the check after the held-back update arrives is what catches a snapshot that dropped them;
    - live plus archived equals appended, and every `seq` is in exactly one of them;
    - after a successful compaction the snapshot's bytes equal a fresh `compact` of everything appended.
  - About 100 cases, under a minute on a laptop; shrinking must still work.
- **Stress** (`Compaction/CompactionStressTests`, scenario 13):
  - 5,000 edits with an appender and a compactor running at once, random crashes and parallel attempts, as in the spike.
  - The 50,000-edit seeds only with `INKPACT_STRESS=1`.
  - The test writes its counts (compactions, crashes, skips, snapshot size) to the test output.
- **Worker** (`Compaction/CompactionWorkerTests`, with `MutableTimeProvider`):
  - **Thresholds:** 500 updates triggers a compaction; 499 updates within `IdleAfter` does not; the same page after `IdleAfter` does.
  - **Failures:** a failing page is backed off while another page still gets compacted; the sidecar being down ends the round without errors.
  - **Purge:** only rows past retention go, and the snapshots of their pages get `history_complete = false`.

### Where it differs from the card

1. **The plan review changed the card before building** (all folded into the text above): the snapshot row is read `for update` so the purge cannot shorten the archive under a full-history check; the watermark is the larger of the old one and the batch's; a page that returns `Unavailable` is backed off too (a compaction that times out kills the sidecar, and oldest-first would pick the same page every round); the script is in `scripts/`, not `test-support/`; test classes use `IClassFixture<YjsSidecarFixture>`.
2. **The extra `FingerprintAsync(replay)` call suggested by the 1.10a handoff is not made.** It would run the same function on the same inputs as `CompactAsync`'s `ReplayFingerprint`. The checks are state against replay, and the sampled full-history check.
3. **`PurgeBatchSize` is an option** (10,000), so a test can purge in batches of 7.
4. **A NUL character is dropped from the text** before it is stored: Postgres text cannot hold it, a document can, and one such page would otherwise fail every compaction forever.
5. **Scenario 10 is in `SyncHubDiffTests`,** not `SyncHubTests`, which has the sidecar helpers. The log mode there uses a codec that cannot diff and hands everything else to a real sidecar of its own.
6. **The property test compares the text as well as the fingerprint.** The fingerprint (state vector and delete set) does not see content, so a snapshot that dropped formatting or a deleted type would pass it. A second test cuts one stream at every point (through `MaxUpdatesPerCompaction`), which puts a cut between an update and the one it needs, so the snapshot holds a pending struct.

- **Compactor (34):** the card's list, with the crash theory over every stage with and without a snapshot, and the full-history check (healthy, tampered, skipped after the purge, only every tenth version).

### Found while building

- **The first version of the commit-order test passed with the bug in.** The late row was still uncommitted when the delete ran, so even `seq <= watermark` could not see it. The row has to commit between the compaction's read and its delete (the test does it from the `Merged` hook). Checked by putting the bug back.
- **Python's text mode writes CRLF on Windows,** and `dotnet format` then fails with ENDOFLINE on files that were LF. Edit with `newline=''`.
- **After a restart the first pages are backed off for an hour** if the sidecar is not up yet at the first tick: they return `Unavailable`. Harmless (they are compacted an hour later), and the alternative is a way to tell "starting" from "timed out", which the codec does not offer.
- **The sidecar still does one request at a time.** A compaction of up to 5,000 updates makes subscribes to other pages wait for it and fall back to the log after `DiffTimeout`. Not measured with 5,000 real updates; `MaxUpdatesPerCompaction` is the limit, and a second process is the fix if it hurts.

### Not covered by a test

- The worker's timing with the real 30 s poll and the hourly purge: the tests use 200 ms and call the purge directly.
- A `Failed` page that is fixed by an upgrade of the sidecar: it is retried after its backoff, or after a restart.
- Compaction of a page while the sidecar restarts half way: the hub tests cover the sidecar dying, the compactor tests the exception, not the two together.

- A page's text (`content_text`) is only as fresh as its last compaction, up to ten minutes behind. Search (1.17) must accept that.
