# Run 1.05: local account and login

**Model:** O·high → S·high (planned on Opus 5.5, built on Sonnet)

## Goal

The first person to open a fresh install creates the admin account, then signs in and out with an email and password. Sessions live in Postgres, so logging out everywhere and revoking a session take effect at once. Restarts keep everyone signed in. The setup and login pages work in English and Dutch, on a phone and on plain HTTP.

## Inputs

- `docs/architecture.md`: "Security from day one" (sessions, passwords, Data Protection keys), the `users` and `workspaces` rows ("every user gets a private workspace on signup"), "Trusted administrator".
- Run 1.03: `users` (email, normalized email, password hash), `DatabaseTestBase`. Run 1.04: security headers, e2e harness, the plain-HTTP project.
- GarageStack `AuthenticationSetup.cs`: the "auto" Secure policy that keeps plain-HTTP LAN installs working.

## Done when

- On a fresh database, `/` shows the setup page. Creating the admin with the setup code signs the admin in, creates their private workspace, and closes setup for good.
- Login, logout and logout everywhere work. A deleted session row signs that browser out on its next request.
- The cookie is `__Host-inkpact` (HttpOnly, Secure, SameSite=Lax, Path=/) over HTTPS, and `inkpact` (HttpOnly, SameSite=Lax) on plain HTTP.
- A restart keeps sessions valid, because the Data Protection keys are on the data volume.
- Unit, integration and e2e tests pass on every project, including plain HTTP.

## Design

### Packages (to approve)

- **Geralt** (MIT, libsodium; 4.4.0, July 2026) for Argon2id: an encoded PHC string, constant-time verification, and `NeedsRehash`. libsodium is the reference implementation. Its native binaries cover linux-x64, linux-arm64 and musl.
  - The alternative is Konscious.Security.Cryptography.Argon2 (managed, no native code, last release 2024). It is 2–3× slower and has no encoded-hash helpers.
- **vue-router**: `/setup` and `/login` now, and the tree and editor routes from 1.08 on. 1.12 needs it for lazy loading anyway.
- Nothing else. Cookie authentication and Data Protection are in the ASP.NET shared framework.

### Schema (migration `AddSessions`)

- `users.is_admin` (bool). The setup account is admin. Admin pages arrive in 2.9, and invites in 2.1.
- `sessions`:
  - `id` (text, 32 random bytes, base64url), the key the cookie points to;
  - `user_id` (FK, cascade delete);
  - `ticket` (bytea, `TicketSerializer` output);
  - `created_at`, `last_seen_at`, `expires_at`;
  - `user_agent` (truncated to 256 characters).
  - Index on `user_id` and on `expires_at`.

### Passwords (`IPasswordHasher`, `Argon2PasswordHasher`)

- Argon2id with m = 46 MiB, t = 1, p = 1 (OWASP's first option), stored as the PHC string. On a successful login, `NeedsRehash` upgrades old parameters.
- A `SemaphoreSlim(4)` caps concurrent hashes, so a burst of logins can't exhaust memory before rate limiting arrives in 1.06.
- Policy: 12–128 characters, no composition rules, and not equal to the email (NIST style). Codes: `password_too_short`, `password_too_long`, `password_same_as_email`.
- **Unknown email:** a dummy hash is verified anyway, so the response time does not reveal whether the account exists. Both cases answer `invalid_credentials`.

### Sessions (`PostgresTicketStore : ITicketStore`)

- `StoreAsync` creates the row and returns the key. `RetrieveAsync` returns null for a missing or expired row, and updates `last_seen_at` at most once per minute. `RenewAsync` updates the ticket and expiry. `RemoveAsync` deletes the row.
- It uses `IDbContextFactory<InkpactDbContext>`, because the cookie options, and so the store, are singletons.
- 30 days, sliding. `SessionCleanupWorker` deletes expired rows every hour.
- The ticket holds only the user id claim and the session id. The user is loaded from the database per request, so a deleted user loses access at once.

### Cookie (`AuthenticationSetup`)

- Cookie authentication with `SessionStore`, `HttpOnly`, `SameSite=Lax`, Path `/`, and no Domain.
- **Secure policy `Auth:CookieSecure`:**
  - `auto` (the default) follows the request;
  - `true` always sets `Secure`;
  - `false` never does.
- **Name per request:** a small `ICookieManager` wrapping `ChunkingCookieManager` reads and writes `__Host-inkpact` when the request is HTTPS and `inkpact` when it isn't. So the hardened prefix is used wherever the browser allows it, and a LAN install over plain HTTP still logs in. (GarageStack: `upgrade-insecure-requests` and a Secure-only cookie each blanked or broke LAN installs once.)
- **API behaviour:** no redirects. `OnRedirectToLogin` → 401 `{ code: "not_authenticated" }`, `OnRedirectToAccessDenied` → 403 `{ code: "forbidden" }`.
- **Forwarded headers:** `UseForwardedHeaders` for `X-Forwarded-Proto` and `-For`, trusted only from `Network:TrustedProxies`. The default is loopback plus the private ranges (10/8, 172.16/12, 192.168/16), which cover Docker and Unraid networks. A spoofed header from a LAN client can at worst make its own cookie unusable. The client IP for rate limiting (1.06) depends on this.
- **Authorisation:** set `FallbackPolicy = RequireAuthenticatedUser` now, so a new endpoint is denied unless it says otherwise. The permission service and the policy-coverage test stay in 1.06.

### Data Protection

- `SetApplicationName("Inkpact")` and `PersistKeysToFileSystem(DataProtection:KeysDirectory)`, default `data/keys`, with the directory set to 0700 on Unix.
- `DataProtection:CertificatePath` (plus a password) optionally encrypts the keys at rest. Without it the keys are stored in plain form: under "Trusted administrator", whoever can read the data volume can read everything anyway, and a certificate on the same volume adds nothing. ASP.NET logs a warning about this at startup; leave the warning as it is.

### First-run setup

- When `users` is empty, the server generates a **setup code** (8 characters from an unambiguous alphabet). It is logged at startup in a clearly marked line and kept in memory only. `Auth:SetupCode` overrides it, for unattended installs and the e2e run.
- Anyone who reaches a fresh install first would otherwise become admin. Behind a reverse proxy on the internet that matters; the code proves access to the container logs.
- `POST /api/auth/setup {setupCode, email, displayName, password, workspaceName}`:
  - in one transaction, under an advisory lock: check that `users` is empty; create the admin and their private workspace (the client sends the translated default name); sign in.
  - `409 setup_not_available` once a user exists. `400 setup_code_invalid` when the code is wrong.
  - The code is compared in constant time.

### Endpoints (all JSON)

Bodies must be `application/json`, because a cross-site form cannot send that without a CORS preflight. Together with SameSite=Lax this covers CSRF until the tokens arrive in 1.06.

| Method and path | Auth | Result |
| --- | --- | --- |
| `GET /api/auth/state` | anonymous | `{ setupRequired, user: { id, email, displayName, isAdmin } \| null }` |
| `POST /api/auth/setup` | anonymous | 204 + cookie |
| `POST /api/auth/login {email, password}` | anonymous | 204 + cookie, or 401 `invalid_credentials` |
| `POST /api/auth/logout` | authenticated | 204; deletes this session |
| `POST /api/auth/logout-everywhere` | authenticated | 204; deletes every session of the user, including this one |

- Validation errors: 400 `{ code, field }`.
- An unsupported content type is 415 `{ code: "unsupported_media_type" }`.

### Client

- **vue-router**, with routes `/setup`, `/login` and `/` (a placeholder home with the user's name, logout and logout everywhere).
- A guard asks the auth store:
  - `setupRequired` → `/setup`;
  - not signed in → `/login?redirect=...` (only same-origin relative paths are accepted);
  - signed in on `/login` or `/setup` → `/`.
- **`api.ts`:** a fetch wrapper with `credentials: 'same-origin'` and JSON. It throws `ApiError(code, field)`, and components show `t('errors.' + code)` with a generic fallback key.
- **`useAuthStore` (Pinia):** `load()`, `setup()`, `login()`, `logout()`, `logoutEverywhere()`.
- **Pages:**
  - `SetupPage`, `LoginPage` and `HomePage` with native inputs and the Reka `Label`. They use the correct `autocomplete` values (`email`, `current-password`, `new-password`, `one-time-code`).
  - Errors live in an `aria-live` region and are linked to the field with `aria-describedby`.
  - Buttons are disabled while a request runs.
  - Layout is mobile first, using the tokens only.
- Every string is in `en.json` and `nl.json`, including all the error codes above.

### Tests

**Server (xUnit, Testcontainers):**
- Hasher:
  - round trip;
  - a wrong password fails;
  - rehash on old parameters;
  - the encoded string starts with `$argon2id$v=19$m=47104,t=1,p=1$`;
  - the concurrency cap.
- Password policy: the limits.
- Ticket store:
  - store, retrieve and remove;
  - an expired row returns null;
  - renew moves the expiry;
  - `last_seen_at` throttling;
  - cleanup deletes only expired rows.
- Setup:
  - a fresh database reports `setupRequired`;
  - the wrong code gives 400;
  - success creates the admin and the workspace and signs in;
  - a second setup gives 409;
  - two concurrent setups produce exactly one admin.
- Login:
  - success sets the cookie;
  - a wrong password and an unknown email both give 401 `invalid_credentials` with the same body;
  - the email is case-insensitive.
- Sessions:
  - logout deletes the row and the cookie stops working;
  - logout everywhere signs out a second client;
  - deleting a row directly signs that client out;
  - a deleted user loses access.
- Cookie:
  - over `https://` the name is `__Host-inkpact` with Secure, HttpOnly, SameSite=Lax, Path=/ and no Domain;
  - over `http://` it is `inkpact` without Secure;
  - `X-Forwarded-Proto: https` from a trusted proxy gives the `__Host-` name, and from an untrusted address it does not;
  - `CookieSecure=true` sets Secure on HTTP.
- Errors: 415 on a form post; 401 JSON (not a redirect) on `/api/auth/logout` without a session.
- Data Protection: a cookie issued by one app instance still works after "restarting" with the same keys directory, and not with a different one.

**Web (Vitest):**
- `api.ts` error mapping;
- the auth store;
- the guard rules, including an open-redirect attempt (`?redirect=//evil.example`);
- LoginPage and SetupPage: they render, validate, show translated errors and disable the button while busy.

**E2E (Playwright):**
- Every run uses a fresh database: the config sets `E2E_DB_NAME=inkpact_e2e_<timestamp>` once, and workers inherit it. `Auth__SetupCode` is fixed for the run.
- A `setup` project creates the admin and saves the storage state; the other projects depend on it.
- Specs:
  - login and logout;
  - wrong password;
  - logout everywhere signs out a second browser context;
  - a deep link while signed out returns to the page after login;
  - setup is closed once done;
  - keyboard-only login;
  - plain HTTP: logging in works and the cookie is named `inkpact`.
- The 1.04 smoke specs run signed in.

## Decisions (confirmed)

1. Geralt (libsodium) for Argon2id.
2. vue-router added now.
3. First-run setup protected by a code from the logs (or `Auth:SetupCode`).

## As built: changes from the plan

- **Setup uses a serializable transaction instead of an advisory lock.** Raw SQL is for tree queries only (CLAUDE.md). Two concurrent setups give exactly one account; the loser gets 409. Postgres reports the race as a serialization failure, a deadlock or the unique email index, and the code accepts all three, also when EF wraps them.
- **`UseForwardedHeaders` trusts a request with no client address** (a Unix socket), which is also what the test server has. That is the framework's behaviour and harmless: a Unix socket peer is local.
- **API responses are `Cache-Control: no-store`.** Added so that "who is signed in" can never come from a cache.
- **A request that no endpoint and no file claims is a plain 404** (small middleware after static files). Without it the fallback authorisation policy answered 401 for a missing `/assets/x.js`. A catch-all endpoint was tried and does not work: static files only serves while no endpoint has been selected.
- **`ApiError` leaves out `field` when it is null.**
- **`Microsoft.EntityFrameworkCore` logging is Warning** in `appsettings.json`; at Information it logged every SQL command.
- **Server tests use a `RemoteIpStartupFilter`** to give the test server a client address, so the trusted-proxy rules can be tested.
- **Playwright:** a `setup` project creates the administrator through the setup page and saves the signed-in state; `desktop`, `phone` and `iphone` reuse it. Every run uses a fresh database (`inkpact_e2e_<run id>`, left behind in the dev container: `docker compose -f deploy/docker-compose.dev.yml down -v` clears them). `plain-http` signs in over a non-localhost name. `lifecycle` runs last, because "sign out everywhere" ends the shared session.
- **A Playwright trap, worth remembering:** `request.newContext()` from `@playwright/test` inherits the project's saved sign-in. The first version of the anonymous API tests therefore ran signed in, and its logout test ended the session every other test used. They now pass an explicit empty `storageState`.
- **WebKit reports `SameSite=Lax` as `None`** in `context.cookies()`; the e2e test skips that one assertion there, and the server tests check the header itself.
