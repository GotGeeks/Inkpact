# Search

Detail for the `pages (search)` row of the data model in [architecture.md](../architecture.md). Moved here from the plan (review 2026-11-11, finding 6.1); nothing changed.

Postgres full-text search (run 1.17). The text search configuration `inkpact_search` is `simple` with the `unaccent` dictionary in front of it, so that case and accents do not matter and English and Dutch notes both match without stemming (the `unaccent` extension, which the migration creates). The punctuation that joins words into one token for Postgres' parser (`report.pdf`, `user@example.com`, `3.14`, `2026-11-03`) is turned into spaces before a vector is made, so the text is split into runs of letters and digits as the search is. A search word is a prefix (`vergad:*`), so a half typed word finds its page. Only the first 200,000 characters of a page's text are indexed, because a `tsvector` holds at most 1 MB and a note may have 8,000,000 bytes of text. The vectors are generated, so they are right after every kind of write; the compactor writes `content_text` only when it changed, as writing it builds the vectors again. The pages search looks at are those of the SQL function `live_pages`, which the tree reads too. `title_vector` exists because ranking has to read a vector, which costs what the page is long: the pages that match by their title or tags are ranked on it, and the pages that match in their text only are ranked among the 1,000 edited last. The endpoint is `GET /api/workspaces/{id}/search?q=`: at most 30 results, title and tag matches first, then text matches, each with its matches marked, and `more` when more pages matched. A snippet is about 400 characters of the text around the first matching word, which a regular expression finds as the index would; the server marks the words in it and in the title, so no markup reaches the client. Other backends (such as vector search for related notes) can be added later without changing page storage
