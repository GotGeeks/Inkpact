# Sync: edits a Sync would delete are kept as a copy

Detail for point 7 of the sync flow in [architecture.md](../architecture.md). Moved here from the plan (review 2026-11-11, finding 6.1); nothing changed.

**Edits a Sync would delete are kept as a copy.** Yjs deletes text whose block is deleted, also text that reaches the block's document later: a client that typed offline into a paragraph that someone else (or the Joplin import) deleted meanwhile would lose it on reconnect, with nothing merged and nothing said. So before applying a Sync the client notes the items it made that the server's state vector does not cover (content only: formatting items Yjs cleans up itself when concurrent formatting meets); if applying the Sync deletes any of them, it keeps the page as it was just before and makes a new page right after the original, in the original's workspace (`GET /api/pages/{id}` says which), titled "<title> (your offline changes)" in the person's language, and says where it is in a notice. The page and its content are one request: `POST /api/workspaces/{id}/pages` takes an `id` the client chose and `content`, the page's first Yjs update (base64, from the first paragraph as every page, at most the largest page that can be opened (exactly half of `Sync:MaxQueuedBytes`, 8 MiB by default: `SyncOptions.MaxPageBytes`, the limit the import keeps its notes to) and an eighth more, since the copy is written again from the page's blocks and can come out a little larger than the update the page was made from (`SyncOptions.MaxCopyBytes`, 9 MiB by default, still well inside the queue). The handler enforces that limit exactly, on the base64 text and again on the decoded bytes; the route's own body limit (the copy in base64 and 64 KiB for the rest) is only a coarse cap, which Kestrel enforces before a body far too large is read, stored with the page in one transaction. Sent again with the same id (its answer was lost), it gives the page it made, never a second one, and there is never a page without its content. When the place beside the page is gone (it or its parent is in the trash), the copy goes to the top level. A copy that cannot be made yet is tried again when the connection is back, and the person is told once that it is waiting; a 413 (the server's, or a proxy's body limit) is not tried at another place, since the size is the cause. A copy the server itself says is larger than that (`content_too_large`; only a page that could not be opened has such a copy) is not tried again at all, and the person is told once that the page is too large to keep a copy of, also after having been told it was waiting; either way it waits in the tab, and it is dropped when the session ends, so it is never written for whoever signs in next. Live Updates are not checked: online, the window is one round trip.

## A page the server replaces while it is open (run B.5b)

"Live Updates are not checked" stays true for what other people type. The one live change that deletes every block at once is a replacement the server makes itself (a Joplin re-import, a restored version), and that is no longer sent as an Update: it is sent as a `Replaced` message and a Sync, so the check above runs for it. On a client that knows `Replaced`, any change the server had not confirmed keeps the page as it was as a copy, also when it is only formatting or a deletion. The rules are in [`docs/sync-protocol.md`](../sync-protocol.md), "When the server replaces a page's content".
