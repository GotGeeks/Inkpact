# Large pages and notes

Detail for the size limits under "Attachments" in [architecture.md](../architecture.md). Moved here from the plan (review 2026-11-11, finding 6.1); nothing changed.

Configurable size limit per file, 50 MB by default. A page whose Yjs state is over 5 MiB stays a normal, editable page, but a notice above it says it may be slow (measured once, after the page first is in step with the server). What a page can be is set by what the sync hub can send: a page is opened by one reply that holds its whole state, and a client whose send queue goes over `Sync:MaxQueuedBytes` (16 MiB) is dropped, so a page larger than that could never be opened (and one near it would take the sidecar's diff past its timeout). So an imported note is converted only up to `Import:MaxNoteTextBytes` (8,000,000 bytes of text) and `Import:MaxNoteUpdateBytes` (8 MiB for the update it makes); for a replacement, the new update alone must fit, and the page's stored updates with the new one added must be within three quarters of `Sync:MaxQueuedBytes` (12 MiB): when they are over `Import:MaxNoteUpdateBytes` the import compacts the page right after the write (see "Importing again"), and a client that opens it before that is sent all of it, which then still fits the queue with the traffic around it. The compacted page is never larger than its inputs. A note whose update is up to about 6 MiB (about 5 MB of text: the update is about a fifth larger than the text, for the structure of every paragraph) therefore stays text when it changes in Joplin, where one over about 4 MiB did before; it becomes a file when its new update is over `Import:MaxNoteUpdateBytes`, or when the old and new content together are over three quarters of the queue (a note of 6 MB of text, whose update is 7.3 MB, is over it); start-up refuses either above half of `Sync:MaxQueuedBytes`, so the reply plus the traffic around it fits. A note over either becomes a page that holds the note whole as a file (its body as `<title>.md`, or `.html`, with no external id, served as a download) followed by every file the note uses, since the body can no longer show them, and the report says `stored_as_file`; this goes for a new page, a replacement and a conflict copy alike. A body larger than a file may be (50 MB) cannot be kept, and the note is skipped (`item_too_large`) before any of its files are stored; so is a note whose page of files would itself be too large (thousands of files). A body file the page already has with the same name and bytes is used again. On a re-import, what the field step took stays taken and the line says `updated` with `item_too_large`. The page keeps the note's text for search in `file_text` (plain text, the first 200,000 characters), which the import writes for a new page, a replacement and a conflict copy, and which the compactor never touches, since it rewrites `content_text` from a document that holds only a file node; a note stored as a file before run 1.17c gets it at the next import, which the migration makes convert such a note again (its item marked as from an older converter), when nobody changed its page here.
