# Tags in the interface

Detail from [architecture.md](../architecture.md). Moved here from the plan (review 2026-11-11, finding 6.1); nothing changed.

**Tags in the interface** (run B.2). A page's tags show under its title as pills, each opening that tag's page; an editor adds one (an existing tag of the workspace, suggested by its name, or a new one) and removes one, through `POST /api/pages/{id}/tags` (`{add: names, remove: ids}`, removed first, then added). A name is cleaned by the import's own rule (`TagNames.Clean`: no control characters, tabs and line breaks as spaces, trimmed, inner spaces kept), so a name typed here finds the tag the import made from it; it is matched to an existing tag by its lower case, with that tag's own spelling kept, or made new. Accents count: "cafe" and "café" are two tags, and the add field offers to make one next to the other (finding a tag while typing ignores accents, matching a name does not). The page row is locked `for update` for the change (never the workspace's tree version: a tag is not the tree's title or place), so two requests on one page run one after the other; two pages making the same new tag at once meet the tags table's unique index, and the losing request is retried once, which then finds the tag the other made (a rename that drops an unused tag the request had just found is retried the same way). The client sends a row's changes one at a time, each after the last was answered, and reads the row again on the same queue, so an older answer never replaces a newer one. A page in the trash, or below one (the same rule `live_pages` gives the tree), refuses the change (`page_in_trash`). The "Tags" view (`GET /api/workspaces/{id}/tags`) lists the workspace's tags that are on at least one live page, with that count; a tag on none is left out of the list and the suggestions, but kept, reused the next time its name is typed. A tag's own page (`GET /api/workspaces/{id}/tags/{tagId}/pages`) lists its live pages by title (case ignored, sorted and cut in the database), with the parent's title, at most 200 and a flag when there are more, and lets an editor rename the tag (`PATCH`). A change of case only is allowed. A name another tag has is refused: `tag_name_taken` when a live page has that tag, `tag_name_taken_in_trash` when only pages in the trash do (the Tags view does not show it); a tag no page has at all is only kept so its name reuses it, so the renamed tag takes over that role and the unused one is deleted. Two renames to one name at once let one through and refuse the other with `tag_name_taken`. Search (`tag_text`), the export's front matter and the Joplin re-import's three-way comparison of a note's tags all read `tags` and `page_tags` straight, so a tag added, removed or renamed here needs no code of its own to reach them.
