# Joplin import: importing again

Detail for the section "Joplin import mapping" in [architecture.md](../architecture.md). Moved here from the plan (review 2026-11-11, finding 6.1); nothing changed.

## The `import_items` table

How an item that was imported is recognised, and what the re-import's three-way comparison needs (run 1.16). `content_hash` is the fast path: when the item's file is unchanged, and for a note the item of every file it uses and the ids of its tags too (Joplin rewrites a resource's item when its bytes change, not the note's), nothing is parsed. `base` (`jsonb`) is what the other app had, field by field, when it was last imported (for a note its content key: the body, whether it is HTML, and the versions of the files it uses; and the title, notebook, to-do fields and tags; for a notebook the title and notebook; for a tag its name), so a change in the other app is told from its bookkeeping. `page_fingerprint` (SHA-256 of the page's state vector and delete set) says whether the page was edited here: a deletion alone moves no state vector, so the state vector (`state_vector`) is only the fallback for items made before run 1.16, which have no fingerprint and no base. `converter_version` says which version of the conversion made the page's content. `page_seq` is the sequence number of the import's own last update of the page: with nothing in the log after it (and no snapshot past it), nobody has written to the page, which needs no replay to know. An item of run 1.15 (no base, a hash of the note's file alone) whose file is unchanged gets its base from the note as it is, since that is the version run 1.15 imported; a file of such a note whose bytes changed since cannot be told. A resource's version is its `blob_updated_time`, size and data length, which change with its bytes and not with the rest of its item (OCR text, its own times)

## Importing again

**Importing again** finds every item by its external id in `import_items`; nothing is duplicated, and the unique indexes make a duplicate a database error as well. An unchanged note is counted as already imported, without parsing it; one whose file changed but whose body did not (Joplin's bookkeeping, or a field) too, and its file hash moves on. A note that changed is compared three ways for its content (run 1.16a): changed only in Joplin (the body's hash differs from the base, the page's fingerprint is the stored one), the page's content is replaced by one Yjs update that deletes every block and writes the new content, published through the sync hub so that a page that is open updates at once. It is written under the hub's page lock, and only when no update was stored since the page was read (none in the log above the last sequence number read, and no snapshot whose watermark is past it, for the compactor may have folded one in meanwhile) and the page is still in the tree; otherwise nothing is written and the note is compared again (now as changed here), because text typed into a block the replacement deletes is deleted with it. A replacement whose page with the old content would be over `Import:MaxNoteUpdateBytes` is compacted right after it is written, once the page's lock is let go (run 1.22). Not inside the lock: every client of the page waits for it, a client's socket stops answering pings meanwhile and is dropped after eight seconds, and a compaction of a large page takes seconds. So a client that opens the page in those seconds is sent the old content with the new, which the size rule keeps within three quarters of the queue. It is the compactor's own compaction, with every guarantee above, asked again until nothing is live (at most five rounds). It never waits and never fails the import: when the worker has the page at that moment, or the sidecar is down, or the merge does not verify, the replacement stays written, and the worker compacts the page at its next round, which takes any page whose live updates are over `Compaction:LiveBytesThreshold` (2 MiB). A page whose stored updates are already over the limit when a new version comes (its compaction could not run) is compacted before the replacement is made, so the replacement is measured against the page and not against its history. The compaction leaves the replacement's sequence number as the page's last, so the next import still sees the page as unchanged here without reading it. A client that typed offline into the old blocks, and reconnects after the replacement, keeps that text in a copy beside the page (sync flow, step 7); changed only here, left alone; changed in both, the page keeps its content and Joplin's version becomes a new page right after it, titled in the words the upload came with (the client sends them in the person's language, for example `{title} (Joplin)`; the server writes no language of its own, and without them the copy has the note's title), with Joplin's to-do fields and no tags, not linked to the Joplin id (so no later import touches it), and listed in the report with both pages. The item then moves on to the version of Joplin it has seen, so the same export makes no second copy, but keeps the page's old fingerprint: the next change in Joplin makes another copy, and a page edited here is never overwritten. A page made by an older converter version that nobody has edited is converted again, so a better conversion reaches notes that are already imported. A file used by the note with the same bytes is reused; one whose bytes changed gets a new attachment row, and the old row stays (an earlier state of the page may show it) but gives up its external id. The fields of an item are compared the same way, each on its own (run 1.16b): the base (what Joplin had when it was last imported), Joplin now, and the page now. Changed only in Joplin: taken. Changed here, or in both places with different values: the value here stays, and the report says so (`title_kept`, `notebook_kept`, `todo_kept`, `completed_kept`, `due_kept`, `tag_name_kept`). The fields are a note's title (cleaned as on import), place (its notebook), to-do state, completed and due dates, and tags, and a notebook's title and place, and a tag's name. The base moves to Joplin's value as soon as that value has been seen, also when the value here is kept, so a kept field is reported once and a later change in Joplin is compared with what Joplin had then; the one exception is a move that is refused, which leaves the base and the item's hash as they are so the next import tries again. A move goes through the tree's own rules (`TreeService.CheckMoveAsync`: the new parent is live and in the workspace, and no cycle), under the workspace lock, to the end of the new notebook, raising the page's version and the tree version; a refusal says why (`move_target_in_trash`, `move_cycle`, `move_target_missing`). The to-do fields hang together in one respect: a page that is not a to-do has no due date or completion, so when taking some of them and keeping the others would make one, all three stay as they are here (`todo_kept`). A due date that is taken moves the importing person's undelivered reminder (or makes or removes one). A page whose old notebook is in the trash here or gone has been moved here, wherever it is now (the top level included). Tags are a set, compared in the ids they have here (two tags of Joplin can be one tag here): what Joplin added since the base is added, what it removed is removed if the page still has it, and a tag added here is never touched. A tag is renamed only when it was made for this Joplin tag, still has the base name and no other tag has the new name. A JEX keeps a note's tags as items of their own, so a note's hash includes its tags. An item of run 1.15 has no base: a field that differs keeps the value here and the item's line says `base_unknown` once; the base is Joplin's from then on. A note that Joplin has put in its trash (`deleted_time`) and that an earlier import made goes to the trash here when nothing was changed here (its fields are the base's and nothing was written to its content), where it can be restored; a notebook goes only when everything below it goes, and only the highest page is put in the trash, so restoring it restores everything under it. What changed here stays and is listed as `deleted_in_joplin_kept`; a page that is unchanged but has a page below it that stays is listed as `deleted_in_joplin_not_empty`, and one that could not be looked at (the sidecar is down) stays and is counted as failed. The tree is walked without recursion. A note that is missing from the export is never deleted, since an export can be of one notebook, and a page that the import put in the trash is not restored when the note comes back in Joplin. An item whose page the person has put in the trash is left there (counted as already in the trash), and nothing new goes under it: those items are listed as `notebook_in_trash` (restore the notebook and import again). An item whose page or tag is gone altogether is imported again. An import that was running when the app stopped is marked `interrupted` at the next start, and uploading the same file again finishes it; one whose job could not even write its end (the database went away) is marked by the next upload to the workspace, so it never blocks it.
