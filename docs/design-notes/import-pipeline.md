# Joplin import: how it runs and how a note is converted

Detail for "Joplin import mapping" in [architecture.md](../architecture.md). Moved here from the plan (review 2026-11-11, finding 6.1); nothing changed. The re-import rules are in [import-reimport.md](import-reimport.md) and the links in [links.md](links.md).

**How the import runs (run 1.15b).** The export is uploaded once, streamed to `/data/imports`, and a single background worker reads it with `System.Formats.Tar` (nothing is extracted; only entries named like an item or a resource are looked at). One workspace imports one file at a time: the upload claims its place by inserting the import's row first, and a partial unique index allows one waiting or running import per workspace. The server runs one import at a time. The upload refuses a second import before it reads the body, which a browser still sending a large file often sees as a reset connection, so the client first asks `GET /api/workspaces/{id}/imports/open` (run 1.15c).

- **Where the pages go.** Notebooks are added at the end of the top level, below what is there; children keep their nesting. Within a notebook, its sub-notebooks come first and then its notes, each sorted by title without regard to case or accents (Joplin's own order is per device). A notebook that is its own ancestor in the file is put at the top level; a note whose notebook is not in the file goes there too, and the report says so. Every page takes the key after the last live page under its parent, read under the same workspace lock a tree operation takes, so a page a person adds while the import runs (even under a notebook the import made) never collides with one of the import's.
- **One transaction per note, and a short one**: the files are stored, the content is converted and the sidecar builds and checks the page's first update first, outside any transaction. Only then is the workspace locked, for the key and the rows (the page, its attachments, its update, its tag links, its reminder, its import item), so a person's changes to the tree never wait for a large file or a slow sidecar. A job that stops leaves whole notes only. Resources are copied onto each page that uses them (the stored file is shared), so a page's files belong to the page.
- **What is left out, and said so:** encrypted items (the report lists them; export from Joplin desktop with encryption off), items in Joplin's trash (counted, not listed), and any item over 64 MB (listed). A conflict note from Joplin keeps its title and is listed in the report as a conflict: nothing user-facing is written in a language on the server.
- **The sidecar.** A page is never written without its content. While the Yjs sidecar is down the job waits for it, up to two minutes, and then ends the import as failed with `sidecar_unavailable`. Content the sidecar's builder refuses is a fault in the conversion: that note is reported as failed and the rest go on.
- **Timestamps and to-dos.** `user_created_time` and `user_updated_time` are the page's created and updated times. To-do state, completion and due date go on the page, and a to-do with a due date gets a reminder for the person who imported.

**How a note's content is converted (run 1.15).** On the server, in three steps: Markdig parses the Markdown and AngleSharp parses HTML (HTML notes and HTML inside Markdown); a mapper builds the editor's own nodes (ProseMirror JSON, in the names of the editor's schema) and never copies markup through; the Yjs sidecar's `build` operation writes that JSON as the page's first update. Three rules keep the result safe and stable:

- **One allow-list.** `web/src/editor/allowList.json` lists the tags and attributes the client's paste sanitiser keeps. The server is built with the same file, and its mapper understands exactly those tags; it copies no attribute from the HTML (it reads a few, such as an address or a span, to decide what to build). Anything outside the tags keeps its text and loses its element, and the report says so. Script, style, frames and objects go with their content. Links follow the client's rule (`http`, `https`, `mailto`, absolute only), attachments are only ever the export's own resources by id (an id written in a note's HTML means nothing), and the sidecar refuses any node, mark or attribute the editor does not have.
- **Opening an imported page writes nothing.** The page starts from the fixed first-paragraph update (the sidecar applies it, deletes that paragraph and writes the content after it), ends with the empty paragraph the editor would add after a table, list or image, and has regular tables (every row as wide as the table). Otherwise each client that opened the page would add its own paragraph or repair the table, and two clients would disagree.
- **Contracts are tested across the languages.** The same fixture file (`server/tests/Inkpact.Api.Tests/Fixtures/import/conversions.json`) is the expected output of the C# conversion tests and the input of a web test that loads each document through the sidecar into the real editor.

Nesting deeper than the editor handles is flattened (the text stays), and markup or Markdown nested thousands of levels deep is kept as plain paragraphs, because the parsers' time grows with the square of the depth.
